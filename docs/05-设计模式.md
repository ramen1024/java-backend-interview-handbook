# 第 5 章 设计模式：面试要的是判断力，不是背 23 个名字

> 一句话定位：这一章几乎不会单独成卷，但它决定了你讲项目时听起来像"写业务的人"还是"能做设计的人"。

## 一、本章考察重点概览

设计模式是面试里最容易被低估的一章。它很少以"请说说观察者模式"这种形式出现，更多是嵌在项目追问里：你说做了个订单超时关闭，面试官问"以后要加退款、加对账怎么办"；你说用了一堆 if-else 判断渠道，面试官问"再加一个渠道要改几处"。这些问题的答案，就是设计模式。

面试官在这一章实际筛三种能力：

1. **能不能识别变化点。** 模式不是目的，"哪里会变、把变的部分隔离出来"才是。能指出"变化的维度"比能背出类图重要得多。
2. **有没有代价意识。** 每引入一层抽象就多一次跳转、多一个类、多一份理解成本。只会说"用了策略模式所以很优雅"的人，通常没维护过自己设计的代码。
3. **能不能自我批判。** 被问"现在回头看这个设计有什么问题"，能说出"这里其实过度抽象了"的人，可信度远高于坚持"我们设计得很好"的人。

| 考点 | 出现频率 | 难度 | 说明 |
| --- | --- | --- | --- |
| 单例与 DCL 的 volatile | 高 | 初级 | 开场常客，能追问到指令重排 |
| 策略模式消除 if-else | 高 | 中级 | 几乎必问"你的项目里怎么落地" |
| 代理 / 装饰 / 适配器的边界 | 高 | 中级 | 三者最容易混，表格答法最稳 |
| 工厂三兄弟的区别 | 中 | 中级 | 常结合 Spring 的 BeanFactory 问 |
| 模板方法与框架设计 | 中 | 中级 | 能联系 AQS、JdbcTemplate 加分 |
| 责任链与 Filter / Interceptor | 中 | 中级 | Web 开发背景必问 |
| Spring 中的设计模式清单 | 高 | 中级 | 考的是"读框架源码的习惯" |
| 过度设计的识别 | 中 | 高级 | 高级岗位用来筛"有判断力的人" |

## 四、题目详解

### Q1. 设计模式在面试中到底怎么考？（中级）

**一句话结论**：面试不考你能不能背出 23 个模式的定义，而是考你能不能说清"项目里哪个变化点被隔离了、隔离的代价是什么、如果重来会不会这么设计"，回答框架是"场景—变化点—结构—代价"四步。

**先把话说白**：如果把设计模式当成一门需要背诵的课，那它几乎没有面试价值——网上随便搜一张 23 种模式的对照表就够了。它真正的价值在于：当需求变化时，你的代码需要改几个文件。面试官问模式，本质是在问"你的代码抗不抗变"。

**底层原理**：

1. **为什么面试官不直接问定义。** 定义是公共知识，问不出区分度。而"你项目里哪里用了策略模式"这个问题，能同时暴露三件事：你是不是真的写过（有没有具体类名和场景）、你理解不理解模式想解决的问题（说的是"消除 if-else"还是"隔离算法变化"）、你有没有判断力（知不知道自己用得对不对）。

2. **"场景—变化点—结构—代价"四步框架。** 第一步说场景，一句话交代业务背景，比如"支付渠道有微信、支付宝、银联，每家的签名和回调格式都不一样"。第二步点出变化点，"变化的是支付渠道，未来还会加"。第三步说结构，"所以抽了一个 `PayChannel` 接口，每个渠道一个实现，用工厂按 code 取"。第四步说代价，"代价是新增一个渠道要加一个类并注册，比加一个 case 麻烦，但渠道多了以后不会互相影响"。

3. **为什么第四步最关键。** 前三步任何人都能编，第四步"代价"编不出来。只有真正维护过自己设计的人，才知道多一层抽象意味着多一次跳转、多一个要读的文件、多一处可能忘记注册的地方。能主动说出代价，说明你不是在背模式，而是在做工程判断。

4. **常见的形式变形。** 面试官很少说"请讲讲策略模式"，更常见的问法是："你这个类有 800 行，怎么拆？""加一个新类型要改哪些地方？""这两个模块为什么耦合这么紧？""如果要支持多渠道，你会怎么设计？"这些问题背后都是同一件事：识别变化点并隔离它。

5. **边界：不要为了模式而模式。** 一个只有两种实现、且未来大概率不会增加的分支，用 if-else 就是最优解。模式的价值随"变化频率 × 变化种类"增长，当这两个因子都很小时，抽象是纯负债。

**面试追问**：
- 追问：你项目里哪个地方用了设计模式？→ 答题要点：按四步说，重点落在"变化点是什么"和"代价是什么"，不要只报模式名。
- 追问：如果不用这个模式会怎样？→ 答题要点：说具体后果，比如"每加一个渠道要改 5 处 if-else，容易漏改，测试要全回归"。
- 追问：这个设计有什么问题？→ 答题要点：主动指出一处不足，比如"工厂的注册是手写的，漏注册只有运行时才发现，应该改成启动时校验"。

### Q2. 六大设计原则怎么用一句话讲清？（中级）

**一句话结论**：单一职责、接口隔离、迪米特法则管"职责怎么切"，开闭、里氏替换、依赖倒置管"扩展怎么做"；六条的共同目标是把"变化"关进一个尽可能小的盒子里。

**先把话说白**：设计原则不是六条独立的口号，它们是从不同角度看同一件事。你把职责切干净了（SRP、ISP），依赖方向就自然清晰（DIP）；你依赖抽象而不是实现（DIP），扩展时就只需要加类而不改旧代码（OCP）；而替换子类不破坏语义（LSP），是"依赖抽象"能成立的前提。

**底层原理**：

1. **单一职责（SRP, Single Responsibility Principle）：一个类只对一个变化原因负责。** 反例是一个 `UserService` 同时做参数校验、数据库读写、发短信、导出报表。四个职责对应四个变化源：校验规则变了、表结构变了、短信服务商换了、报表格式改了，任何一处改动都要动这个类，且都要回归测试全部功能。

2. **开闭原则（OCP, Open-Closed Principle）：对扩展开放，对修改关闭。** 反例是 `if (type == 1) ... else if (type == 2) ...` 的支付分发，每加一种支付方式都要改这个已经测试过的类。注意 OCP 不是"永远不改代码"，而是"把预期的变化点做成扩展点，让新增走扩展而不是改旧逻辑"——没人能预测所有变化，所以 OCP 只对**已经识别出的变化维度**成立。

3. **里氏替换（LSP, Liskov Substitution Principle）：子类必须能在不破坏语义的前提下替换父类。** 经典反例是 `Square extends Rectangle`：父类有 `setWidth` 和 `setHeight` 两个独立方法，正方形必须让两者联动，于是"设置宽之后高不变"这个父类隐含的契约被破坏，任何按 Rectangle 写的代码传进 Square 都会算错面积。LSP 的本质是**行为契约**，不是类型兼容。

4. **依赖倒置（DIP, Dependency Inversion Principle）：高层模块不依赖低层实现，两者都依赖抽象。** 反例是 `OrderService` 里直接 `new MySQLOrderRepository()`，业务逻辑被绑死在 MySQL 上，单元测试必须连数据库。改成注入 `OrderRepository` 接口后，测试可以传内存实现，换存储只改装配处。

5. **接口隔离（ISP, Interface Segregation Principle）：客户端不应被迫依赖它不用的方法。** 反例是一个 20 个方法的 `UserService` 接口，只做查询的实现类也得写 15 个空方法或抛 `UnsupportedOperationException`。拆成 `UserQueryService` 与 `UserCommandService` 后，每个实现只依赖自己需要的部分。

6. **迪米特法则（LoD, Law of Demeter）：只和直接朋友说话，不要 `a.getB().getC().getD().doSomething()`。** 反例是这种链式调用，一旦 `C` 的结构变了，所有写这行代码的地方都要改，而且调用方知道了太多本不该知道的内部结构。正确做法是在 `A` 上暴露一个 `a.doSomething()`，把导航逻辑收进对象内部。

**易混对比**：

| 原则 | 一句话 | 反例 | 修正方向 |
| --- | --- | --- | --- |
| 单一职责 | 一个类只有一个变化原因 | `UserService` 兼做校验、持久化、发短信 | 按变化源拆成三个类 |
| 开闭 | 新增走扩展，不改旧代码 | 加支付方式要改 `if-else` | 抽策略接口 + 注册表 |
| 里氏替换 | 子类不破坏父类契约 | `Square extends Rectangle` | 不建立继承关系，各自实现形状接口 |
| 依赖倒置 | 依赖接口不依赖实现 | `new MySQLRepo()` 写死在业务类 | 构造器注入接口 |
| 接口隔离 | 不强迫实现无用方法 | 20 方法的巨型接口 | 按客户端拆小接口 |
| 迪米特 | 只和直接朋友通信 | `a.getB().getC().doX()` | 在 `A` 上封装行为 |

**面试追问**：
- 追问：开闭原则是不是意味着永远不改老代码？→ 答题要点：不是，只对已识别的变化维度成立；预测不到的变化该改还得改，重构是正常的。
- 追问：里氏替换和"子类不能缩小访问权限"是一回事吗？→ 答题要点：后者是编译器层面的规则，LSP 更宽，还包括前置条件不能加强、后置条件不能减弱、异常不能变宽。
- 追问：迪米特法则会不会导致到处写包装方法？→ 答题要点：会，所以它只适用于"内部结构容易变"的场景，数据载体（DTO）暴露 getter 是合理的。

### Q3. 单例有哪几种写法，各自代价是什么？（初级）

**一句话结论**：饿汉式靠类初始化保证线程安全但不能懒加载；懒汉式加 `synchronized` 能懒加载但每次调用都加锁；DCL 用两次检查加 `volatile` 兼顾两者；静态内部类用 `<clinit>` 的线程安全实现无锁懒加载；枚举最简洁且天然防反射与反序列化。

**先把话说白**：单例要解决两件事：只创建一个实例，以及什么时候创建。这两个目标互相牵制——越晚创建越省资源，但越晚创建越要小心并发。五种写法本质上是在"创建时机"和"同步开销"之间做不同的取舍。

**底层原理**：

1. **饿汉式。** `private static final Singleton INSTANCE = new Singleton();`，实例在类初始化（`<clinit>`）时创建。JVM 保证 `<clinit>` 只执行一次且加锁，所以线程安全，且不需要任何同步开销。缺点是：不管用不用都会创建，如果构造过程要读配置、连数据库，会拖慢启动甚至在配置缺失时直接失败。

2. **懒汉式（方法加锁）。** `public static synchronized Singleton getInstance()`，第一次调用才创建。问题是每次 `getInstance` 都要拿锁，即使实例早已创建。JDK 6 之后的偏向锁、轻量级锁能缓解，但在高并发下仍是不必要的开销。

3. **DCL（Double-Checked Locking）。** 先无锁判断 `instance == null`，为空才进 `synchronized` 块，块内再判断一次。第一次检查过滤掉绝大多数调用，第二次检查防止两个线程先后进入同步块重复创建。必须配合 `volatile`，原因见 Q4。

4. **静态内部类（Holder）。** 外部类加载不会触发内部类初始化，只有首次调用 `getInstance()` 访问 `Holder.INSTANCE` 时才触发 `Holder` 的 `<clinit>`，由 JVM 保证线程安全。既懒加载又无锁，是利用"类初始化的锁"这一语言特性的巧妙用法。缺点是：无法传参（构造需要外部参数时不好用），且如果构造抛异常，会得到 `ExceptionInInitializerError`，之后该类永久不可用。

5. **枚举。** `enum Singleton { INSTANCE; }`，JVM 保证枚举常量在类初始化时创建且唯一，天然线程安全。防反射：`Constructor.newInstance` 检测到 `Modifier.ENUM` 直接抛 `IllegalArgumentException`；防反序列化：`ObjectInputStream` 对枚举走 `readEnum`，按名字返回同一个常量，不会新建对象。Effective Java 首推这种写法。代价是：不能继承其他类（枚举已隐式继承 `Enum`），不够"像普通类"，有些人会觉得语义别扭。

```java
// DCL：两次检查 + volatile
public class Singleton {
    private static volatile Singleton instance;   // volatile 不可省

    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {                   // 第一次检查，避免每次加锁
            synchronized (Singleton.class) {
                if (instance == null) {           // 第二次检查，防止重复创建
                    instance = new Singleton();   // 非原子：分配、初始化、赋值
                }
            }
        }
        return instance;
    }
}

// 静态内部类：懒加载 + 无锁
class HolderSingleton {
    private HolderSingleton() {}
    private static class Holder {
        static final HolderSingleton INSTANCE = new HolderSingleton();
    }
    public static HolderSingleton getInstance() { return Holder.INSTANCE; }
}
```

**易混对比**：

| 写法 | 懒加载 | 线程安全 | 同步开销 | 防反射 | 防反序列化 |
| --- | --- | --- | --- | --- | --- |
| 饿汉式 | 否 | 是（`<clinit>`） | 无 | 否 | 否 |
| 懒汉式（方法锁） | 是 | 是 | 每次调用加锁 | 否 | 否 |
| DCL + volatile | 是 | 是 | 仅首次加锁 | 否 | 否 |
| 静态内部类 | 是 | 是（`<clinit>`） | 无 | 否 | 否 |
| 枚举 | 否（类加载即创建） | 是 | 无 | 是 | 是 |

**面试追问**：
- 追问：静态内部类为什么能懒加载？→ 答题要点：外部类初始化不会递归初始化内部类，只有主动访问 `Holder.INSTANCE` 才触发它的 `<clinit>`。
- 追问：单例的构造器真能私有吗？→ 答题要点：反射 `setAccessible(true)` 可以调用，需要在构造器里加 `if (INSTANCE != null) throw new RuntimeException()` 兜底。
- 追问：Spring 的 Bean 单例和这个单例是一回事吗？→ 答题要点：不是，Spring 是"每个容器每个 bean name 一个实例"，容器可以有多个，JVM 里仍可能有多个实例。

### Q4. DCL 为什么必须加 volatile？（高级）

**一句话结论**：`new Singleton()` 不是原子操作，它分"分配内存、调用构造器初始化、把引用指向内存"三步，其中第 2 步和第 3 步可能被指令重排；没有 `volatile` 时另一个线程可能看到一个非 null 但字段还是默认值的"半初始化对象"。

**先把话说白**：对象创建像装修房子——先拿到钥匙（分配内存），再装修（执行构造器），最后挂上门牌（引用赋值）。如果工人先挂门牌再装修，路人按门牌找过去，看到的就是一间空房子。`volatile` 的作用是禁止"挂门牌"和"装修"调换顺序。

**底层原理**：

1. **字节码层面的三步。** `new` 指令分配内存并把字段置零值；`invokespecial <init>` 执行构造器；`astore` 把引用写入变量。JIT 编译后，后两步在没有数据依赖时可以重排，因为单线程看结果一样——这是合法的编译优化。

2. **半初始化对象怎么被看见。** 线程 A 执行到"引用赋值"但构造器还没跑完，此时 `instance != null` 已成立。线程 B 进入 `getInstance`，第一次检查发现不为 null，直接返回这个对象。B 拿到的是一个字段全是 0/null 的对象，用的时候就是 NPE 或业务数据错误。这类 bug 极难复现，因为它依赖具体的 CPU 乱序和缓存时序。

3. **volatile 提供的两重语义。** 一是可见性：写 `instance` 后立刻刷到主存，读时从主存读；二是禁止重排：在 volatile 写之前的操作不能被重排到写之后（这是 JSR-133 的 happens-before 规则）。有了第二重，"构造器执行完"一定发生在"引用可见"之前，B 要么看到 null，要么看到完整对象。

4. **为什么第一次检查可以不加锁。** DCL 的性能收益来自"绝大多数调用走无锁路径"。第一次检查读到非 null 时，因为 `volatile` 的可见性保证，此时对象一定已经初始化完成，直接返回是安全的。这正是"为什么必须 volatile"和"为什么 DCL 能快"是同一个答案。

5. **反射与序列化的破坏方式。** 反射：`getDeclaredConstructor().setAccessible(true).newInstance()` 绕过私有构造器，得到第二个实例。防护是在构造器里判断已有实例则抛异常（枚举除外，JVM 层直接拒绝）。序列化：`readObject` 会新建对象而不是返回原实例。防护是实现 `readResolve()` 返回 `INSTANCE`，或直接用枚举（`ObjectInputStream` 对枚举有特殊处理，按名字返回同一常量）。

**易混对比**：

| 破坏方式 | 原理 | 防护手段 | 枚举是否免疫 |
| --- | --- | --- | --- |
| 反射 | `setAccessible` 后调私有构造器 | 构造器内判断实例已存在则抛异常 | 是，JVM 直接拒绝 |
| 反序列化 | `readObject` 反序列化出新对象 | 实现 `readResolve` 返回单例 | 是，按名字返回常量 |
| 克隆 | `clone` 复制出新对象 | 不实现 `Cloneable` 或重写 `clone` 抛异常 | 是 |
| 多类加载器 | 不同 ClassLoader 各加载一份类 | 用同一加载器或注册为系统类 | 是（同一加载器内） |

**面试追问**：
- 追问：不加 volatile 一定会出问题吗？→ 答题要点：不一定，取决于 CPU 架构与 JIT 是否真的重排；x86 的 TSO 模型下 store-store 不重排，但 JIT 编译仍可能重排，属于"可能出错"而非"必然出错"。
- 追问：volatile 能保证原子性吗？→ 答题要点：不能，只保证可见性与有序性；`i++` 这种复合操作仍然不安全，需要 `AtomicInteger` 或加锁。
- 追问：枚举为什么防得住反射？→ 答题要点：`Constructor.newInstance` 里有 `if ((clazz.getModifiers() & Modifier.ENUM) != 0) throw new IllegalArgumentException(...)`。

### Q5. 简单工厂、工厂方法、抽象工厂怎么分？Spring 的 BeanFactory 是哪一类？（中级）

**一句话结论**：简单工厂用一个工厂类按参数造多种产品，违反开闭；工厂方法让每个产品配一个工厂，新增产品只加类；抽象工厂让一个工厂造一"族"相关产品，适合产品族稳定但产品等级会扩展的场景。

**先把话说白**：三者的区别可以用"谁决定造什么"来记。简单工厂是"一个总承包商，你说要什么他造什么"，加新产品就得改他的清单；工厂方法是"每种产品一个专门车间"，加产品就新开一个车间，不用动老车间；抽象工厂是"一整套生产线"，比如"高端家具厂"能一次产出沙发、茶几、椅子，换风格就整条线换掉。

**底层原理**：

1. **简单工厂（不算 GoF 23 种之一）。** 一个 `PayFactory.create(String type)`，内部 switch 决定 new 哪个实现。优点是调用方简单，只依赖一个入口；缺点是每加一种产品都要改这个工厂类，违反 OCP，且工厂会随着产品增多变成一个巨大的 switch。

2. **工厂方法。** 定义 `PayChannelFactory { PayChannel create(); }`，每个产品一个具体工厂。新增产品时加"产品类 + 工厂类"两个类，不改任何已有代码，符合 OCP。代价是类数量翻倍，产品多时会出现大量只 new 一次的小工厂类。

3. **抽象工厂。** 一个工厂接口定义一族产品的创建方法，比如 `DbFactory { Connection createConn(); Command createCmd(); }`，`MySQLFactory` 与 `OracleFactory` 分别实现整族。它解决的是"产品族"问题：同一族的产品必须配套使用（MySQL 的连接不能配 Oracle 的命令）。新增一个产品族（加 PostgreSQL）容易，新增一个产品等级（给所有工厂加 `createTx()`）要改所有工厂，这违反了 OCP——这正是抽象工厂的边界。

4. **Spring 的 BeanFactory 属于哪类。** 严格说它不是教科书上的任何一种，而是"工厂方法 + 注册表 + 单例缓存"的复合体：`getBean(name)` 根据 `BeanDefinition` 决定用反射、`FactoryBean.getObject()` 还是 `Supplier` 创建，产品类型在运行时才知道，不受编译期接口约束。如果一定要归类，它更接近"参数化的通用工厂"，而不是经典工厂方法。

5. **FactoryBean 才是标准的工厂方法。** `FactoryBean<T>` 只暴露 `T getObject()`，一个实现类对应一种产品，Spring 通过 `&beanName` 拿到工厂本身、通过 `beanName` 拿到产品。MyBatis 的 `MapperFactoryBean`、Spring 的 `ProxyFactoryBean` 都是这个套路：产品是动态生成的代理对象，无法用 `new` 直接创建。

**易混对比**：

| 维度 | 简单工厂 | 工厂方法 | 抽象工厂 |
| --- | --- | --- | --- |
| 产品维度 | 一个等级 | 一个等级 | 多个等级（一族） |
| 工厂数量 | 1 个 | 每个产品 1 个 | 每个产品族 1 个 |
| 新增产品 | 改工厂（违反 OCP） | 加两个类 | 改所有工厂（违反 OCP） |
| 新增产品族 | 改工厂 | 不适用 | 加一个工厂类 |
| 典型例子 | `Calendar.getInstance()` | `FactoryBean` | `DbFactory` 整族 |

**面试追问**：
- 追问：Spring 的 `BeanFactory` 和 `FactoryBean` 有什么区别？→ 答题要点：前者是容器本身，负责管理所有 bean；后者是一个特殊的 bean，用来生产另一个 bean。
- 追问：抽象工厂和工厂方法能一起用吗？→ 答题要点：能，抽象工厂的具体工厂内部通常用工厂方法创建各个产品，Spring 就是这种组合。
- 追问：为什么简单工厂违反 OCP 还这么常用？→ 答题要点：产品种类少且稳定时，一个 switch 的可读性远好于十个类，OCP 的收益抵不过复杂度。

### Q6. 建造者模式解决什么问题？`@Builder` 有什么坑？（中级）

**一句话结论**：建造者把"对象的构造过程"从"构造器参数列表"里拆出来，用链式调用逐步设置可选参数，解决多参数构造器可读性差、参数顺序易错的问题；Lombok 的 `@Builder` 不会继承字段声明处的默认值，需要显式加 `@Builder.Default`。

**先把话说白**：一个类有 10 个字段，其中 3 个必填、7 个可选，构造器会变成什么样？要么写一堆重载，要么全参构造然后传一堆 null。建造者的做法是：先 `new Builder()`，需要哪个字段就 `.xxx()` 一下，最后 `build()` 一次性造出对象。

**底层原理**：

1. **结构。** 产品类（`Computer`）+ 建造者（`ComputerBuilder`），建造者持有所有字段，每个 setter 返回 `this` 实现链式调用，`build()` 里调产品类的构造器并做校验。可选加一个 `Director` 来封装固定的组装流程（比如"游戏本配置""办公本配置"），但在业务代码里通常省略，直接链式调用。

2. **与重叠构造器、JavaBean 的对比。** 重叠构造器（ telescoping constructor）在参数多时无法阅读，`new Person("a", 1, null, null, true)` 完全看不出含义；JavaBean 的 setter 方式可读，但对象在构造过程中处于"不一致状态"，且无法做成不可变对象。建造者兼顾可读性与不可变性：`build()` 返回的对象可以是 `final` 字段、没有 setter。

3. **`@Builder` 做了什么。** Lombok 在编译期生成一个静态内部类 `XxxBuilder`，字段与外部类一一对应，`build()` 里 `new Xxx(a, b, c)` 调全参构造器。注意它是**全量赋值**：builder 里没设置的字段是 `null`/`0`/`false`，`build()` 会把这些默认值一起传进去。

4. **默认值丢失的坑。** 如果类里写了 `private int retry = 3;`，用 `Xxx.builder().build()` 得到的对象 `retry` 是 0，不是 3——因为 builder 的字段初始值是 0，`build()` 显式传了 0，覆盖了字段声明处的赋值。必须改成 `@Builder.Default private int retry = 3;`，Lombok 才会在 builder 里初始化这个值，并在 `build()` 时用 `$default$retry` 兜底。

5. **其他坑。** `@Builder` 会吃掉无参构造器（生成了全参构造后，默认无参构造不再自动生成），需要同时加 `@NoArgsConstructor` + `@AllArgsConstructor`；继承场景下父类字段不会自动进子类 builder，需要 `@SuperBuilder`；`@Builder` 生成的类没有 setter，若同时需要 JSON 反序列化，得配 `@Jacksonized` 或保留 setter。

```java
@Builder
@AllArgsConstructor
public class HttpConfig {
    private final String url;
    @Builder.Default                 // 不加这行，build() 后 timeout 是 0
    private final int timeout = 3000;
    @Builder.Default
    private final int retry = 3;
}

// 使用：可选参数清晰，未设置的走默认值
HttpConfig cfg = HttpConfig.builder()
        .url("https://api.example.com")
        .retry(5)
        .build();
```

**易混对比**：

| 方式 | 可读性 | 能否不可变 | 参数校验 | 典型问题 |
| --- | --- | --- | --- | --- |
| 重叠构造器 | 差，参数多时无法阅读 | 可以 | 构造器内 | 参数顺序易错 |
| JavaBean setter | 好 | 不可以 | 需额外 `validate()` | 构造中出现半成品对象 |
| 建造者 | 好 | 可以 | `build()` 内 | 类数量增加 |
| 静态工厂 + 命名参数 | 中 | 可以 | 工厂内 | Java 无命名参数，需大量重载 |

**面试追问**：
- 追问：建造者和工厂的区别是什么？→ 答题要点：工厂关注"造哪一种"，一步产出；建造者关注"怎么一步步造"，分步装配并可复用构建过程。
- 追问：`@Builder` 为什么会导致默认值失效？→ 答题要点：builder 字段初始为 0/null，`build()` 全量传参覆盖了字段声明处的初始化。
- 追问：建造者一定要有 `Director` 吗？→ 答题要点：不必，GoF 引入 `Director` 是为了复用固定组装流程，业务中链式调用更常见。

### Q7. 代理、装饰、适配器的边界在哪？（中级）

**一句话结论**：三者结构上都叫"包装"，但意图完全不同：代理是"控制对这个对象的访问"（接口不变，通常一个被包对象），装饰是"给这个对象动态加职责"（接口不变，可多层嵌套），适配器是"把不兼容的接口转成需要的接口"（接口改变）。

**先把话说白**：三个模式长得很像，都是"一个类持有另一个类并实现同样的方法"。区分它们只需要问一句：**包装前后，接口变了吗？包装的目的是什么？** 接口没变、目的是拦一道 → 代理；接口没变、目的是加功能、而且能一层层套 → 装饰；接口变了、目的是让旧的能用在新地方 → 适配器。

**底层原理**：

1. **代理的意图是"控制"。** 客户端本来能直接访问目标对象，但出于某些原因（权限、延迟加载、远程调用、事务、日志）需要中间隔一层。代理类实现与目标相同的接口，在调用前后插入逻辑，然后转调目标。客户端通常**不知道自己拿的是代理**。典型：Spring AOP 的事务代理、MyBatis 的 Mapper 代理、Hibernate 的懒加载代理、RPC 的桩对象。

2. **装饰的意图是"增强"，且强调组合优于继承。** 装饰器实现与被装饰者相同的接口，持有一个同类型引用，在转调前后追加行为。关键在于它可以**多层嵌套**：`new BufferedInputStream(new FileInputStream(f))`，每层只加一个职责（缓冲、解压、校验），运行时自由组合。如果用继承实现同样的组合，2 个维度就要 4 个子类，3 个维度要 8 个，类爆炸。

3. **适配器的意图是"转换"。** 目标接口 `Target` 与现有实现 `Adaptee` 不兼容，适配器实现 `Target` 并在内部调用 `Adaptee` 的方法，做参数与语义的映射。典型：`InputStreamReader` 把字节流转成字符流、`Arrays.asList` 把数组适配成 List、SLF4J 的绑定层适配不同日志实现、Spring MVC 的 `HandlerAdapter` 把各种 Controller 适配成统一的 `handle` 调用。

4. **为什么这三者最容易混。** 因为它们的类图几乎一样：都是"实现接口 + 持有引用 + 转发调用"。静态代理和装饰器在代码层面**完全无法区分**，只能从意图和行为判断：装饰器通常接受同类型的另一个实例作为构造参数（可嵌套），代理通常在内部自己创建或注入一个具体目标（不可嵌套）。

5. **一个实用的判别顺序。** 先看接口：变了 → 适配器；没变 → 再看能否嵌套、是否在运行时叠加职责：能 → 装饰器；不能，且主要做访问控制或横切增强 → 代理。如果还分不清，就问"如果去掉这一层，功能会不会缺失"——代理去掉后功能仍在（只是少了控制），装饰去掉后功能就缺了。

**易混对比**：

| 维度 | 代理 Proxy | 装饰 Decorator | 适配器 Adapter |
| --- | --- | --- | --- |
| 接口 | 与被代理对象相同 | 与被装饰对象相同 | 与目标接口相同，与被适配者不同 |
| 目的 | 控制访问、加横切逻辑 | 动态增加职责 | 转换接口，让不兼容者协作 |
| 对象数量 | 通常 1 个，且客户端不感知 | 可多层嵌套，层层叠加 | 1 个被适配者 |
| 创建时机 | 常由框架动态生成 | 调用方手工组合 | 调用方手工组合 |
| 客户端感知 | 不感知 | 感知（要选择装饰器） | 感知（拿到的是新接口） |
| 典型例子 | Spring AOP、MyBatis Mapper | `BufferedInputStream` | `InputStreamReader`、`HandlerAdapter` |
| 去掉后 | 功能还在，少了控制 | 功能缺失 | 无法协作 |

**面试追问**：
- 追问：静态代理和装饰器代码一样，怎么区分？→ 答题要点：看意图和构造参数，装饰器接收同类型实例可嵌套，代理注入具体目标且客户端不感知。
- 追问：为什么 Java IO 要用装饰器而不是继承？→ 答题要点：维度组合会爆炸，3 个维度 8 个子类，装饰器只需 3 个类自由组合。
- 追问：`HandlerAdapter` 为什么算适配器而不是策略？→ 答题要点：它把不同形态的 Handler 统一成 `handle()` 调用，重点是"接口转换"；策略是"同一接口多种算法可替换"。

### Q8. Spring AOP 为什么有时用 JDK 代理有时用 CGLIB？（中级）

**一句话结论**：JDK 动态代理只能代理接口，通过 `Proxy.newProxyInstance` 生成实现同接口的类；CGLIB 通过生成子类代理普通类，无法处理 `final` 类与 `final` 方法。Spring 的传统策略是"有接口用 JDK、无接口用 CGLIB"，Spring Boot 2.x 起默认 `proxyTargetClass=true`，统一用 CGLIB。

**先把话说白**：JDK 代理是"找个替身演员，但只能演这个演员签了合同的角色（接口）"；CGLIB 是"直接生一个儿子，让儿子继承父亲的活儿"。替身只能按接口演，儿子不能继承被 `final` 封死的家业。

**底层原理**：

1. **JDK 代理的生成过程。** `Proxy.newProxyInstance(classLoader, interfaces, handler)` 在运行时生成 `$Proxy0` 类，它实现传入的所有接口，每个方法体都是 `handler.invoke(this, method, args)`。所以它拿不到目标类的非接口方法，也无法代理没有接口的类。生成类会按接口组合缓存，重复创建同一组接口的代理不会重复生成字节码。

2. **CGLIB 的生成过程。** 用 ASM 生成目标类的子类，重写所有非 `final`、非 `private` 的方法，方法内回调 `MethodInterceptor.intercept()`，再由 `MethodProxy.invokeSuper()` 调用父类实现。因为是继承，所以 `final` 类无法代理、`final` 方法无法增强、`private` 方法不可见；同时构造器会被调用两次（一次是 CGLIB 创建代理实例时），如果构造器里有副作用要注意。

3. **Spring 的选择逻辑。** `DefaultAopProxyFactory` 判断：目标类实现了至少一个接口，且 `proxyTargetClass` 为 false → JDK 代理；否则 CGLIB。Spring Boot 2.x 把 `spring.aop.proxy-target-class` 默认设为 true，原因是：CGLIB 可以避免"注入接口却拿到代理、按实现类注入却报错"的类型不匹配问题（JDK 代理生成的是接口的实现，不是目标类的子类，`@Autowired` 按具体类注入会失败）。

4. **性能的真相。** 早期 CGLIB 创建慢、调用快，JDK 代理创建快、调用慢（走反射）。现代 JDK 上这个差距已经很小，Spring 官方也明确表示性能不应是选型的主要依据——**类型兼容性**才是。

5. **两者的共同限制。** 都只能拦截 `public` 方法（Spring AOP 的语义）；同类内部方法调用（`this.method()`）不经过代理，`@Transactional` 会失效；`final` 方法无法增强。这些限制的根源是"代理对象在调用方和目标之间"，一旦调用不经过代理，增强就无从谈起。

**易混对比**：

| 维度 | JDK 动态代理 | CGLIB |
| --- | --- | --- |
| 前提 | 目标类实现接口 | 目标类非 `final` |
| 原理 | 生成实现同接口的类 | 生成目标类的子类 |
| 可代理方法 | 仅接口方法 | 非 `final` 的 public/protected |
| 注入具体类 | 失败（代理不是目标类的子类） | 正常 |
| 构造器调用 | 只调代理类构造器 | 目标类构造器会被调用 |
| Spring Boot 2.x 默认 | 否 | 是 |

**面试追问**：
- 追问：`@Transactional` 为什么在同类方法调用时失效？→ 答题要点：内部调用走 `this`，不经过代理对象，增强逻辑没机会执行；解决方式是自注入、`AopContext.currentProxy()` 或拆类。
- 追问：CGLIB 代理为什么不能代理 `final` 类？→ 答题要点：靠继承生成子类，`final` 类不可继承；`final` 方法不可重写，同理无法增强。
- 追问：JDK 17 之后 JDK 代理有什么变化？→ 答题要点：模块系统下对非 public 接口的代理受限，动态生成类默认在 `jdk.proxy` 包里。

### Q9. 策略模式怎么真正消除 if-else？（中级）

**一句话结论**：策略模式把每个分支的算法抽成独立实现类，用"注册表 + 按 key 查表"替代条件判断；落地方式有三种——策略接口加工厂 Map、枚举绑定函数式接口、Spring 直接注入 `Map<String, Strategy>`，其中 Spring 注入的方式最省代码。

**先把话说白**：if-else 的问题不是"难看"，而是"每加一个分支都要改这个已经测试过的方法，且所有分支的依赖都堆在一个类里"。策略模式做的事，是把"选择哪个分支"和"分支怎么执行"分开：选择逻辑收敛到一次查表，执行逻辑分散到各自的类。

**底层原理**：

1. **为什么简单抽接口还不够。** 很多人抽了 `PayStrategy` 接口、写了三个实现，然后在 `PayService` 里仍然写 `if (type.equals("wx")) new WxPay() ...`。这只是把代码搬了个家，判断还在，新增渠道照样要改这里。真正消除 if-else 的关键是**把"type → 实现"的映射变成数据**，让新增实现只影响注册处。

2. **方式一：策略接口 + 工厂 Map。** 定义 `Map<String, PayStrategy>`，在工厂的静态块或构造器中 `register("wx", new WxPayStrategy())`，调用方 `map.get(type).pay(order)`。新增渠道只需新增一个类并加一行注册，`PayService` 完全不动。缺点是注册是手写的，漏注册只有运行时才发现，可以在启动时校验"枚举值是否都有对应实现"。

3. **方式二：枚举 + 函数式接口。** `enum PayType { WX(WxPay::new), ALI(AliPay::new); private final Supplier<PayStrategy> factory; }`，或者更直接地让枚举常量持有一个 `BiFunction<Order, BigDecimal, Boolean>`。优点是类型安全、枚举值即注册表、不可能漏；缺点是每个分支的逻辑只能写成 lambda，复杂逻辑还是要落到独立类。

4. **方式三：Spring 注入 `Map<String, Strategy>`。** 给每个实现类加 `@Component("wx")`，然后 `@Autowired Map<String, PayStrategy> strategies`，Spring 会把 bean name 作为 key 全部注入。这是最省代码的方式，新增渠道只需加一个带 `@Component` 的类，零改动。要注意：拿不到 key 时要处理 `null`，且 bean name 与业务 code 的映射最好用一个常量类约束，避免拼错。

5. **还有第四种：List 注入 + 自选择。** 注入 `List<Strategy>`，每个策略实现 `supports(type)` 方法，调用方遍历找到第一个支持的就执行。这种方式更接近责任链，好处是支持"一个请求匹配多个策略"或"按优先级选择"，代价是每次都要遍历，且顺序依赖 `@Order`。

```java
// 方式三：Spring 注入 Map，key 为 bean 名称
public interface PayStrategy {
    void pay(Order order);
}

@Component("wx")
class WxPayStrategy implements PayStrategy {
    public void pay(Order o) { /* 微信支付 */ }
}

@Component("ali")
class AliPayStrategy implements PayStrategy {
    public void pay(Order o) { /* 支付宝 */ }
}

@Service
public class PayService {
    private final Map<String, PayStrategy> strategies;   // Spring 自动注入所有实现

    public PayService(Map<String, PayStrategy> strategies) {
        this.strategies = strategies;
    }

    public void pay(String channel, Order order) {
        PayStrategy s = strategies.get(channel);
        if (s == null) throw new IllegalArgumentException("不支持的渠道: " + channel);
        s.pay(order);                                     // 没有 if-else
    }
}
```

**易混对比**：

| 落地方式 | 新增实现要改哪里 | 类型安全 | 适用场景 |
| --- | --- | --- | --- |
| 接口 + 手工 Map | 加类 + 加一行注册 | 编译期弱，运行时查 | 无 Spring 环境、实现少 |
| 枚举 + 函数式 | 加枚举常量 | 强，漏写编译报错 | 分支逻辑短、参数固定 |
| Spring 注入 Map | 只加一个 `@Component` 类 | 弱，key 拼错运行时才发现 | Spring 项目首选 |
| List + `supports()` | 只加一个类 | 中，需遍历匹配 | 一请求可匹配多策略、需优先级 |

**面试追问**：
- 追问：策略模式和状态模式有什么区别？→ 答题要点：策略由客户端选，策略之间互不知道；状态由对象内部流转，状态自己决定下一个状态。
- 追问：策略太多导致类爆炸怎么办？→ 答题要点：逻辑简单时用枚举 + 函数式合并，逻辑复杂时按领域再分组，不要为了"一个类一个策略"硬拆。
- 追问：怎么保证新增枚举值时有对应实现？→ 答题要点：启动时校验枚举值与 Map 的 key 集合一致，缺失就 fail-fast。

### Q10. 模板方法在框架里怎么体现？（中级）

**一句话结论**：模板方法在父类里定义算法骨架（步骤顺序、公共逻辑、异常处理），把可变步骤留给子类实现；AQS 的 `acquire`/`release`、`JdbcTemplate` 的 `execute`、`HttpServlet` 的 `service` 都是这个结构。

**先把话说白**：模板方法就是"填空题"。出题人（父类）把题面和步骤写死——第一步干什么、第二步干什么、什么情况下回滚——只在关键位置留空，让答题人（子类）填。这样所有人交上来的卷子结构一致，只有答案不同。

**底层原理**：

1. **AQS 的骨架。** `AbstractQueuedSynchronizer.acquire(int arg)` 定义了完整的获取锁流程：`tryAcquire` 尝试获取 → 失败则 `addWaiter` 入队 → `acquireQueued` 自旋并挂起 → 处理中断。其中 `tryAcquire`、`tryRelease`、`tryAcquireShared` 都是 `protected` 方法，默认抛 `UnsupportedOperationException`，由子类实现。`ReentrantLock` 的 `Sync`、`ReentrantReadWriteLock` 的读写锁都是这么做的。这就是为什么 AQS 被称为"并发包的骨架"——它把排队、唤醒、中断这些又难又通用的部分写死了。

2. **`JdbcTemplate` 的骨架。** `execute(ConnectionCallback)` 里依次做：从 DataSource 取连接、创建 Statement、执行、`SQLException` 转成 `DataAccessException`、`finally` 里释放资源。变化的 SQL 与结果映射通过回调接口传入，而不是靠继承。这其实是"模板方法 + 回调"的混合体：GoF 的模板方法靠继承覆写，Spring 更倾向用回调对象组合，避免继承带来的强耦合。

3. **`HttpServlet` 的骨架。** `service(req, resp)` 先判断请求方法，再分发到 `doGet`、`doPost`、`doPut` 等。默认实现返回 405，子类按需覆写。这保证了你只需要写业务逻辑，方法分发、`HEAD` 处理、`OPTIONS` 响应这些公共部分由父类统一完成。

4. **为什么框架偏爱模板方法。** 因为它能把"不可变的部分"锁在框架内，避免使用者写错顺序（比如忘了关连接、忘了释放锁）。代价是**继承耦合**：子类与父类的实现细节绑定，父类改骨架可能破坏所有子类，这也是"组合优于继承"要提醒的地方。Spring 后期大量改用回调/Template 类（`JdbcTemplate`、`RestTemplate`、`TransactionTemplate`）就是为了避开这个代价。

5. **钩子方法（Hook）的作用。** 除了抽象方法，模板里常留一些空实现的钩子，比如 `AbstractApplicationContext.refresh()` 里的 `onRefresh()`、`postProcessBeanFactory()`。子类可以选择性覆写，不覆写就用默认行为。钩子让模板的扩展点更丰富，同时不强制子类实现。

**易混对比**：

| 载体 | 骨架方法 | 变化点 | 扩展方式 |
| --- | --- | --- | --- |
| AQS | `acquire` / `release` | `tryAcquire` / `tryRelease` | 继承并实现 |
| `JdbcTemplate` | `execute` | `ConnectionCallback` / `RowMapper` | 传回调对象 |
| `HttpServlet` | `service` | `doGet` / `doPost` | 继承并覆写 |
| `AbstractApplicationContext` | `refresh` | `onRefresh` / `postProcessBeanFactory` | 继承并覆写钩子 |

**面试追问**：
- 追问：模板方法和策略模式都能消除 if-else，怎么选？→ 答题要点：模板方法靠继承、编译期绑定，适合步骤固定顺序；策略靠组合、运行期替换，适合算法整体可换。
- 追问：模板方法的缺点是什么？→ 答题要点：继承耦合、父类改动影响所有子类、受单继承限制；可用回调或函数式接口替代。
- 追问：`JdbcTemplate` 算模板方法还是回调？→ 答题要点：骨架是模板方法，变化点用回调实现，属于两者的结合，Spring 有意用组合替代继承。

### Q11. 责任链在 Filter、Interceptor、Netty 中有何不同？（中级）

**一句话结论**：三者都是责任链，但传递方式、能否中断、传递方向不同：Servlet Filter 通过 `chain.doFilter` 显式向下传递且可中断，Spring Interceptor 通过返回值 `false` 中断且分前后两个回调点，Netty Pipeline 是双向链表、Inbound 与 Outbound 分别传播且可动态增删。

**先把话说白**：责任链就是"一件事经过一串处理者，每个决定是继续往下传还是就地返回"。审批流是最直观的例子：组长批完给经理，经理批完给总监，任何一级驳回就结束。技术里的 Filter、Interceptor、Pipeline 都是这个结构，区别在于"往下传的动作由谁做"和"能不能中途掉头"。

**底层原理**：

1. **Servlet Filter 的链式调用。** 容器维护一个 `FilterChain`，`chain.doFilter(req, resp)` 会调用下一个 Filter 或最终的 Servlet。所以"传递"是**显式**的：你不调 `doFilter`，链就断了，请求直接返回。这让 Filter 可以在前后都加逻辑（`doFilter` 前做鉴权，后做响应包装），也能通过不调用 `doFilter` 直接中断。

2. **Spring MVC Interceptor 的三段式。** `preHandle` 返回 `false` 表示中断，后续的拦截器和 Controller 都不执行；返回 `true` 继续。Controller 执行完后回调 `postHandle`（视图渲染前），最后 `afterCompletion`（请求完成后，无论是否异常）。所以它天然有"环绕"能力，且 `afterCompletion` 适合做资源清理。

3. **Netty 的双向 Pipeline。** `ChannelPipeline` 是一个 `ChannelHandler` 的双向链表，Inbound 事件（读）从 `head` 到 `tail` 传播，Outbound 事件（写）从 `tail` 到 `head` 反向传播。传递靠 `ctx.fireChannelRead(msg)` 或 `ctx.write(msg)`。Handler 可以在运行时动态增删（`pipeline.addLast`），这对协议升级、动态加解密很关键。`ByteToMessageDecoder` 这类入站处理器会在解码后调用 `fireChannelRead` 把对象传给下一个。

4. **为什么 Netty 要设计成双向。** 因为网络处理本身就是双向的：入站要解码、限流、心跳检测，出站要编码、压缩、写回。用一条双向链表把"读路径"和"写路径"都表达出来，比 Filter 的单向链更贴合 IO 场景。代价是顺序容易搞混——`addLast` 一个 Outbound Handler，它的执行顺序其实是"从后往前"。

5. **共同的设计取舍。** 责任链把"处理逻辑"与"调用顺序"解耦，新增一个处理者只需插入链中，不必修改其他处理者。代价是：链路长了难调试（不知道哪个环节改了请求）、顺序敏感（鉴权必须在业务之前）、异常传播规则复杂（谁负责捕获、谁负责回滚）。

**易混对比**：

| 维度 | Servlet Filter | Spring Interceptor | Netty Pipeline |
| --- | --- | --- | --- |
| 传递方式 | 显式 `chain.doFilter` | 返回值 `true` 继续 | `ctx.fireXxx` / `ctx.write` |
| 中断方式 | 不调 `doFilter` | `preHandle` 返回 `false` | 不调 `fireXxx` |
| 方向 | 单向 | 单向（三段回调） | 双向（Inbound / Outbound） |
| 作用对象 | `ServletRequest` | `HandlerMethod` | `Channel` 与消息 |
| 动态增删 | 不支持（启动时固定） | 不支持 | 支持 |
| 典型用途 | 编码、鉴权、日志、跨域 | 登录校验、权限、日志 | 编解码、心跳、背压 |

**面试追问**：
- 追问：Filter 和 Interceptor 谁先执行？→ 答题要点：Filter 在 Servlet 层面，先于 DispatcherServlet；Interceptor 在 Spring MVC 内部，晚于 Filter。
- 追问：责任链和装饰器有什么区别？→ 答题要点：装饰器每层都包裹同一个对象、必定调用内层；责任链每个处理者独立、可以选择不传递。
- 追问：链路太长怎么排查？→ 答题要点：给每个处理者打 traceId 与耗时，或用 SkyWalking 这类链路追踪，定位到具体环节。

### Q12. 观察者模式与 Spring Event 是什么关系？（中级）

**一句话结论**：Spring 的 `ApplicationEvent` 机制就是观察者模式的生产级实现，`publishEvent` 通知所有监听者，默认同步执行；JDK 自带的 `Observer`/`Observable` 因 `Observable` 是类、无法泛型、顺序无保证等设计缺陷，在 JDK 9 被标记 `@Deprecated`。

**先把话说白**：观察者的本质是"我不认识你，但你有事要告诉我"。订单服务不需要知道有哪些下游关心"订单创建"这件事，它只管发一条事件，积分、短信、报表各自订阅。新增一个下游，订单服务一行代码都不用改。

**底层原理**：

1. **观察者的两个角色。** 主题（Subject）维护一个观察者列表，提供 `register`/`unregister`/`notify`；观察者（Observer）实现 `update` 方法。主题状态变化时遍历列表逐个通知。核心价值是**解耦**：主题只依赖 `Observer` 接口，不依赖任何具体观察者。

2. **Spring Event 的实现。** `ApplicationEventPublisher.publishEvent(event)` 会把事件交给 `ApplicationEventMulticaster`（默认 `SimpleApplicationEventMulticaster`），它遍历所有匹配的 `ApplicationListener` 并调用 `onApplicationEvent`。监听器注册有两条路：实现 `ApplicationListener<T>` 接口，或用 `@EventListener` 注解（Spring 4.2 起支持，且事件类不必继承 `ApplicationEvent`）。

3. **默认同步执行的含义。** 默认的 multicaster 没有配 `TaskExecutor`，所以 `publishEvent` 会在**当前线程**依次调用所有监听器。这意味着：任何一个监听器抛异常，都会中断后续监听器并向上传播到发布方；任何一个监听器慢，都会拖慢发布方。要异步必须显式配置 `applicationEventMulticaster` 的 `taskExecutor`，或在监听方法上加 `@Async`（需 `@EnableAsync`）。

4. **为什么 JDK 的 Observer 被废弃。** 三个硬伤：`Observable` 是**类**不是接口，使用者必须继承它，而 Java 单继承，业务类往往已经有父类；`notifyObservers` 是 `protected`，外部无法直接调用，必须写子类暴露；没有泛型，`update(Observable o, Object arg)` 全靠强转，且通知顺序依赖 `Vector` 的遍历顺序、不可控。JDK 9 将其标记为 `@Deprecated`，官方建议用 `java.beans.PropertyChangeSupport` 或 `java.util.concurrent.Flow`。

5. **工程上的坑。** 事件滥用会让调用链变得不可追踪（A 发事件，B 监听又发事件，C 再监听……）；同步事件里做重活会拖垮主流程；事务未提交时发事件，监听器可能读不到数据（应该用 `@TransactionalEventListener(phase = AFTER_COMMIT)`）。这几点是"用了事件"和"用对了事件"的分界线。

**易混对比**：

| 维度 | JDK `Observer` | Spring `@EventListener` | 消息队列（MQ） |
| --- | --- | --- | --- |
| 范围 | 单 JVM | 单容器（单 JVM） | 跨服务 |
| 耦合 | 接口耦合 | 注解解耦，事件类可任意 | 完全解耦，靠 broker |
| 可靠性 | 内存态，进程挂了就丢 | 同左，除非配事务监听 | 可持久化、可重试 |
| 同步性 | 同步 | 默认同步，可配异步 | 天然异步 |
| 现状 | JDK 9 废弃 | 推荐 | 分布式场景首选 |

**面试追问**：
- 追问：Spring 事件默认是同步还是异步？→ 答题要点：同步，在发布线程内依次调用；要异步需配置 `taskExecutor` 或加 `@Async`。
- 追问：监听器抛异常会影响主流程吗？→ 答题要点：同步模式下会向上传播，除非监听器自己 catch；异步模式下异常只进日志。
- 追问：事务提交前发事件有什么问题？→ 答题要点：监听器可能在另一个事务/线程里读不到未提交的数据，应该用 `@TransactionalEventListener` 在提交后触发。

### Q13. 原型模式与深拷贝是什么关系？（初级）

**一句话结论**：原型模式用"复制现有实例"代替"重新 new 并初始化"，`clone()` 是它的实现手段；但 `Object.clone()` 默认是浅拷贝，引用字段仍共享，要实现真正的原型隔离必须自己处理深拷贝。

**先把话说白**：如果一个对象的创建过程很贵——要查库、算配置、拼一大坨默认值——那不如把它当模板，需要时复印一份。复印的问题在于：复印件上的"地址"还是同一个地址，如果对象里有引用字段，两份会互相影响。

**底层原理**：

1. **原型模式的动机。** 适用于"初始化成本高"或"初始化依赖运行时状态"的场景：比如一个已经加载好规则的风控对象、一个解析完的配置树。复制比重新构造便宜，且不用知道构造细节。

2. **`clone` 的机制。** `Object.clone()` 是 native 方法，按内存块复制：基本类型字段直接复制值，引用字段只复制引用地址。所以默认就是浅拷贝。调用前类必须实现 `Cloneable`，否则抛 `CloneNotSupportedException`——`Cloneable` 只是个标记接口，本身没有 `clone` 方法，这是 Java 早期设计的遗留问题。

3. **浅拷贝带来的共享问题。** 原型里有一个 `List<String> tags`，克隆出来的对象和原型指向同一个 List。改其中一个，另一个跟着变。如果原型是"模板"，这会导致所有副本被污染。所以原型模式落地时必须回答一个问题：哪些字段需要隔离？

4. **深拷贝的三种做法。** 逐层 `clone`：可控但要为每个类实现，遇到循环引用会栈溢出；Java 序列化：整体复制对象图，能处理循环引用，但要求全部可序列化且性能差；JSON 序列化：最常用，但会丢泛型与多态信息、忽略 `transient`。选择依据是"对象图复杂度"和"性能要求"，第 1 章已展开，这里只强调它与原型模式的关系：**原型模式要求的是"独立副本"，而 `clone` 默认给的是"共享副本"**。

5. **Spring 的 prototype 不是原型模式。** `@Scope("prototype")` 表示每次 `getBean` 创建一个新实例，本质是"工厂每次 new"，不走 `clone`，也不复制已有状态。名字相同，机制不同，这是常见误解。

**易混对比**：

| 概念 | 机制 | 是否复制状态 | 典型用途 |
| --- | --- | --- | --- |
| 原型模式 | `clone` 复制现有实例 | 是（浅拷贝则部分共享） | 模板对象、昂贵初始化 |
| `new` 新建 | 调用构造器 | 否，从零初始化 | 普通对象 |
| Spring prototype | 每次 `getBean` 新建 | 否 | 有状态 bean |
| 对象池 | 借出与归还 | 保留状态需重置 | 连接、线程 |

**面试追问**：
- 追问：`clone` 为什么被批评？→ 答题要点：`Cloneable` 是空接口、`clone` 在 `Object` 上是 protected、强制抛受检异常、绕开构造器，语义不清晰。
- 追问：原型模式一定要用 `clone` 吗？→ 答题要点：不一定，拷贝构造器 `new Foo(other)` 更可控，Effective Java 也更推荐。
- 追问：深拷贝会复制 `String` 吗？→ 答题要点：不需要，`String` 不可变，共享引用完全安全。

### Q14. 门面、组合、享元三个模式怎么区分？（初级）

**一句话结论**：门面是"把复杂子系统包一个简单入口"，组合是"用树形结构统一对待单个对象和容器"，享元是"共享细粒度对象的内部状态以省内存"；三者解决的问题分别是"用起来麻烦""结构是树""对象太多"。

**先把话说白**：门面像医院的导诊台，你不需要知道挂号、缴费、取药分别在哪，问导诊台就行；组合像文件夹，文件夹里可以放文件也可以放文件夹，你对两者做"打开"操作的方式一样；享元像共享单车，车是共用的，但"你骑到哪"这个状态是你自己的。

**底层原理**：

1. **门面（Facade）。** 把多个子系统的调用编排成一个方法，比如 `OrderFacade.createOrder()` 内部依次调库存、优惠、支付、消息。它**不增加新功能**，只是降低调用方的认知负担，也不阻止调用方直接访问子系统。典型：SLF4J 统一日志门面、`JdbcTemplate` 封装 JDBC 的取连接/执行/关资源、`ApplicationContext` 封装 bean 的创建与依赖注入。

2. **组合（Composite）。** 定义统一接口 `Node`，叶子 `File` 与容器 `Folder` 都实现它，容器内部持有一个 `List<Node>` 并递归调用子节点。价值在于客户端不需要判断"这是文件还是文件夹"，一棵树可以整体处理。典型：菜单树、组织架构、表达式求值（`AddNode` 持有两个子表达式）、UI 组件树。

3. **享元（Flyweight）。** 把对象状态拆成"内部状态"（可共享、不变）与"外部状态"（随场景变化、由调用方传入）。工厂用 Map 缓存内部状态相同的对象，复用一个实例。典型：`Integer` 缓存 -128~127、`String` 常量池、棋子游戏里共享"棋子的颜色与形状"而外部传入坐标。注意连接池严格说是"对象池"，池中对象有状态且需要重置，与享元的"不可变共享"不完全一致，但共享意图相同。

4. **三者的结构差异。** 门面是"一对多"的编排（一个入口调多个子系统），组合是"一对多"的递归（一个容器含多个同类型子节点），享元是"多对一"的共享（多个使用方共用一个实例）。看依赖方向就能分清。

5. **常见误用。** 把门面写成"上帝类"，所有业务都往里塞，最后变成一个两千行的 `XxxFacade`；组合在树很深时递归爆栈，需要改迭代或限制深度；享元把可变状态也共享出去，导致"一个用户改了，所有用户都变了"的串数据事故。

**易混对比**：

| 维度 | 门面 Facade | 组合 Composite | 享元 Flyweight |
| --- | --- | --- | --- |
| 解决的问题 | 子系统调用复杂 | 树形结构的统一处理 | 大量相似对象占内存 |
| 结构 | 一个入口编排多个子系统 | 容器与叶子实现同一接口 | 工厂缓存并复用实例 |
| 是否新增功能 | 否，只是简化 | 是，支持递归组合 | 否，只是共享 |
| 典型例子 | SLF4J、`JdbcTemplate` | 菜单树、表达式树 | `Integer` 缓存、常量池 |
| 主要风险 | 变成上帝类 | 递归过深 | 共享了可变状态 |

**面试追问**：
- 追问：门面和适配器的区别？→ 答题要点：门面是简化多个接口的调用，适配器是转换一个不兼容的接口。
- 追问：组合模式一定要有叶子节点吗？→ 答题要点：不一定，但如果没有叶子，树无法终止递归，通常叶子是必需的终止条件。
- 追问：连接池算享元吗？→ 答题要点：思想上共享，但池中对象可变且需要重置状态，更准确叫对象池。

### Q15. Spring 里到底用了哪些设计模式？（中级）

**一句话结论**：Spring 至少用了单例、工厂、模板方法、代理、观察者、策略、适配器、装饰器、责任链、建造者、门面十余种模式，但它的用法普遍比教科书更"轻"——大量用回调、注解、Bean 注册表替代继承式实现。

**先把话说白**：背这张清单的意义不在于数量，而在于说明你读框架时是"看它怎么用"而不是"看它实现了什么功能"。同一个"工厂"，Spring 用的是注册表 + 反射，而不是 23 种模式里的标准类图。理解这种变形，才算真懂模式。

**底层原理**：

1. **单例。** Bean 默认 `singleton` scope，但它是"容器级单例"：每个 `ApplicationContext` 里每个 bean name 一个实例。容器有多个时，同一类型的对象可以有多个实例。实现上不是 DCL，而是 `DefaultSingletonBeanRegistry` 里的 `singletonObjects`（ConcurrentHashMap）+ 三级缓存。

2. **工厂。** `BeanFactory` 是容器级的通用工厂；`FactoryBean` 是标准工厂方法，一个实现对应一种产品（`MapperFactoryBean` 生产 Mapper 代理）。`BeanDefinition` 相当于产品的"图纸"，容器按图纸用反射或 Supplier 创建实例。

3. **模板方法。** `AbstractApplicationContext.refresh()` 是典型骨架：准备上下文、初始化 BeanFactory、调用 `onRefresh()`、注册监听器、完成初始化。`JdbcTemplate`、`RestTemplate`、`TransactionTemplate` 都是"骨架 + 回调"。AQS 虽然不属于 Spring，但 `ReentrantLock` 的思路与之一致。

4. **代理。** AOP 的底层，`@Transactional`、`@Async`、`@Cacheable` 都靠代理织入。JDK 代理与 CGLIB 的选择见 Q8。

5. **观察者。** `ApplicationEvent` + `ApplicationListener` / `@EventListener`，容器启动、刷新、关闭都会发布内置事件（`ContextRefreshedEvent`、`ContextClosedEvent`）。

6. **策略。** `Resource` 接口有 `UrlResource`、`ClassPathResource`、`FileSystemResource` 等多种实现，按前缀（`classpath:`、`file:`）选择；`InstantiationStrategy` 有反射与 CGLIB 两种实例化策略；`PlatformTransactionManager` 有 JDBC、JTA、Reactive 等实现。

7. **适配器。** `HandlerAdapter` 把 `@RequestMapping` 方法、`HttpRequestHandler`、`Controller` 接口等不同形态的处理器，统一适配成 `handle(request, response)` 调用；`MessageConverter` 把不同格式的消息适配成对象。

8. **装饰器。** `BeanWrapper` 在 Bean 外面包一层属性访问能力；`HttpServletRequestWrapper` / `HttpServletResponseWrapper` 允许在 Filter 里包装请求（比如包装成可重复读的 body）；`TransactionAwareCacheDecorator` 让缓存操作跟随事务。

9. **责任链。** Servlet Filter 链、Spring MVC 的 `HandlerExecutionChain`（Interceptor 链）、Spring Security 的 `FilterChainProxy`（十几层 Filter 各管一件事）。

10. **建造者与门面。** `BeanDefinitionBuilder`、`WebClient.builder()`、`MockMvcBuilders` 都是链式建造者；`JdbcTemplate`、`ApplicationContext` 本身也是门面，把复杂的底层细节收在一个入口后面。

**易混对比**：

| 模式 | Spring 中的落点 | 关键类 |
| --- | --- | --- |
| 单例 | Bean 默认作用域 | `DefaultSingletonBeanRegistry` |
| 工厂 | 容器与产品工厂 | `BeanFactory`、`FactoryBean` |
| 模板方法 | 启动流程、JDBC 操作 | `refresh()`、`JdbcTemplate` |
| 代理 | AOP、事务、异步 | `JdkDynamicAopProxy`、`CglibAopProxy` |
| 观察者 | 事件机制 | `ApplicationEventPublisher` |
| 策略 | 资源加载、实例化 | `Resource`、`InstantiationStrategy` |
| 适配器 | 处理器适配 | `HandlerAdapter`、`MessageConverter` |
| 装饰器 | 请求包装、缓存 | `HttpServletRequestWrapper` |
| 责任链 | 过滤与拦截 | `FilterChain`、`HandlerExecutionChain` |
| 建造者 | 链式构建 | `BeanDefinitionBuilder` |

**面试追问**：
- 追问：Spring 的单例和 GoF 单例有什么区别？→ 答题要点：Spring 是容器级、按 bean name 隔离；GoF 是 JVM 级、按类唯一。
- 追问：`BeanFactory` 和 `ApplicationContext` 的区别？→ 答题要点：后者继承前者，增加了事件、国际化、资源加载、AOP 集成等企业级能力，且默认预初始化单例。
- 追问：Spring 为什么大量用回调而不是继承实现模板方法？→ 答题要点：避免继承耦合与单继承限制，回调可以用 lambda，组合更灵活。

### Q16. 什么信号说明你过度设计了？（高级）

**一句话结论**：过度设计的典型信号是"抽象没有第二个实现、扩展点从未被使用、为了将来可能的变更加了没人需要的参数"，判断标准是"这层抽象带来的理解成本，是否小于它已经或即将节省的修改成本"。

**先把话说白**：设计模式的反面不是"不用模式"，而是"用了模式却没有换来确定性收益"。一个只有一个实现的接口、一个永远返回同一个值的策略、一个从没被覆写过的钩子方法，它们不是"为将来做准备"，而是给现在的人加阅读负担。

**底层原理**：

1. **信号一：接口只有一个实现，且没有测试替身的需求。** 如果 `UserService` 只有一个 `UserServiceImpl`，抽接口的唯一收益是"将来可能换实现"。但这个"将来"往往不来，而代价是每次改方法要改两处、跳转多一层、新人要多读一个文件。例外：需要 mock 的边界（外部依赖、时钟、随机数）值得抽接口。

2. **信号二：扩展点从未被使用。** 加了 `beforeXxx`、`afterXxx` 钩子，加了 `plugin` 机制，加了一堆配置开关，结果两年没人用。这说明当初预测的变化方向错了。设计应该跟着**已发生的变化**走，而不是跟着想象走。

3. **信号三：层级只做透传。** Controller → Service → Manager → Helper → Repository，每一层都只是把参数原样传下去，没有任何逻辑。这种分层不产生价值，只产生跳转。分层应该按"职责边界"（事务边界、领域边界、外部依赖边界）切，不是按名字切。

4. **信号四：DTO/VO/DO/PO 机械转换。** 四个模型字段完全一样，只为了"规范"互相 `BeanUtils.copyProperties`。这不是解耦，是把一个类的改动放大成四处改动。只有当模型确实承载不同职责（比如 DO 有数据库注解、VO 有脱敏字段）时才值得拆。

5. **信号五：为不可预见的参数预留。** 方法签名里加 `Map<String, Object> ext`、`Object... args`，或者配置里加一堆没人填的项。这类"灵活性"会让类型检查失效、让调用方不知道传什么，最终变成隐性契约。

6. **正确的判断方式。** 问三个问题：这层抽象**现在**解决了什么具体问题？如果删掉它，代码会变差在哪里？它的成本（类数量、跳转、理解时间）是否小于收益？三个问题有一个答不上来，就该考虑删。重构的方向应该是"三次法则"——同样的逻辑出现第三次时再抽象，而不是第一次就抽象。

**易混对比**：

| 现象 | 看起来像 | 实际是 | 判断依据 |
| --- | --- | --- | --- |
| 只有一个实现的接口 | 面向接口编程 | 可能的过度抽象 | 是否需要 mock 或确实有多种实现 |
| 大量 `if` 被拆成 5 个类 | 策略模式 | 可能只是搬家 | 新增分支是否还需要改调用方 |
| 三层只做透传 | 分层架构 | 无价值跳转 | 每层是否有独立的职责与边界 |
| 预留的扩展参数 | 灵活性 | 隐性契约 | 是否有人真的传过 |
| 全链路 DTO 转换 | 规范 | 改动放大 | 模型是否承载不同职责 |

**面试追问**：
- 追问：怎么说服团队删掉一个过度设计的抽象？→ 答题要点：用数据和成本说话——维护它花了多少时间、出过几次 bug、删掉后影响面多大，而不是争论"设计好不好"。
- 追问：什么时候应该提前抽象？→ 答题要点：变化已经可见（需求明确说要支持多实现）、或抽象成本极低（一个函数式接口）时。
- 追问：重构和过度设计怎么区分？→ 答题要点：重构是"让已有的重复收敛"，过度设计是"为不存在的变化预留"，前者基于事实，后者基于想象。

## 五、本章速记卡

- 面试考模式，考的是"变化点—抽象—代价"，答题用"场景—变化点—结构—代价"四步。
- 六大原则：SRP、ISP、LoD 管职责怎么切；OCP、LSP、DIP 管扩展与依赖方向。
- 单例五种：饿汉（`<clinit>`）、懒汉（方法锁）、DCL（`volatile` + 两次检查）、静态内部类（Holder）、枚举（最安全）。
- DCL 必须 `volatile`：`new` 分三步，2 与 3 可重排，否则会发布半初始化对象。
- 防反射：构造器内判断实例已存在则抛异常；防反序列化：`readResolve` 返回单例；枚举两者天然免疫。
- 简单工厂改一个类、工厂方法加两个类、抽象工厂加一族产品要改所有工厂。
- `FactoryBean` 是标准工厂方法，`BeanFactory` 是容器级通用工厂。
- `@Builder` 会丢字段默认值，必须用 `@Builder.Default`；它还会吃掉无参构造器。
- 代理控访问、装饰加功能可嵌套、适配器转接口；三者类图相同，只能看意图。
- Spring AOP：有接口用 JDK，无接口用 CGLIB；Boot 2.x 起默认 CGLIB，原因是按具体类注入不失败。
- 策略消除 if-else 的关键是"把 type 到实现的映射变成数据"，Spring 注入 `Map<String, Strategy>` 最省代码。
- 模板方法靠继承（AQS、HttpServlet），Spring 更爱"模板 + 回调"（JdbcTemplate）。
- 责任链三差异：传递方式、能否中断、方向；Netty Pipeline 是双向且可动态增删。
- Spring 事件默认同步，监听器异常会影响主流程，异步要配 `taskExecutor` 或 `@Async`。
- 过度设计的核心信号：抽象没有第二个实现，扩展点从未被使用。
