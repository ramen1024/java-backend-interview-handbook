# 附录：答题话术与冲刺计划

> 前 13 章解决"知识会不会"，这一章解决"讲不讲得出来"。技术面试的失分，很大一部分不是不会，而是讲乱了。

## 一、自我介绍的三种时长

自我介绍不是复述简历，而是给面试官一个**提问的钩子**。你希望他问什么，就往那里放什么。

### 1. 一分钟版（电话初筛、HR 面）

结构：年限 + 技术栈 + 一个可量化的成果 + 求职动机。

> 面试官您好，我是 XXX，目前在某公司做 Java 后端，三年经验。主要技术栈是 Spring Boot、MySQL、Redis、Kafka，最近一年负责订单履约链路，做过一次从 3 万到 12 万日订单的扩容改造，主要是分库分表和异步化。这次看机会主要想找一个业务复杂度更高、能参与架构设计的团队。

要点：
- 不要念简历上的公司列表，面试官手里有。
- "做过什么"要用**动词 + 对象 + 结果**，不要用"负责""参与"这种虚词。
- 结尾给动机，避免"想换个环境"这种消极表述。

### 2. 三分钟版（技术一面开场）

结构：现状 → 一条主线项目 → 技术深度锚点 → 一个软性亮点。

> 我目前在后端团队负责交易域。主线项目是订单履约系统，日订单从 3 万涨到 12 万之后，原来的单库单表在写入和查询上都到了瓶颈。我做了三件事：第一是按用户 ID 分库分表，把订单表拆成 16 库 64 表，用 ShardingSphere 做路由；第二是把履约流程里非核心的积分、通知改成 Kafka 异步，主链路 RT 从 380ms 降到 120ms；第三是补了全链路的幂等和补偿，把丢单率从千分之三降到万分之一以下。
>
> 这个过程中我踩过两个比较深的坑：一个是分片键选错导致跨库查询，后来改成基因法把买家维度和订单维度统一；另一个是异步化之后消息重复消费导致积分多发，最后用业务唯一键加状态机兜住。这两个问题让我对"分布式下没有原子性，只有最终一致"这句话有了实际体会。
>
> 除了业务，我平时会看一些中间件源码，写过一个小型的 RPC 框架，主要是想搞明白 Dubbo 的服务暴露和引用到底做了什么。

要点：
- **必须有一个"我踩过的坑"**，这是可信度的来源，也是面试官最容易追问的地方。
- 技术深度锚点要选你真的能聊 10 分钟的，不要提一个自己讲不清的框架。
- 三分钟已经很长，不要超过。

### 3. 项目深挖的应答模板

面试官问"这个项目你负责什么"，本质是在找**你个人的技术判断**，不是团队成果。

| 层次 | 错误答法 | 正确答法 |
| --- | --- | --- |
| 背景 | "我们系统流量很大" | "日订单 12 万，峰值 QPS 约 600，大促会到 2000" |
| 任务 | "我负责订单模块" | "我负责下单链路的库存扣减和幂等，另外主导了分库分表方案选型" |
| 动作 | "用了 Redis 做缓存" | "库存用 Redis + Lua 预扣，DB 做最终扣减，选 Lua 是因为要保证判断和扣减的原子性" |
| 取舍 | （没有） | "也考虑过 DB 悲观锁，但行锁持有时间会随下游 RT 放大，压测下 TPS 只有 Redis 方案的三分之一" |
| 结果 | "效果很好" | "超卖从每天几十单降到 0，扣减 RT 从 45ms 降到 8ms" |

**关键**：每个技术选型都要准备"三件套"——为什么选它、代价是什么、出问题怎么兜底。

## 二、八类高频软性问题的答法

### 1. 你为什么想离职？

不要说前公司坏话，不要只说"钱少"。给一个**向前看**的理由，并把它和面试岗位挂钩。

> 现在的系统已经比较稳定，我更多是在做维护性需求，想找一个业务增量更大、能参与架构决策的环境。贵司这边刚好在扩交易中台，和我这两年的方向比较一致。

### 2. 你最有成就感的一件事？

选一个**技术难度中等但影响面清晰**的事，不要选"我加班最多"。

答法：问题有多难 → 你怎么想的 → 做了什么权衡 → 结果 → 你的反思。

### 3. 你遇到的最大困难？

避免"没有困难"。也不要选纯粹的人际冲突。推荐选**信息不足下的技术决策**，因为它能体现判断力。

> 最难的是分库分表时选分片键。业务上既有买家维度查询，也有商家维度查询，任何单键都会有一边变成跨库。我当时对比了三种方案：冗余双写、基因法、搜索引擎异构。最后选基因法，是因为双写一致性成本太高，而异构索引会引入新的故障点。代价是分片键生成逻辑变复杂，我把它收敛到了统一的 ID 生成服务里。

### 4. 你和同事意见不一致怎么办？

结构：先对齐目标 → 用数据/原型验证 → 保留分歧但执行 → 复盘。

不要说"我听领导的"，也不要说"我说服了他"，要说"我们用压测数据做了决定"。

### 5. 你怎么学习新技术？

给一个**具体的路径**，不要罗列"看博客、看源码"。

> 一般是先用最小 demo 跑通，再读官方文档把概念对齐，然后带着问题看源码。比如学 Kafka，我先写了生产消费 demo，然后卡在"为什么消费组扩容会触发 rebalance"，才去读 Coordinator 的源码。最后会写一篇笔记，强迫自己把机制讲清楚。

### 6. 你的缺点是什么？

选一个**真实但不致命**的，并说明正在怎么改。

> 我有时会过于关注实现细节，导致排期偏紧。后来强制自己在动手前先写一页设计，把边界和验收标准定下来，情况好一些。

### 7. 未来三年的规划？

不要说"想当架构师"这种空话。说能力方向 + 业务理解。

> 短期内想把交易域的稳定性做扎实，把可观测性补齐；中期希望能独立负责一个中等规模系统的架构设计，而不只是执行方案。

### 8. 你还有什么想问我们的？

见下一节。

## 三、反问清单

反问是最后一次展示判断力的机会。**不要问能百度到的**（如"公司做什么业务"），也不要一上来问薪资。

按面试轮次选：

| 轮次 | 可问的问题 | 想获取的信息 |
| --- | --- | --- |
| 技术一面 | 团队现在最头疼的技术问题是什么？ | 判断技术债与你的发挥空间 |
| 技术二面 | 这个岗位未来半年最重要的三件事是什么？ | 判断岗位是否核心、预期是否合理 |
| 交叉面 | 团队的技术决策是怎么做的？有没有设计评审？ | 判断工程文化 |
| HR 面 | 晋升周期与标准？团队目前的人员结构？ | 判断成长路径 |
| 任意 | 如果我有幸入职，您希望我前三个月解决什么问题？ | 展示结果导向，同时探预期 |

不要问：
- "加班多吗"（可以问"团队一般的发布节奏是怎样的"）
- "我表现得怎么样"（通常得不到真实答案）
- 涉及公司机密的问题

## 五、面试当天检查清单

**技术准备**

- 白板/纸笔是否就手（现场面试），共享屏幕是否可用（视频面试）。
- 项目架构图能否 2 分钟内画出来（分层 + 关键中间件 + 数据流向）。
- 准备 3 个可量化的数字：QPS、数据量、优化前后的指标。

**表达准备**

- 自我介绍控制在 1 分钟，出声练 3 遍。
- 每个项目准备一个"坑"和一个"被否决的方案"。
- 准备 3 个反问问题，按轮次取用。

**心态**

- 遇到不会的题，先说"我确认一下问题的边界"，争取 10 秒思考时间。
- 不要抢答。面试官问完停 1 秒再答，能显著降低答偏的概率。
- 被质疑时不要防御。可以说"您说的这个场景我确实没考虑到，如果是这样，我会……"。

## 六、面试后复盘表

每场面完 30 分钟内填完，比刷十道新题有用。

| 字段 | 记录内容 |
| --- | --- |
| 公司/轮次 | |
| 被问住的题 | 原题 + 当时怎么答的 + 正确思路 |
| 答得最好的题 | 为什么好，能否复用这个结构 |
| 面试官的追问方向 | 说明他在意什么，下一次同类项目怎么准备 |
| 表达问题 | 有没有超时、跑题、术语堆砌 |
| 待补章节 | 对应到本书的章节与题号 |
| 反问效果 | 对方回答是否透露了团队真实状态 |

复盘的核心不是"记下答案"，而是**找出自己的表达模式问题**。连续三场都被追问同一个方向，说明那里是真空区；连续三场都在某个环节超时，说明结构需要调整。

## 七、最后一页：把 55 万字压缩成 10 句

如果只剩考前一小时，看这十句：

1. 底层知识不是用来背的，是用来解释方案的。
2. 任何"为什么用它"，都要能接上"代价是什么"。
3. 分布式下没有原子性，只有最终一致和补偿。
4. 缓存解决的是读性能，代价是一致性；加锁解决的是并发，代价是吞吐。
5. 索引让读变快，让写变慢；分库分表让写变快，让查询变难。
6. 线程池的本质是资源隔离与排队策略，不是"提升性能"。
7. JVM 调优先定目标（吞吐还是延迟），再谈参数。
8. 消息队列解决解耦和削峰，代价是重复、乱序与运维复杂度。
9. 系统设计面试考的是取舍的合理性，不是组件的数量。
10. 讲不清的项目，等于没做过。
