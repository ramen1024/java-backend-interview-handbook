# 第 8 章 MySQL：索引、事务、锁与 SQL 优化

> 一句话定位：后端面试里唯一既考"背"又考"推"的模块——索引和锁必须能当场推导，不能只报结论。

## 一、本章考察重点概览 {#s1}

MySQL 在面试中的权重高于其他存储中间件，原因是它同时承载了三种能力考察：**数据结构与磁盘 IO 的结合能力**（索引为什么长这样）、**并发正确性的推理能力**（一条 SQL 到底锁了什么）、**线上问题的定位能力**（慢查询、死锁、主从延迟怎么查）。前两项决定你能不能过技术面，第三项决定定级。

这一章有三个特征需要提前说明：

1. **结论型问题会被追问到实现层。** 你说"B+ 树适合范围查询"，下一句必然是"那 B 树为什么不适合"；你说"RR 解决了幻读"，下一句必然是"那为什么还能测出幻读"。停在结论层面就等于没答。
2. **加锁分析是高级岗的分水岭。** 中级能说出记录锁、间隙锁、临键锁的定义，高级能拿一张具体的表和一条具体的 SQL，按索引扫描路径一步步推出锁的区间。这部分必须动手推，背不下来。
3. **版本差异必须主动交代。** 查询缓存在 8.0 被移除、Hash Join 在 8.0.18 才有、自增锁默认模式在 8.0 改了、INSTANT 加列在 8.0.12 才有。同一句回答在 5.7 和 8.0 下可能一个对一个错。

## 四、题目详解 {#s4}

### Q1. 一条 SQL 从客户端到返回结果，中间经历了什么？（中级） {#q1}

> 前置：连接器、解析器、优化器、执行器

**一句话结论**：一条查询依次经过连接器（认证与权限）、解析器（词法语法分析生成语法树）、优化器（选索引与 join 顺序生成执行计划）、执行器（按计划调用引擎接口逐行取数）、存储引擎（InnoDB 在 Buffer Pool 与磁盘之间取页），返回结果后再经连接器写回客户端；server 层本身不存业务数据。

**先把话说白**：MySQL 不是一个程序，而是"一个调度中心 + 若干可插拔的引擎"。调度中心负责理解你要什么、决定怎么拿最省，引擎负责真的去磁盘上把数据翻出来。搞清这条链的意义在于：后面所有优化问题，你都能立刻判断它发生在哪一层——索引选错是优化器层，锁等待是引擎层，连接打满是连接器层。

**底层原理**：

1. **连接器。** 处理 TCP 握手、账号密码认证、库权限校验。认证通过后权限就固定了，此后即使管理员改了权限，当前连接也不生效，除非重连。连接是长连接还是短连接由客户端决定，服务端用 `wait_timeout`（默认 28800 秒）回收空闲连接。连接本身消耗内存，所以有 `max_connections` 上限，生产上必须配连接池。

2. **查询缓存（仅 5.7 及以前）。** 以 SQL 文本为 key 缓存结果集，命中直接返回。问题是只要表有任何一次写，该表所有缓存全部失效，命中率极低、维护成本高，MySQL 8.0 已彻底移除该模块。所以现在讲执行流程时可以直接跳过它，这一点要主动说明，否则会被认为在看旧资料。

3. **解析器与预处理器。** 词法分析把 SQL 拆成 token，语法分析按语法规则构建语法树。若表名、列名写错，在这一步报错。预处理器再做语义检查：表是否存在、列是否歧义、别名是否重复。

4. **优化器。** 这是最值得讲的一层。优化器基于**代价模型（cost-based）**在多个执行计划中选一个，主要决策有三类：单表选哪个索引（或全表扫描）、多表 join 的顺序（哪张做驱动表）、条件如何下推到索引层。代价由两部分估算：IO 代价（读多少个页）与 CPU 代价（比较多少行）。估算依据是统计信息，而统计信息是**采样**出来的（`innodb_stats_persistent_sample_pages` 默认 20 个页），这就埋下了"选错索引"的根因。

5. **执行器。** 拿到执行计划后，先检查当前用户对目标表有没有权限，然后打开表、调用引擎的 `index` 或 `table` 接口，一行一行取，判断是否满足 `WHERE` 条件，满足就放进结果集。这里有个常被忽略的点：**server 层取到行之后还要再做一次条件过滤**，这就是 EXPLAIN 里 `rows` 与实际返回行数经常不一致、以及 `Using where` 的来源。

6. **存储引擎。** InnoDB 以页（16KB）为单位读写。若页在 Buffer Pool 中直接返回，否则发起磁盘 IO 读整页。注意"读一整页"这个事实：这是 B+ 树设计的物理前提，也是为什么"少读页"等于"快"。

```sql
-- 打开优化器追踪，看它比较了哪些计划、每个计划的代价
SET optimizer_trace = 'enabled=on';
SELECT * FROM t WHERE c = 10 AND d > 5;
SELECT * FROM information_schema.optimizer_trace\G
SET optimizer_trace = 'enabled=off';
```

**面试追问**：
- 追问：优化器一定能选到最优计划吗？→ 答题要点：不能，代价模型基于采样统计，且不考虑 Buffer Pool 命中率、并发、数据倾斜，所以会出现选错。
- 追问：`SELECT 1` 需要经过存储引擎吗？→ 答题要点：不需要，没有表访问，server 层直接返回，这也是它常被用作健康检查的原因。
- 追问：为什么权限校验在连接时就固定了？→ 答题要点：避免每次查询都查权限表，属于性能取舍，代价是权限变更需要重连生效。
- 追问：`ORDER BY` 是在哪一层做的？→ 答题要点：若索引本身有序则由引擎顺序返回；否则 server 层做 filesort，这是 `Using filesort` 的含义。

### Q2. InnoDB 的 Buffer Pool 是怎么管理的？为什么要改 LRU？（高级） {#q2}

> 前置：数据页、LRU、脏页

**一句话结论**：Buffer Pool 是 InnoDB 在内存中缓存数据页与索引页的区域，用"空闲链表 + 脏页链表 + 改进 LRU 链表"三套结构管理；改进点在于把 LRU 拆成 young 与 old 两段、新页从 midpoint 插入、并要求在 old 区停留超过一定时间才能晋升，从而避免全表扫描与预读把热数据挤出去。

**先把话说白**：磁盘太慢，所以 InnoDB 把读过的页留在内存里。既然是缓存就得淘汰，最朴素的 LRU 是"最久没用的先走"。但 MySQL 面对的是一个特殊场景：偶尔来一条全表扫描，把几十万个页一次性读进来，它们每个都"刚被用过"，于是一瞬间把真正的热数据全冲掉。这就是所谓的**缓冲池污染**，改进 LRU 就是为了解决它。

**底层原理**：

1. **内存组织。** Buffer Pool 按页划分，每页 16KB，另有一块控制块记录页号、修改次数、脏页标记、链表指针。三套链表：free 链表（空闲页）、flush 链表（脏页，按最早修改的 LSN 排序）、LRU 链表（所有已缓存的页）。`innodb_buffer_pool_size` 决定总大小，生产上通常给物理内存的 50%~70%；8.0 支持 `innodb_buffer_pool_instances` 多实例，把锁竞争分散到多个池上。

2. **改进 LRU 的两个参数。** `innodb_old_blocks_pct` 默认 37，表示 LRU 链表中 old 区占 37%，young 区占 63%。新读入的页不是插到链表头，而是插到 old 区的头部（midpoint）。

3. **抗扫描的关键是时间窗。** 只有当一个页在 old 区停留超过 `innodb_old_blocks_time`（默认 1000 毫秒）之后再次被访问，才会被移到 young 区头部。全表扫描时一个页被连续访问多次，但都在 1 秒内完成，所以永远不会晋升，扫描结束后就被淘汰——热数据毫发无伤。这一条是整道题的核心，只说"分成两段"是不够的。

4. **脏页什么时候刷。** 四种触发：redo log 空间快用完（要推进 checkpoint）、脏页比例超过 `innodb_max_dirty_pages_pct`（默认 90）、LRU 淘汰时需要先刷脏页、系统空闲时后台慢慢刷。刷脏页会造成响应抖动，所以生产上常用 `innodb_io_capacity` 控制刷盘速度，避免一次性打满磁盘。

5. **change buffer。** 对**非唯一二级索引**的插入与更新，如果目标页不在 Buffer Pool 中，InnoDB 不立刻去磁盘读页，而是把"这个页要插一条索引记录"记在 change buffer 里，等后续该页被读入时再 merge。收益是把多次随机读合并成一次。为什么唯一索引不能用？因为唯一索引插入前必须读页判断是否重复，既然必须读，缓存变更就没意义了。这也是"为什么建议用普通索引而非唯一索引"的一个真实理由。

6. **自适应哈希索引（AHI）。** InnoDB 会监控索引页的等值查询模式，对反复出现的等值查询在内存中建哈希索引，把 B+ 树的 3~4 次页访问降为 1 次。`innodb_adaptive_hash_index` 默认开启。它在高并发范围查询多的场景下会带来 `btr_search_latch` 竞争，部分互联网公司会关闭它，这属于"默认值不等于最优"的典型。

**易混对比**：

| 结构 | 存什么 | 作用 | 相关参数 |
| --- | --- | --- | --- |
| Buffer Pool | 数据页、索引页 | 减少磁盘 IO | `innodb_buffer_pool_size` |
| change buffer | 非唯一二级索引的变更 | 合并随机读，延迟 merge | `innodb_change_buffer_max_size`（默认 25%） |
| redo log buffer | 待写入 redo 的变更 | 批量写日志，减少 fsync | `innodb_log_buffer_size`（默认 16MB） |
| AHI | 热点页的等值查询哈希 | 等值查询降为一次查找 | `innodb_adaptive_hash_index` |

**面试追问**：
- 追问：Buffer Pool 越大越好吗？→ 答题要点：不是，要留内存给连接、排序缓冲和 OS 页缓存；且实例重启后预热慢，可用 `innodb_buffer_pool_load_at_startup` 加速。
- 追问：change buffer 会不会丢？→ 答题要点：change buffer 中的变更最终要 merge 到页上，5.7 崩溃后可能丢失需重建索引，8.0 做了持久化改进；不影响数据正确性，因为未 merge 的变更本身也有 redo 保护。
- 追问：为什么唯一索引不适合 change buffer？→ 答题要点：必须读页判重，随机读无法避免，缓存写变更失去意义。
- 追问：脏页刷不过来会怎样？→ 答题要点：查询被阻塞等刷脏，表现为周期性抖动，日志里能看到 checkpoint 相关等待。

### Q3. redo log、undo log、binlog 各自解决什么问题？为什么要两阶段提交？（高级） {#q3}

> 前置：redo / undo / binlog、两阶段提交

**一句话结论**：redo log 是 InnoDB 的物理逻辑日志，保证已提交事务的修改不丢（持久性）；undo log 记录反向操作，用于事务回滚与 MVCC 版本链；binlog 是 server 层的逻辑日志，用于主从复制与数据归档。三者分属两个层次、两套写入体系，必须用两阶段提交保证"主库数据"与"binlog"的一致。

**先把话说白**：改一行数据要动磁盘上的页，而磁盘随机写很慢。InnoDB 的做法是"先在内存改，再把'改了什么'顺序记到日志里，日志落盘就算提交成功，页慢慢刷"。这就是 WAL（Write-Ahead Logging，预写日志）。日志是顺序写，比随机写页快一到两个数量级，于是"提交"这个动作从"等页落盘"变成"等日志落盘"。

**底层原理**：

1. **redo log 的定位。** 它是 InnoDB 引擎层的日志，记录的是"在某个表空间的某个页的某个偏移处，写了什么字节"，属于物理逻辑日志。大小固定（5.7 用 `innodb_log_file_size` 乘组数；8.0.30 起用 `innodb_redo_log_capacity`），循环写，写满就要推进 checkpoint 逼脏页落盘。它的作用是**崩溃恢复时前滚**：把已提交但页还没刷的修改重做一遍。

2. **undo log 的定位。** 逻辑日志，记录"如果要把这条记录改回去该怎么做"（插入对应删除，更新对应改回旧值）。两个用途：事务回滚时反向执行；MVCC 中沿 `DB_ROLL_PTR` 找历史版本。undo 本身也是要写 redo 的，否则 undo 丢了就没法回滚。undo 由 purge 线程异步清理，长事务会让 undo 无法回收、undo 表空间暴涨。

3. **binlog 的定位。** server 层日志，与引擎无关，所以 MyISAM 也能用。记录的是逻辑变更，格式有三种：`STATEMENT`（记 SQL）、`ROW`（记行变更前后镜像）、`MIXED`（自动切换）。binlog 是追加写、不循环，用于主从复制与基于时间点的恢复。`ROW` 格式下一条 update 影响 10 万行就写 10 万条记录，这是"大事务打爆 binlog"的原因。

4. **为什么必须两阶段提交。** redo 和 binlog 是两套独立的写入，无法原子地同时落盘。假设先写 redo 再写 binlog，中间崩溃：主库恢复后有新值，binlog 里没有，从库和备份都缺这条变更，**主从不一致**。反过来先写 binlog 再写 redo，中间崩溃：binlog 有记录会被从库重放，主库却没有这条数据，**从库多数据**。两种不一致都不可接受，所以引入 2PC。

5. **两阶段的时序与崩溃恢复规则。** 提交时先写 redo 并标记为 prepare 状态，再写 binlog，最后写 redo 标记 commit。崩溃恢复时，redo 中处于 prepare 的事务要去看 binlog：**binlog 完整（有结束标记、XID 匹配）则提交，不完整则回滚**。判断依据是 binlog 是否完整，而不是 redo——这是"以 binlog 为准"的设计，因为 binlog 是复制与恢复的事实来源。

6. **组提交（group commit）。** 2PC 带来两次 fsync，为了不退化性能，MySQL 5.6 起把 fsync 按阶段合并：多个事务的 redo 一起 fsync（flush 阶段）、binlog 一起 fsync（sync 阶段）、一起标记 commit（commit 阶段）。并发越高，均摊到每个事务的 fsync 次数越少，这也是高并发下 TPS 反而更好的原因之一。

```text
        事务提交
           |
      [redo prepare]  ←── fsync（受 innodb_flush_log_at_trx_commit 控制）
           |
      [写 binlog]     ←── fsync（受 sync_binlog 控制）
           |
      [redo commit]
           |
        返回客户端
```

**易混对比**：

| 维度 | redo log | undo log | binlog |
| --- | --- | --- | --- |
| 所属层 | InnoDB 引擎 | InnoDB 引擎 | server 层 |
| 日志类型 | 物理逻辑（页 + 偏移） | 逻辑（反向操作） | 逻辑（SQL 或行镜像） |
| 写入方式 | 循环写，空间固定 | 随机读写，按段分配 | 追加写，不覆盖 |
| 主要用途 | 崩溃恢复前滚 | 回滚、MVCC 快照 | 主从复制、归档恢复 |
| 是否可关闭 | 不能 | 不能 | 可关（`skip-log-bin`），但生产禁止 |
| 生命周期 | 刷脏后可覆盖 | 无活跃事务引用后 purge | 由 `expire_logs_days` 清理 |

**面试追问**：
- 追问：能不能只用 binlog 做崩溃恢复？→ 答题要点：不够，binlog 是逻辑日志、没有页级信息，且 InnoDB 需要 redo 保证页的物理一致性（如 double write 配合）。
- 追问：redo log 写满了会怎样？→ 答题要点：必须推进 checkpoint 逼脏页刷盘，此时更新会被阻塞，表现为"抖一下"。
- 追问：为什么说 binlog 是"以它为准"？→ 答题要点：它是复制与备份的唯一事实来源，从库只认 binlog，所以恢复时必须与它对齐。
- 追问：`redo log` 和 `binlog` 能保证主从绝对一致吗？→ 答题要点：同步复制下可以，异步复制下主库提交即返回，从库可能落后，存在窗口。

### Q4. 一条 update 语句的完整执行链路是什么？刷盘参数怎么选？（高级） {#q4}

> 前置：日志顺序、刷盘参数

**一句话结论**：update 依次经过连接器、解析器、优化器、执行器，进入 InnoDB 后：取页到 Buffer Pool（不在则从磁盘读）→ 加行锁 → 写 undo 并记录旧值 → 修改内存中的页成为脏页 → 写 redo log buffer → 提交时按两阶段提交落盘 → 后台线程异步刷脏页。可靠性由 `innodb_flush_log_at_trx_commit` 与 `sync_binlog` 两个参数共同决定。

**先把话说白**：更新一条记录，磁盘上的页可能被改了，也可能还没改。真正保证"你说提交成功，数据就一定在"的，不是页，是日志。理解了这一点，就能理解为什么"机器断电丢数据"这种事故总是和刷盘参数有关，而不是和"有没有写成功"有关。

**底层原理**：

1. **定位记录。** 执行器调用引擎接口取 id=1 的行。若页在 Buffer Pool 中直接返回；否则从磁盘读整页放入 Buffer Pool（走一遍改进 LRU 的插入逻辑）。

2. **加锁。** 对要修改的行加排他锁（X 锁）。注意这里加的是**当前读**语义的锁，且加锁范围取决于走的是哪个索引、是等值还是范围——这是 Q17 的内容，但必须在这里点出来：update 的锁范围是慢 SQL 与死锁的主要来源。

3. **写 undo。** 把旧值写入 undo log，形成版本链的一环。这样回滚可以反向执行，MVCC 也能读到旧版本。

4. **改内存页。** 直接修改 Buffer Pool 中的页，此时页变"脏"，加入 flush 链表。注意：**这一步磁盘上的页还没变**。

5. **写 redo。** 把"哪个页的哪个偏移改成了什么"写入 redo log buffer。redo 在事务执行过程中就不断写入，不是提交时才写。

6. **提交与落盘。** 进入 Q3 描述的两阶段提交：redo prepare 并 fsync（取决于参数）、写 binlog 并 fsync（取决于参数）、redo commit。

7. **后台刷脏页。** 由 page cleaner 线程按 checkpoint 推进，把脏页写到磁盘。此时磁盘数据才真正更新。

```sql
-- 观察一条 update 的影响行数与锁等待
BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1;
-- 此时另一个会话执行相同语句会阻塞，直到本事务提交
COMMIT;
```

**刷盘参数的取舍**：

| 参数 | 取值 | 语义 | 崩溃后果 | 适用场景 |
| --- | --- | --- | --- | --- |
| `innodb_flush_log_at_trx_commit` | 1（默认） | 每次提交都 fsync redo | 不丢已提交事务 | 金融、订单，绝大多数业务 |
| 同上 | 2 | 每次提交写 OS cache，每秒 fsync | MySQL 进程崩溃不丢，机器断电丢约 1 秒 | 可容忍少量丢失的日志类业务 |
| 同上 | 0 | 每秒写并 fsync | 进程崩溃也可能丢约 1 秒 | 极少使用，仅批量导入 |
| `sync_binlog` | 1 | 每次提交 fsync binlog | 不丢 | 主从架构必选（8.0 默认 1） |
| 同上 | N | 每 N 次提交 fsync 一次 | 最多丢 N 个事务的 binlog | 5.7 默认为 0，需手动改 |
| 同上 | 0 | 交给 OS 决定 | 不可控 | 单机、可重建数据 |

需要强调：**`innodb_flush_log_at_trx_commit=1` 与 `sync_binlog=1` 是"双 1"配置**，这是主从架构下的安全底线。很多团队为了压测数据把它调成 2 或 0，压完忘了改回来，这是典型的生产事故来源。

**面试追问**：
- 追问：为什么"双 1"下还能有不错的吞吐？→ 答题要点：组提交把多个事务的 fsync 合并，并发越高摊薄越明显。
- 追问：`innodb_flush_log_at_trx_commit=2` 到底丢了什么？→ 答题要点：丢的是 OS 缓冲区里未 fsync 的 redo，即最后约 1 秒已提交事务，进程崩溃不丢、断电丢。
- 追问：double write 是干什么的？→ 答题要点：防止页写到一半断电导致页损坏，redo 无法在坏页上重放；先把页写到 doublewrite 区再写数据文件。
- 追问：update 没走索引会怎样？→ 答题要点：全表扫描并对扫描到的每一行加锁，等于锁表，还可能升级为大量锁冲突。

### Q5. 为什么用 B+ 树做索引，而不是 B 树、哈希、红黑树或跳表？（中级） {#q5}

> 前置：磁盘 IO、页、索引结构

**一句话结论**：B+ 树的非叶节点只存键和指针，单页能容纳上千个键，使 2000 万行数据只需 3~4 层，即 3~4 次磁盘 IO；叶子节点用双向链表串联，天然支持范围查询与排序。B 树非叶也存数据导致扇出小、树更高；哈希不支持范围；红黑树树高太大；跳表适合内存不适合磁盘。

**先把话说白**：索引的本质是"用更少的磁盘 IO 找到目标行"。磁盘一次 IO 的固定开销很大，但一次能读 16KB，所以关键不是"比较次数少"，而是"每次 IO 能排除掉尽可能多的数据"。B+ 树就是为这个目标长出来的形状：一个节点塞满一页，一页里放上千个键，一次 IO 就能把搜索范围缩小一千倍。

**底层原理**：

1. **先算扇出。** InnoDB 页 16KB。假设主键是 bigint（8 字节），页内指针 6 字节，则一条索引项约 14 字节，一页能放 `16384 / 14 ≈ 1170` 个。若叶子节点每行 1KB，一页放 16 行。三层 B+ 树可存 `1170 × 1170 × 16 ≈ 2190 万` 行。也就是说，两千万行的表，查一条记录最多 3 次 IO（根页常驻内存，实际往往 2 次）。这个数量级是 B+ 树最有力的论据，面试时一定要报出来。

2. **对比 B 树。** B 树的非叶节点同时存键和数据。数据一旦进了非叶节点，一页能放的键就少一个数量级，扇出从上千降到几十，树高从 3 层涨到 6~7 层，IO 翻倍。而且 B 树的范围查询需要在树中反复中序遍历，无法顺序扫描。

3. **对比哈希。** 哈希等值查询 O(1)，看起来更快，但三个致命问题：不支持范围查询（`>`、`between`、`like`）、不支持排序（`order by` 要额外排序）、不支持最左前缀（联合索引无从谈起）。此外哈希冲突严重时退化为链表。InnoDB 的自适应哈希索引只是 B+ 树之上的补充加速，不是替代。

4. **对比二叉搜索树 / 红黑树。** 二叉树每个节点只有两个分支，2000 万行需要约 24 层，即 24 次 IO；即便红黑树平衡，也只是把常数压到 `log2N`，无法改变"每个节点只排掉一半"的本质。B+ 树是"多路"的，一个节点排掉 99.9%。

5. **对比跳表。** 跳表用多层链表实现 O(logN) 查找，实现简单、写入无需 rebalance，Redis 的 ZSet 就用它。但它是**内存结构**：节点随机分布、指针跳跃，磁盘上无法保证局部性，一次查找可能触发多次随机 IO；且层高靠随机数，最坏情况退化。B+ 树把所有键紧凑排在一页内，一次 IO 拿到连续的一千个键，这是磁盘友好的关键。

6. **为什么叶子要连成链表。** 范围查询 `where id between 100 and 200` 只需定位到 100 所在的叶子，然后沿链表顺序读下去，不需要回到根节点重新查找。同时链表有序意味着 `order by id` 可以直接利用索引顺序，避免 filesort。

**易混对比**：

| 结构 | 等值查询 | 范围查询 | 排序 | 磁盘 IO 特性 | 典型使用者 |
| --- | --- | --- | --- | --- | --- |
| B+ 树 | O(logN)，3~4 次 IO | 叶子链表顺序扫描 | 天然有序 | 扇出大、树矮、局部性好 | InnoDB、MyISAM |
| B 树 | O(logN)，树更高 | 需中序遍历，差 | 部分支持 | 非叶存数据，扇出小 | MongoDB 索引（B 树变体） |
| 哈希 | O(1) | 不支持 | 不支持 | 随机 IO | Memory 引擎、AHI |
| 红黑树 | O(logN)，约 24 层 | 中序遍历 | 有序 | 每节点一次 IO，不可接受 | `std::map`、Java TreeMap |
| 跳表 | O(logN) 期望 | 链表顺序扫描 | 有序 | 随机指针，局部性差 | Redis ZSet、LevelDB MemTable |

**加分点 / 易错点**：
- 说"B+ 树比 B 树查询快"是错的。单点查询两者都是 O(logN)，B+ 树优势在**扇出更大导致树更矮**与**范围查询更友好**。
- 说"B+ 树叶子存数据所以快"也不准确。聚簇索引叶子存整行，二级索引叶子存主键，两者都是 B+ 树。

**面试追问**：
- 追问：三层 B+ 树能存多少行？→ 答题要点：按 16KB 页、bigint 主键估算约两千万，要现场把 1170×1170×16 算出来。
- 追问：为什么不用哈希索引做范围查询的补充？→ 答题要点：范围查询无法用哈希定位起点，仍需有序结构，所以 InnoDB 只在 AHI 上做等值加速。
- 追问：B+ 树的页分裂是什么？→ 答题要点：插入的键所在页已满时拆成两页并提升中间键到父节点，随机插入会频繁分裂。
- 追问：为什么根页常驻内存？→ 答题要点：访问频繁，Buffer Pool 自然长期持有，实际 IO 次数比理论层数少一次。

### Q6. 聚簇索引与二级索引有什么区别？回表、覆盖索引、索引下推是什么？（中级） {#q6}

> 前置：回表、覆盖索引、索引下推

**一句话结论**：聚簇索引（Clustered Index）以主键组织，叶子节点存放整行数据，一张表只有一个；二级索引（Secondary Index）叶子存放"索引列 + 主键值"，查询非索引列时需要拿主键回聚簇索引再查一次，称为回表。若查询的列全部在索引中则无需回表，即覆盖索引；索引下推（ICP）把部分条件下推到引擎层在索引上过滤，减少回表次数。

**先把话说白**：聚簇索引是"按主键排好序的整张表"，它本身就是数据；二级索引是"按某列排好序的目录"，目录里只写"这一列的值和对应的主键"，你想看这一行的其他字段，得拿着主键再去正文里翻一次——这就是回表。翻一次是随机 IO，翻一万次就是一万次随机 IO，所以回表是二级索引最大的成本。

**底层原理**：

1. **聚簇索引的结构。** InnoDB 的主键索引即聚簇索引，叶子节点存完整行记录（含隐藏列 `DB_TRX_ID`、`DB_ROLL_PTR`）。如果没有主键，InnoDB 选第一个非空唯一索引；都没有则生成 6 字节的隐藏 `DB_ROW_ID`。所以"没有主键的表"并不是没有聚簇索引，而是用了隐式主键——这一点常被答错。

2. **二级索引的结构。** 叶子存索引列的值 + 主键值。这解释了两个现象：一是二级索引比聚簇索引小很多，同样的 Buffer Pool 能缓存更多；二是**主键越长，所有二级索引都越大**，这是"主键要短"的根本原因。

3. **回表的代价。** 先在二级索引上找到一批主键，再按主键逐个回聚簇索引查整行。问题在于：二级索引上相邻的主键，在聚簇索引中可能相隔很远，于是变成大量随机 IO。若回表行数很多，优化器可能判定"不如直接全表扫描"——这就是有时候明明有索引却走了全表扫描的原因。

4. **覆盖索引。** 查询需要的列全部在索引中，引擎返回索引记录即可，不需要回表。EXPLAIN 的 Extra 显示 `Using index`。实践含义：把高频查询的列放进联合索引，用空间换掉回表。注意 `select *` 永远无法覆盖。

5. **索引下推（ICP, Index Condition Pushdown）。** MySQL 5.6 引入。没有 ICP 时，引擎按索引找到记录后必须回表取整行，再交给 server 层判断其余条件；有 ICP 时，引擎在索引上就能判断的条件先判断，不满足的直接跳过，不回表。Extra 显示 `Using index condition`。

```sql
-- 表：user(id PK, name, age, city)，联合索引 idx_name_age(name, age)
-- 查询：name 以 '张' 开头且 age = 20

-- 无 ICP（5.5 及以前）：
-- 1. 索引上扫到所有 name like '张%' 的记录（假设 10000 条）
-- 2. 每条都回表取整行
-- 3. server 层再过滤 age = 20，最后剩 10 条
-- → 10000 次回表

-- 有 ICP（5.6+）：
-- 1. 索引上扫到 name like '张%'
-- 2. 直接在索引记录上判断 age = 20（age 就在索引里）
-- 3. 只有满足的 10 条才回表
-- → 10 次回表
```

**易混对比**：

| 维度 | 聚簇索引 | 二级索引 |
| --- | --- | --- |
| 数量 | 每表一个 | 可有多个 |
| 叶子内容 | 完整行记录 | 索引列 + 主键值 |
| 是否需回表 | 否 | 查非索引列时需要 |
| 大小 | 最大 | 较小（但随主键变长而变大） |
| 组织键 | 主键 | 建索引时指定的列 |
| 更新代价 | 主键变更代价极高 | 只影响自身与指向 |

**面试追问**：
- 追问：为什么建议查询避免 `select *`？→ 答题要点：无法使用覆盖索引，必然回表，且会增加网络传输与内存占用。
- 追问：把 `select *` 改成需要的列就一定能覆盖吗？→ 答题要点：不一定，必须是联合索引包含所有查询列，且顺序无关但列要齐。
- 追问：ICP 与覆盖索引是一回事吗？→ 答题要点：不是。ICP 减少回表次数，覆盖索引消除回表；前者 Extra 是 `Using index condition`，后者是 `Using index`。
- 追问：二级索引为什么存主键而不是行地址？→ 答题要点：行地址会随页分裂变动，存主键则只需在聚簇索引中重新定位，代价是可能回表两次（主键变更时）。

### Q7. 最左前缀原则是怎么来的？为什么跳过最左列就用不上索引？（中级） {#q7}

> 前置：联合索引、B+ 树排序

**一句话结论**：联合索引 `(a, b, c)` 的排序规则是"先按 a 排，a 相同再按 b 排，a、b 都相同再按 c 排"，因此只有在 a 确定（或 a 上有等值/范围条件）时，b 才在索引内局部有序；跳过 a 直接查 b，b 在全局是无序的，无法二分定位，索引失效。

**先把话说白**：想象一本先按"省"、再按"市"、再按"区"排序的通讯录。你要找"杭州市"，可以直接翻到浙江省那一段再找；但你要找"所有叫朝阳区的区"，只能把整本书翻一遍，因为朝阳区可能在北京，也可能在长春。索引就是这么一本书，它只保证"前缀确定后，后面的列才有顺序"。

**底层原理**：

1. **排序的本质。** 联合索引的键值是 `(a, b, c)` 拼接后按字典序排序。字典序的第一原则是"先比第一个字段，相等才比第二个"。所以 a 全局有序，b 只在 a 相同的分组内有序，c 只在 (a,b) 相同的分组内有序。

2. **B+ 树只能跳一次。** 索引查找是"在根页二分 → 定位子页 → 再二分"，每一层都依赖**当前层的键在页内有序**。给定 a=1，b 的取值在 a=1 的分组里有序，可以二分；不给 a，b 在整个索引里跨分组无序，二分的前提不成立，只能全索引扫描。

3. **哪些写法能用。** `where a=1`、`where a=1 and b=2`、`where a=1 and b=2 and c=3` 都能用；`where a=1 and c=3` 只能用 a 这一段（c 无法定位，但若有 ICP 可在索引上过滤）；`where b=2`、`where c=3` 完全用不上。

4. **范围查询会截断。** `where a>1 and b=2`：a 是范围，扫描到 a>1 的所有记录后，b 在这些记录里跨多个 a 分组，不再全局有序，所以 b 不能用于定位。这就是"范围之后的列失效"。但 MySQL 5.6 之后，b 仍可能被 ICP 用于索引内过滤，只是不能缩小扫描范围——这两件事要分清。

5. **顺序无关的错觉。** `where b=2 and a=1` 与 `where a=1 and b=2` 等价，优化器会自动调整条件顺序去匹配索引。所以"最左前缀"约束的是**索引定义的列顺序**，不是 SQL 里 where 的书写顺序。这一点很多人答错。

6. **8.0 的跳跃扫描。** MySQL 8.0.13 引入 Index Skip Scan，当最左列区分度很低（比如性别只有两个值）时，优化器可以"跳过"最左列，对每个可能的最左值分别做一次查找。它降低了最左前缀的刚性，但代价是扫描次数等于最左列的基数，只在最左列基数极小时才有收益。

```sql
-- 索引：idx_abc(a, b, c)
SELECT * FROM t WHERE a = 1 AND b = 2 AND c = 3;   -- 全用上
SELECT * FROM t WHERE a = 1 AND c = 3;             -- 只用到 a，c 靠 ICP 过滤
SELECT * FROM t WHERE b = 2;                        -- 用不上，全索引扫描或全表
SELECT * FROM t WHERE a > 1 AND b = 2;              -- a 用于范围，b 不能定位
SELECT * FROM t ORDER BY a, b;                      -- 可用索引顺序，免 filesort
SELECT * FROM t ORDER BY b, a;                      -- 不可用，需 filesort
```

**面试追问**：
- 追问：`where a=1 and c=3` 能用索引吗？→ 答题要点：能用 a 定位，c 只能过滤；Extra 可能出现 `Using index condition`。
- 追问：`order by` 也遵循最左前缀吗？→ 答题要点：是，`order by a,b` 可用，`order by b` 不可用；且 8.0 之前 asc/desc 混用也无法利用索引。
- 追问：范围查询后面的列一定完全没用吗？→ 答题要点：不能用于定位，但可用于 ICP 过滤与覆盖，减少回表。
- 追问：8.0 的 skip scan 能替代最左前缀吗？→ 答题要点：不能，只适用于最左列基数极小的场景，成本是最左列基数倍的查找。

### Q8. 哪些情况会导致索引失效？（中级） {#q8}

> 前置：隐式转换、函数、范围查询

**一句话结论**：索引失效的本质是"索引上的有序性被破坏"或"优化器判断走索引更贵"，典型场景包括：对索引列做函数或运算、隐式类型转换、前导模糊匹配、OR 分支中存在无索引列、范围条件之后的列、`!=` 与 `not in`、字符集或排序规则不一致、以及回表行数过多时优化器主动放弃索引。

**先把话说白**：索引能加速的前提是"按索引列的值能排好序、能二分"。任何让"列的值"变成"表达式的结果"的写法，都会让索引里存的值和你要比的值对不上号，只能逐行算。理解了这一句，下面所有场景都能自己推出来，不用背。

**底层原理**：

1. **对索引列做函数或运算。** `where date(create_time) = '2026-01-01'`、`where id + 1 = 10`。索引里存的是 `create_time` 的原始值，不是 `date(create_time)`，B+ 树无法用"函数结果"去二分。改写成范围查询 `create_time >= '2026-01-01' and create_time < '2026-01-02'` 即可。MySQL 8.0.13 起支持函数索引（`create index idx on t((date(create_time)))`），是另一种解法。

2. **隐式类型转换。** 这是最隐蔽的一类，分两个方向：
   - 字符串列与数字比较：`where phone = 13800000000`（phone 是 varchar）。MySQL 会把字符串列转成数字再比，等价于 `cast(phone as signed) = ...`，列上套了函数，索引失效。这是手机号查询失效的经典原因。
   - 数字列与字符串比较：`where id = '10'`（id 是 int）。规则是把字符串转成数字，转换发生在常量侧，索引仍然可用。所以"隐式转换一定失效"是错的，要看转换发生在哪一侧。

3. **前导模糊匹配。** `like '%abc'` 无法定位起点（索引按前缀有序，后缀无序）；`like 'abc%'` 可以；`like '%abc%'` 不行。若必须中缀搜索，应使用全文索引或搜索引擎（ES）。

4. **OR 连接的条件。** `where a = 1 or b = 2`，若 b 无索引，则 b 那一路必须全表扫描，优化器索性整体走全表。若两边都有索引，可能走 index merge（Extra 显示 `Using union`），但 index merge 往往不如单索引高效，也常被优化器放弃。

5. **范围条件之后的列。** 见 Q7。`where a > 1 and b = 2` 中 b 不能用于定位，只能过滤。

6. **`!=`、`not in`、`not exists`。** 这类条件通常需要扫描"不满足"的绝大部分数据，若该列区分度不高，优化器判定走索引的回表成本高于全表扫描，主动放弃。注意：不是语法上不能用，而是代价上不划算，区分度极高时仍可能走索引。

7. **`is null` 与 `is not null`。** 与常见说法相反，`is null` **可以**走索引（索引里存了 NULL 值），真正的问题是 NULL 值多时区分度低、优化器可能放弃。前提是列的统计信息里 NULL 占比不高。

8. **字符集或排序规则不一致。** 两张表 join 时，一边 utf8mb4、一边 utf8，或 `collation` 不同，MySQL 需要转换，转换发生在列上，索引失效。这类问题在多团队协作、历史表迁移后很常见，EXPLAIN 里表现为 `ref` 变 `ALL` 且 `key` 为 NULL。

9. **回表行数过多。** 即使语法完全正确，若优化器估算需要回表的行数超过全表行数的某个比例（经验值 20%~30%，无固定阈值，取决于代价模型），会主动选全表扫描。顺序读整表比随机回表更便宜，这是**优化器的合理选择**，不是"索引失效"的 bug。

**易混对比**：

| 写法 | 是否走索引 | 原因 |
| --- | --- | --- |
| `where dt = '2026-01-01'` | 是 | 常量直接比较 |
| `where date(dt) = '2026-01-01'` | 否 | 列上套函数，索引值对不上 |
| `where phone = 13800000000`（varchar 列） | 否 | 列被隐式转数字 |
| `where id = '10'`（int 列） | 是 | 常量侧转换，列未被改 |
| `like 'abc%'` | 是 | 前缀有序可二分 |
| `like '%abc'` | 否 | 起点不确定 |
| `where a = 1 or b = 2`（b 无索引） | 否 | 另一路需全表，整体退化 |
| `where a is null` | 可能 | 索引含 NULL，看区分度 |
| `where a != 1` | 通常否 | 需回表行数过多 |

**面试追问**：
- 追问：为什么 `varchar` 列传数字会失效，`int` 列传字符串不会？→ 答题要点：转换方向由"哪边精度高"决定，字符串转数字发生在常量侧，数字转字符串发生在列侧。
- 追问：`like '%abc'` 有救吗？→ 答题要点：倒序存储 + 前缀匹配、全文索引、或外置搜索引擎，三者按数据量与实时性取舍。
- 追问：`or` 改成 `union all` 有用吗？→ 答题要点：有，`union all` 让两个分支各自用索引再合并，避免整体退化为全表。
- 追问：怎么确认是"失效"还是"优化器主动放弃"？→ 答题要点：看 `possible_keys` 有值但 `key` 为 NULL，且 `rows` 接近全表行数，就是主动放弃。

### Q9. 联合索引的列顺序应该怎么设计？（中级） {#q9}

> 前置：选择性、最左前缀

**一句话结论**：联合索引的列顺序按三条规则定：区分度高的列优先（能最快缩小范围）、等值条件列在前范围条件列在后（范围会截断后续列）、以及尽量让索引覆盖最高频的查询（用覆盖索引消除回表）。同时要控制索引数量，能用 `(a, b)` 覆盖的查询不要再建 `(a)`。

**先把话说白**：联合索引像一张多级排序表，你把哪一列放在第一级，就决定了这张表"按什么聚类"。放错了，索引还在，但用不上；放对了，一条 SQL 从扫十万行变成扫十行。设计索引不是"给每个 where 条件都建一个"，而是"给最高频的查询路径建一条最短的路"。

**底层原理**：

1. **区分度决定第一列。** 区分度（selectivity）= 不重复值个数 / 总行数，越接近 1 越好。第一列区分度低（如性别、状态），过滤后还剩一半数据，后续列再精确也没意义。所以 `(user_id, status)` 通常优于 `(status, user_id)`。例外：如果某个低区分度列是**几乎所有查询都带**的条件，把它放前面可以复用同一条索引服务多个查询，这是一种折中。

2. **等值在前，范围在后。** `(a, b)` 上执行 `where a = 1 and b > 5`，a 定位、b 范围，两列都用上。反过来 `where a > 1 and b = 5`，a 是范围导致 b 无法定位，只能过滤。所以设计时要把"总是等值"的列放前，"可能范围"的列放后。

3. **排序与分组也要吃进索引。** `where a = 1 order by b` 要求索引是 `(a, b)` 才能免排序。若索引是 `(b, a)`，虽能过滤 a，但 b 在结果中不保证有序，仍需 filesort。这是"索引要同时服务 where 和 order by"的典型场景。

4. **前缀复用，避免冗余索引。** `(a, b, c)` 已经能服务 `where a`、`where a,b`、`where a,b,c`，再建 `(a)` 和 `(a,b)` 是纯浪费，只增加写放大。判断标准：新索引是否是已有索引的**最左前缀**，若是则不建。反之 `(b, a)` 不能被 `(a, b)` 替代，因为最左列不同。

5. **覆盖索引优先。** 若某条查询极高频且只需 3~4 个列，可以把这些列做成联合索引，让查询全程不回表。代价是索引变大、写入变慢，所以只对**最高频的 1~2 条**查询做，不能滥用。

6. **控制数量的硬约束。** 单表索引数建议不超过 5~6 个。每多一个索引，每次 insert 多一次 B+ 树维护（虽然有 change buffer 缓冲），每次 update 若涉及索引列还要额外维护；更重要的是优化器要在更多计划中做选择，选错的概率上升。

```sql
-- 订单表高频查询：
-- 1) 按用户查最近订单：where user_id = ? order by create_time desc limit 20
-- 2) 按状态扫超时订单：where status = 1 and create_time < ?
-- 3) 按订单号查详情：where order_no = ?

-- 推荐：
ALTER TABLE orders ADD INDEX idx_user_time (user_id, create_time);  -- 服务 1，且免排序
ALTER TABLE orders ADD INDEX idx_status_time (status, create_time);  -- 服务 2
ALTER TABLE orders ADD UNIQUE INDEX uk_order_no (order_no);          -- 服务 3，唯一约束顺便
-- 注意：不要再建 (user_id)，它是 idx_user_time 的最左前缀
```

**面试追问**：
- 追问：`(a, b)` 和 `(b, a)` 有什么区别？→ 答题要点：最左列不同，能服务的查询不同；`where a=? and b=?` 两者都能用，但 `where a=?` 只有前者能用。
- 追问：区分度低的状态列还有必要建索引吗？→ 答题要点：单列意义不大，但作为联合索引的后置列配合高区分度列仍有效。
- 追问：索引是不是越多越好？→ 答题要点：不是，写放大、空间、优化器选择空间变大，通常控制在 5 个以内。
- 追问：怎么找出无用索引？→ 答题要点：`sys.schema_unused_indexes` 视图（需开启 `performance_schema`），结合业务慢日志交叉验证。

### Q10. 主键为什么建议自增？用 UUID 会有什么问题？（中级） {#q10}

> 前置：聚簇索引、页分裂、随机写

**一句话结论**：自增主键保证新记录总是追加到 B+ 树最右侧的叶子页，页填充率高、几乎不发生页分裂；UUID 是随机值，插入位置随机，会频繁触发页分裂与页合并，导致页利用率下降、索引体积膨胀，且 UUID 作为字符串比较更慢、作为二级索引的"主键指针"会让所有二级索引一起变大。

**先把话说白**：B+ 树的叶子页像一本按页码排好的活页本。你总往最后加页，本子始终是满的、整齐的；你要是随机往中间插，每次插满一页就得撕成两半，长久下来本子里到处是半空的页，翻起来费劲、占地方还多。UUID 就是那个"随机往中间插"的人。

**底层原理**：

1. **顺序插入的行为。** 自增主键总是最大的值，B+ 树只需定位到最右叶子页追加。页写满后申请新页，页与页之间物理上大致连续，页内填充率接近 100%，顺序写对磁盘友好。

2. **随机插入的行为。** UUID 主键落到随机位置。目标页满了就要**页分裂**：把一半记录挪到新页，并调整父节点指针。分裂后两个页的填充率都只有约 50%，且新页在物理上不与原页相邻，形成**碎片**。持续随机插入会让整棵树长期处于低填充率状态，同样的数据量占用更多页，Buffer Pool 能缓存的记录数变少，间接拖慢所有查询。

3. **页合并也会来凑热闹。** 删除记录后页利用率过低时，InnoDB 会尝试把相邻页合并，合并又涉及指针调整与锁，是另一种开销。随机主键 + 频繁删除的表，分裂与合并会反复发生。

4. **UUID 的连带成本。** 一是长度，36 字符（含连字符）的 char(36) 或 16 字节的 binary(16)，比 bigint 的 8 字节大 2~4 倍；二是**所有二级索引的叶子都要存主键值**，主键变长意味着每个二级索引都变大，Buffer Pool 命中率整体下降；三是字符串比较比整数比较慢，且 UUID 的字符串形式对索引不友好（若用 binary(16) 可缓解）。

5. **UUID 的真实价值。** 它能在**分布式环境无协调地生成全局唯一 ID**、不泄露数据量、方便数据合并与迁移。所以不是不能用，而是要用对方式：MySQL 8.0 提供 `UUID_TO_BIN(uuid, 1)`，把 UUID 的时间低位调到前面，使其具备时间有序性，从而恢复顺序插入特性；或者改用雪花算法（Snowflake）这类"趋势递增"的 64 位 ID。

```sql
-- 8.0 的有序 UUID：第二个参数 1 表示交换时间高低位，让 UUID 按时间递增
INSERT INTO t (id, name)
VALUES (UUID_TO_BIN(UUID(), 1), 'a');
-- 主键列定义为 BINARY(16)，既保持唯一性又恢复顺序性
```

**易混对比**：

| 主键类型 | 长度 | 插入模式 | 页分裂 | 分布式唯一 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| `bigint` 自增 | 8 字节 | 顺序追加 | 极少 | 否 | 单库单表，绝大多数业务 |
| `binary(16)` UUID v1（重排） | 16 字节 | 趋势递增 | 少 | 是 | 需要分布式 ID 且想保留顺序性 |
| `char(36)` UUID v4 | 36 字节 | 完全随机 | 频繁 | 是 | 不推荐做主键，可作业务唯一键 |
| Snowflake | 8 字节 | 趋势递增 | 极少 | 是 | 分库分表场景的主流选择 |

**面试追问**：
- 追问：自增主键用完了怎么办？→ 答题要点：`bigint unsigned` 实际不可能用完；`int` 约 21 亿，用尽后插入报错，扩容需改类型（大表 DDL 风险高）。
- 追问：自增主键会不会泄露业务量？→ 答题要点：会，竞品可通过 ID 增长估算订单量，对外接口应使用独立的业务编号。
- 追问：分库分表后自增主键还能用吗？→ 答题要点：不能直接用，需按步长分段（如每库起始值不同、步长为库数）或改用 Snowflake。
- 追问：为什么二级索引要存主键而不是物理地址？→ 答题要点：物理地址会因页分裂变化，存主键更稳定，代价是回表需要再查一次聚簇索引。

### Q11. 索引有什么代价？优化器为什么会选错索引？（高级） {#q11}

> 前置：优化器、统计信息、回表成本

**一句话结论**：索引的代价有三块：写入时的维护成本（写放大）、磁盘与内存空间占用、以及给优化器带来的选择难度。优化器选错索引的根因是**统计信息不准**（采样估算的 rows 与实际偏差大）和**代价模型不完整**（不感知 Buffer Pool 命中率、并发与数据倾斜），常用 `ANALYZE TABLE`、`FORCE INDEX`、`optimizer trace` 应对。

**先把话说白**：索引不是免费的加速器，它是"用写入变慢、空间变大"换"读取变快"。所以索引设计本质是一道权衡题。而"选错索引"更微妙：优化器不是笨，是它拿到的信息不全——它只知道"大概有多少行"，不知道"这些页是不是已经在内存里"。

**底层原理**：

1. **写放大。** 一次 insert 要维护聚簇索引 + 每个二级索引，每个索引都是一次 B+ 树定位与插入。虽然有 change buffer 缓冲非唯一二级索引的随机写，但唯一索引、主键索引无法缓冲。一次 update 若修改了索引列，等于"删旧记录 + 插新记录"两套操作。

2. **空间成本。** 索引本身占磁盘，也占 Buffer Pool。索引越多，能缓存的数据页越少，可能反过来让原本能命中的查询开始读盘。这是一种"看不见的负反馈"。

3. **统计信息是怎么来的。** InnoDB 默认开启持久化统计（`innodb_stats_persistent=ON`），通过随机采样 `innodb_stats_persistent_sample_pages`（默认 20）个页来估算 `cardinality`（不重复值个数）与行数。20 个页相对于千万行的表是极小的样本，数据分布倾斜时误差会很大。`innodb_stats_auto_recalc` 控制是否在数据变化超过 10% 时自动重算。

4. **代价模型怎么算。** 走索引的代价 ≈ 扫描索引的页数 × IO 代价 + 回表行数 × 回表代价 + 比较的 CPU 代价；全表扫描的代价 ≈ 聚簇索引页数 × IO 代价（且顺序读有折扣）。关键在"回表行数"这一项：若估算需要回表 30 万行，而表总共 100 万行，优化器会认为全表顺序扫描更便宜。

5. **典型的选错场景。** 一是数据倾斜：某列 99% 的值都相同，优化器却按平均值估算；二是范围查询估算偏差：`between` 的选择性估算用经验公式，与实际差很远；三是 `limit` 场景：`order by ... limit 10` 若走错索引会导致大量排序；四是刚做完大批量导入，统计信息未更新。

6. **应对手段的区别。** `ANALYZE TABLE` 是重新采样统计信息，治本但会短暂加锁（8.0 改为轻量）；`FORCE INDEX` 是强制指定，治标且硬编码，索引改名或删除后 SQL 直接报错；`optimizer trace` 是诊断工具，能看到每个候选计划的 cost，用来判断"到底是估算错了还是代价模型不适用"。优先顺序应该是：先 trace 定位 → 再 analyze → 最后才 force index。

```sql
-- 1. 看优化器考虑了哪些索引、每个计划的代价
SET optimizer_trace='enabled=on';
SELECT * FROM orders WHERE status = 1 AND user_id = 100;
SELECT trace FROM information_schema.optimizer_trace\G

-- 2. 重新采样统计信息
ANALYZE TABLE orders;

-- 3. 确认索引基数（越接近行数说明区分度越高）
SHOW INDEX FROM orders;

-- 4. 最后手段：强制索引（需评估后续索引变更风险）
SELECT * FROM orders FORCE INDEX(idx_status_time) WHERE status = 1;
```

**面试追问**：
- 追问：`ANALYZE TABLE` 为什么有时没用？→ 答题要点：采样仍有误差，且若问题是代价模型不感知缓存状态，重算统计也解决不了。
- 追问：`FORCE INDEX` 有什么风险？→ 答题要点：硬编码索引名，索引调整后 SQL 报错；且数据分布变化后可能反而更慢。
- 追问：为什么 `cardinality` 每次看都不一样？→ 答题要点：它是采样估算值，不是精确值，采样页不同结果就不同。
- 追问：联合索引的 `cardinality` 怎么理解？→ 答题要点：是联合列组合的不重复值个数，通常接近总行数，参考价值有限。

### Q12. 前缀索引怎么用？索引选择性怎么算？（中级） {#q12}

> 前置：选择性、覆盖索引限制

**一句话结论**：前缀索引是对长字符串列只取前 N 个字符建索引（`INDEX(col(N))`），用较小的空间换取可用的索引加速；N 的选取标准是"前缀的选择性接近整列选择性"，通常要求 `count(distinct left(col, N)) / count(*)` 达到 0.9 以上。代价是前缀索引无法用于覆盖索引、无法用于 `order by` / `group by`，且必须回表校验完整值。

**先把话说白**：一个 URL 有 200 个字符，但前 20 个字符往往就足以区分大部分记录。全字段建索引，索引比数据还大；只取前 20 个字符，体积降到十分之一，查询照样能快速缩小范围——代价是找到候选后还得回表看一眼完整值是否真的相等。

**底层原理**：

1. **选择性（selectivity）的定义。** `count(distinct col) / count(*)`，取值 0~1，越接近 1 说明该列越能区分记录。索引的价值正比于选择性：选择性为 0.01 的列（如性别）建索引，过滤后仍有 50% 数据，几乎无用。

2. **怎么定前缀长度。** 从小到大试 N，计算 `count(distinct left(col, N)) / count(*)`，取第一个达到目标（如 0.9~0.95）的 N。也可以用 `sum(left(col,N) = col) / count(*)` 看前缀完整匹配的比例。

3. **前缀索引的三个限制。** 一是**不能覆盖索引**：索引里只有前缀，没有完整值，必须回表取完整列才能返回结果，所以 `Using index` 用不上；二是**不能用于排序与分组**：索引里存的是前缀，前缀有序不代表完整值有序；三是**区分度可能不足**：若数据前缀高度重复（如带统一域名的 URL），前缀索引退化严重。

4. **替代方案。** 对超长列可用"倒序存储 + 前缀索引"（解决后缀匹配）、"额外加一列存 hash 值 + 对该列建索引"（`crc32` 或 `md5` 前 8 位，查询时 `where url_hash = ? and url = ?`）。hash 列方案能精确命中且索引小，代价是多一列维护成本与 hash 冲突处理（所以必须再带原列等值条件）。

5. **`cardinality` 与实际选择性的差别。** `SHOW INDEX` 里的 `cardinality` 是采样估算值，用于优化器决策；而你自己算的选择性是精确值，用于设计索引。两者用途不同，不要混为一谈。

```sql
-- 试探前缀长度：找出区分度达标的 N
SELECT
  COUNT(DISTINCT LEFT(url, 10)) / COUNT(*) AS sel10,
  COUNT(DISTINCT LEFT(url, 20)) / COUNT(*) AS sel20,
  COUNT(DISTINCT LEFT(url, 30)) / COUNT(*) AS sel30,
  COUNT(DISTINCT url) / COUNT(*)           AS sel_full
FROM page_visit;

-- 建前缀索引
ALTER TABLE page_visit ADD INDEX idx_url_prefix (url(20));

-- 更稳的方案：hash 列 + 完整值校验
ALTER TABLE page_visit ADD COLUMN url_hash BIGINT UNSIGNED,
  ADD INDEX idx_url_hash (url_hash);
SELECT * FROM page_visit WHERE url_hash = CRC32(?) AND url = ?;
```

**面试追问**：
- 追问：前缀索引能用在 `order by url` 上吗？→ 答题要点：不能，索引里是前缀，前缀有序不保证完整值有序。
- 追问：为什么前缀索引不能覆盖索引？→ 答题要点：索引中没有完整列值，返回结果必须回表取。
- 追问：hash 列方案有什么坑？→ 答题要点：hash 冲突需带原列等值条件、范围查询完全失效、多一次写入维护。
- 追问：`cardinality` 很小说明什么？→ 答题要点：区分度低，优化器会低估索引价值，可能放弃使用。

### Q13. ACID 分别靠什么实现？（初级） {#q13}

> 前置：原子性、一致性、隔离性、持久性

**一句话结论**：原子性（Atomicity）靠 undo log 反向回滚；持久性（Durability）靠 redo log 与刷盘参数；隔离性（Isolation）靠锁与 MVCC；一致性（Consistency）是最终目标，由数据库约束（主键、唯一、外键、check）与业务代码共同保证，不是某一个机制单独实现的。

**先把话说白**：ACID 里最容易被误解的是 C。A、I、D 都是数据库提供的**手段**，而 C 是这些手段加上业务约束共同达成的**结果**。转账场景里"两边总额不变"这条规则，数据库根本不知道，是业务代码保证的。所以面试时把 C 说成"靠某种机制实现"会被追问到答不上来。

**底层原理**：

1. **原子性。** 事务中每一步修改都先写 undo log，记录反向操作。回滚时逆序执行 undo。若事务执行到一半崩溃，恢复阶段也会用 undo 回滚未提交的事务。因此"要么全做要么全不做"的底层依据是"每一步都能被撤销"。

2. **持久性。** 修改先在内存完成，redo log 落盘即视为提交成功。崩溃后按 redo 前滚，把已提交但未刷页的修改重放。真正的保证强度取决于 `innodb_flush_log_at_trx_commit`：设为 1 才是"提交即落盘"，设为 0 或 2 都存在丢失窗口。

3. **隔离性。** 写写冲突靠锁（行锁、间隙锁），读写冲突靠 MVCC（快照读不加锁）。隔离级别的强弱本质上是"锁的范围"与"快照的新旧"两个维度的调节。

4. **一致性。** 分两层：数据库层的主键唯一、非空、外键、`check` 约束保证"数据不违反声明的规则"；业务层的一致性（如库存不能为负、账户借贷平衡）必须由代码或分布式事务保证。数据库能做的只是"不让你写出违反约束的数据"，不能替你保证业务语义。

**易混对比**：

| 特性 | 实现手段 | 失效场景 |
| --- | --- | --- |
| 原子性 A | undo log 反向回滚 | 事务过大导致回滚极慢，但语义不失效 |
| 持久性 D | redo log + `innodb_flush_log_at_trx_commit=1` | 参数调成 0/2 时断电丢最后约 1 秒 |
| 隔离性 I | 行锁、间隙锁、MVCC | 隔离级别设为 RU，或业务代码跨事务读 |
| 一致性 C | 约束 + 业务逻辑 + 分布式事务 | 业务校验缺失，如超卖、余额为负 |

**面试追问**：
- 追问：如果 redo 已经落盘但页没刷，算不算持久化成功？→ 答题要点：算，redo 落盘即可恢复；页由后台异步刷。
- 追问：一致性是数据库保证的吗？→ 答题要点：不是全部，约束保证结构一致，业务语义一致性必须业务保证。
- 追问：隔离性为什么不完全靠锁？→ 答题要点：全用锁会导致读写互相阻塞，MVCC 让读不加锁，提升并发。

### Q14. 四种隔离级别分别解决什么问题？MySQL 为什么默认 RR？（初级） {#q14}

> 前置：脏读、不可重复读、幻读

**一句话结论**：读未提交（RU）允许脏读；读已提交（RC）解决脏读但存在不可重复读；可重复读（RR）解决不可重复读，并通过间隙锁在多数场景下抑制幻读；串行化（Serializable）全部解决但并发最差。InnoDB 默认 RR，历史原因是 statement 格式的 binlog 在 RC 下会导致主从不一致，同时 RR 在 MVCC 加持下读不加锁、开销可接受。

**先把话说白**：三种"读异常"的差别在于"你读到的数据在事务期间会不会变"：脏读是读到了别人还没提交的（可能马上回滚）；不可重复读是同一条记录两次读不一样；幻读是同一范围两次读，行数变了。级别越高，看到的"变化"越少，代价是并发越差。

**底层原理**：

1. **脏读。** 事务 A 修改了某行但未提交，事务 B 读到了这个未提交的值。若 A 回滚，B 读到的就是从未存在过的数据。RU 级别允许这种情况，实际业务几乎不用。

2. **不可重复读。** 事务 A 内两次读同一行，中间事务 B 提交了更新，导致两次结果不同。RC 级别下每次快照读都生成新的 ReadView，所以能看到别人新提交的数据。

3. **幻读。** 事务 A 内两次执行同一范围查询，中间事务 B 插入了一行并提交，第二次多出一行。注意幻读针对的是"行数变化"，不可重复读针对的是"同一行的值变化"。

4. **RR 如何抑制幻读。** 快照读通过 MVCC 保证整个事务看到同一个 ReadView，新插入的行事务 ID 大于快照，不可见；当前读通过临键锁（Next-Key Lock）锁住范围间隙，让别的事务插不进来。

5. **默认 RR 的历史原因。** MySQL 5.0 之前 binlog 只支持 `STATEMENT` 格式，记录的是 SQL 原文。RC 下事务 A 先 `delete where c=1` 再 `insert`，事务 B 在此期间提交了另一条 `c=1` 的记录，从库按相同顺序重放会得到不同结果。RR 加间隙锁能保证可串行化，从而让 statement 复制安全。5.1 引入 `ROW` 格式后这个理由不再必要，但默认值因兼容性保留至今。

6. **互联网公司为什么改成 RC。** RC 没有间隙锁（除唯一键冲突检查与外键检查），锁冲突大幅减少，死锁概率下降；配合 `ROW` 格式 binlog 也不会有主从不一致。代价是同一事务内多次读可能不一致，需要业务接受。所以"默认 RR"与"生产用 RC"并不矛盾，取决于是否需要事务内强一致快照。

**易混对比**：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 读是否加锁 | ReadView 生成时机 |
| --- | --- | --- | --- | --- | --- |
| 读未提交 RU | 可能 | 可能 | 可能 | 不加 | 不生成（直接读最新） |
| 读已提交 RC | 不会 | 可能 | 可能 | 快照读不加 | 每次快照读都生成 |
| 可重复读 RR | 不会 | 不会 | 多数场景不会 | 快照读不加，当前读加间隙锁 | 事务内首次快照读生成一次 |
| 串行化 | 不会 | 不会 | 不会 | 所有读加共享锁 | 不需要（全靠锁） |

**面试追问**：
- 追问：RC 下还会有间隙锁吗？→ 答题要点：基本没有，但外键检查与唯一键冲突检查仍会加间隙锁。
- 追问：RR 下把 `binlog_format` 设为 `ROW`，还会不会有主从不一致？→ 答题要点：行格式记录实际变更，重放结果确定，不会因执行顺序不同而不一致。
- 追问：为什么互联网业务常选 RC？→ 答题要点：减少间隙锁与死锁、提升并发；用 ROW 格式保证复制安全。
- 追问：Serializable 是怎么实现的？→ 答题要点：所有普通 select 隐式加 `lock in share mode`，读写全阻塞，并发极差。

### Q15. MVCC 是怎么实现的？RC 与 RR 的 ReadView 差别在哪？（高级） {#q15}

> 前置：undo 版本链、ReadView、可见性

**一句话结论**：MVCC（Multi-Version Concurrency Control，多版本并发控制）通过三个隐藏字段（`DB_TRX_ID`、`DB_ROLL_PTR`、`DB_ROW_ID`）、undo log 版本链和 ReadView 三部分实现：读操作按 ReadView 的可见性规则沿版本链找到第一个可见版本，从而在不加锁的情况下读到一致快照。RC 每次快照读都新建 ReadView，RR 只在事务内第一次快照读时创建并复用。

**先把话说白**：MVCC 的核心思路是"不改旧数据，只追加新版本"。每次更新都留下一份旧值在 undo 里，用指针串成链。你读的时候，数据库拿一个"时间戳清单"（ReadView）判断"这个版本对我可见吗"，从新到旧找第一个可见的，就返回它。这样读的人看自己的历史，写的人写自己的新版本，互不阻塞。

**底层原理**：

1. **三个隐藏字段。** `DB_TRX_ID`（6 字节）记录最后一次修改该行的事务 ID；`DB_ROLL_PTR`（7 字节）指向 undo log 中的上一个版本；`DB_ROW_ID`（6 字节）在无主键时作为隐式主键。这三个字段用户看不到，但 `select *` 的实际读取会带上。

2. **版本链的形成。** 每次 update 都把旧值写入 undo，新行的 `DB_ROLL_PTR` 指向这条 undo 记录，undo 记录里又有指针指向上一个版本。于是形成一条从新到旧的单向链表，链表头是当前行。purge 线程会在没有事务需要这些旧版本时清理掉链尾。

3. **ReadView 的四个字段。** `m_ids`：创建 ReadView 时**活跃（未提交）**的事务 ID 列表；`min_trx_id`：`m_ids` 中的最小值；`max_trx_id`：创建时系统应分配的**下一个**事务 ID（不是当前最大已分配 ID）；`creator_trx_id`：创建该 ReadView 的事务自己的 ID。

4. **可见性判断规则（按顺序）。** 对版本链上某个版本的 `trx_id`：
   - 若 `trx_id == creator_trx_id`，说明是自己改的，**可见**。
   - 若 `trx_id < min_trx_id`，说明该事务在 ReadView 创建前已提交，**可见**。
   - 若 `trx_id >= max_trx_id`，说明该事务在 ReadView 创建后才开启，**不可见**。
   - 若 `min_trx_id <= trx_id < max_trx_id`：在 `m_ids` 中则说明创建时还活跃（未提交），**不可见**；不在 `m_ids` 中则说明已提交，**可见**。
   - 不可见就顺着 `DB_ROLL_PTR` 找下一个版本，重复直到找到可见版本或链结束（链结束说明该行对当前事务不可见，返回"不存在"）。

5. **RC 与 RR 的差别只在一处。** RC 每次执行快照读都重新生成 ReadView，所以能看到期间其他事务新提交的数据（不可重复读）；RR 在事务内第一次快照读时生成一次，后续所有快照读复用，所以整个事务看到同一份快照（可重复读）。注意 RR 的 ReadView 不是 `begin` 时创建的，是**第一次 select 时**创建——这意味着 `begin` 之后、第一次 select 之前别人提交的数据仍然可见，这个细节常被用来区分"背过"和"懂了"。

6. **MVCC 只对快照读生效。** `select ... for update`、`lock in share mode`、`update`、`delete`、`insert` 都是当前读，读最新已提交版本并加锁，不受 ReadView 约束。

```text
行记录: [DB_TRX_ID=100][DB_ROLL_PTR]──┐
                                      ↓
        undo: [旧值 v2][trx_id=90][ptr]──┐
                                        ↓
              undo: [旧值 v1][trx_id=80][ptr]──→ 更早版本

ReadView(m_ids=[95,100], min=95, max=101, creator=102)
读该行: trx_id=100 在 m_ids 中 → 不可见 → 顺链取 90
        90 < 95 → 可见 → 返回 v2
```

**易混对比**：

| 维度 | RC（读已提交） | RR（可重复读） |
| --- | --- | --- |
| ReadView 创建时机 | 每次快照读都创建 | 事务内首次快照读创建一次 |
| 事务内多次读 | 可能不同（不可重复读） | 始终一致 |
| 能否看到期间新提交数据 | 能 | 不能 |
| 间隙锁 | 基本不用 | 当前读时使用 |
| 适用场景 | 高并发、可接受读不一致 | 需要事务内稳定快照 |
| binlog 格式要求 | 必须 `ROW` | `STATEMENT` 亦可 |

**面试追问**：
- 追问：`begin` 之后立刻 `select` 和隔 10 秒再 `select`，看到的快照一样吗？→ 答题要点：RR 下取决于第一次 select 的时刻，`begin` 本身不生成 ReadView。
- 追问：`max_trx_id` 是当前最大事务 ID 吗？→ 答题要点：不是，是"下一个将被分配"的 ID，所以判断用 `>=`。
- 追问：undo 版本链会无限增长吗？→ 答题要点：不会，purge 线程清理无引用版本；但长事务会阻止清理，导致 undo 膨胀。
- 追问：MVCC 能解决写写冲突吗？→ 答题要点：不能，写写冲突必须靠锁，MVCC 只解决读写冲突。

### Q16. 快照读与当前读有什么区别？RR 真的解决了幻读吗？（高级） {#q16}

> 前置：MVCC、间隙锁、幻读

**一句话结论**：快照读（普通 `select`）读的是 MVCC 生成的可见版本，不加锁；当前读（`select ... for update`、`lock in share mode`、`update`、`delete`、`insert`）读最新已提交版本并加锁。RR 下快照读靠 ReadView 抑制幻读、当前读靠临键锁抑制幻读，但两者**混用**时仍会出现幻读——这是 InnoDB 的 RR 没有完全消灭幻读的根本原因。

**先把话说白**：快照读像看一份打印好的报表，别人后加的数据你看不到；当前读像现场去数，看到的是此刻真实的状态，并且会拦住别人不让他动。问题在于：你先看报表（快照读），再按报表去改（当前读变成现场数），这两次看到的世界可能不一样，于是"幻觉"就出现了。

**底层原理**：

1. **两种读的语义。** 快照读返回事务可见的历史版本，不加任何锁，所以并发高；当前读必须读最新已提交数据，并加锁防止别人修改，所以是阻塞的来源。

2. **哪些语句是当前读。** `select ... for update`（加 X 锁）、`select ... lock in share mode`（加 S 锁）、`update`、`delete`、`insert`（`insert` 加插入意向锁）。注意 `update` 的 where 条件即使没写 `for update`，它也是当前读。

3. **RR 抑制幻读的两条路径。** 路径一：快照读。整个事务复用同一个 ReadView，期间别人插入的行 `trx_id >= max_trx_id`，不可见，所以"看起来没有幻影"。路径二：当前读。临键锁锁住索引区间与间隙，别人的 insert 需要插入意向锁，与间隙锁冲突，被阻塞。

4. **为什么仍会出现幻读。** 经典场景：事务 A 先快照读 `select * from t where id > 10`（看到 3 行），事务 B 插入 `id=11` 并提交，事务 A 再执行 `update t set flag=1 where id > 10`。这个 update 是当前读，会看到 B 插入的那一行并修改它（此时这行的 `trx_id` 变成了 A 自己的 ID），随后 A 再快照读 `select * from t where id > 10`，就会看到 4 行——幻影出现了。原因是"当前读修改过的行，其 `trx_id` 变成自己，按规则对自己可见"。

5. **另一个常见场景。** 事务 A 快照读没看到某行，于是 `insert` 该行，若该行已被 B 插入并提交，A 会遇到主键冲突或唯一键冲突——这也是幻读的一种表现形式（"我以为没有，其实有"）。

6. **实践结论。** 需要严格串行语义时，应使用 `select ... for update` 从一开始就走当前读并加锁，而不是靠"快照读 + 后续 update"的组合。同时要清楚：间隙锁只在 RR 下生效，若隔离级别是 RC，当前读的幻读完全依赖业务自己保证。

```sql
-- 会话 A
BEGIN;
SELECT * FROM t WHERE id > 10;            -- 快照读，看到 3 行
-- 会话 B: INSERT INTO t(id, flag) VALUES (11, 0); COMMIT;
UPDATE t SET flag = 1 WHERE id > 10;      -- 当前读，实际改了 4 行（含 id=11）
SELECT * FROM t WHERE id > 10;            -- 快照读，看到 4 行 —— 幻影出现
COMMIT;
```

**易混对比**：

| 维度 | 快照读 | 当前读 |
| --- | --- | --- |
| 典型语句 | 普通 `select` | `for update`、`lock in share mode`、`update`、`delete`、`insert` |
| 读哪个版本 | ReadView 判定的可见版本 | 最新已提交版本 |
| 是否加锁 | 不加 | 加 S 锁或 X 锁 |
| 幻读防护 | ReadView（RR 复用、RC 每次新建） | 临键锁（仅 RR） |
| 阻塞他人 | 不阻塞 | 阻塞 |
| 能否读到本事务未提交修改 | 能（creator_trx_id 规则） | 能 |

**面试追问**：
- 追问：为什么"快照读 + update"会看到幻影？→ 答题要点：update 是当前读，改了别人的新行后该行 `trx_id` 变为自己，之后快照读对它可见。
- 追问：RC 下有幻读吗？→ 答题要点：有，RC 每次新建 ReadView 且无间隙锁，快照读和当前读都挡不住。
- 追问：如何彻底避免幻读？→ 答题要点：一开始就用 `for update` 加锁走当前读，或用 Serializable，或业务层用唯一约束兜底。
- 追问：`select ... for update` 在没走索引时会怎样？→ 答题要点：全表扫描并对所有行加锁，等于锁表，必须避免。

### Q17. 一条 SQL 到底加了什么锁？（高级） {#q17}

> 前置：索引、行锁、间隙锁、Next-Key Lock

**一句话结论**：InnoDB 的行级锁加在**索引**上，加锁范围由"走的哪个索引、是等值还是范围、是否命中记录、索引是否唯一"共同决定：唯一索引等值命中退化为记录锁（Record Lock）；唯一索引等值未命中加间隙锁（Gap Lock）；非唯一索引等值与范围查询加临键锁（Next-Key Lock），并向右扫描到第一个不满足条件的值为止。

**先把话说白**：很多人背"行锁、间隙锁、临键锁"的定义，一到具体 SQL 就答不出。真正的方法只有一条：**先确定走哪个索引，再确定扫描区间，最后按规则判断区间的开闭**。间隙锁锁的是"两条记录之间的空隙"，临键锁是"记录 + 它前面的间隙"，所以临键锁的区间总是左开右闭。

**底层原理**：

准备一张表和固定数据，后面所有推导都基于它：

```sql
CREATE TABLE t (
  id INT PRIMARY KEY,
  c  INT,
  d  INT,
  KEY idx_c (c)
) ENGINE=InnoDB;

INSERT INTO t VALUES (0,0,0),(5,5,5),(10,10,10),(15,15,15),(20,20,20),(25,25,25);
```

索引上的间隙有：`(-∞,0)`、`(0,5)`、`(5,10)`、`(10,15)`、`(15,20)`、`(20,25)`、`(25,+∞)`。

1. **规则一：唯一索引等值命中 → 记录锁。** `SELECT * FROM t WHERE id = 10 FOR UPDATE;` 主键唯一，等值命中后不需要防插入（唯一性已由主键保证），临键锁退化为记录锁，只锁 `id=10` 这一行。区间：`[10,10]`。

2. **规则二：唯一索引等值未命中 → 间隙锁。** `SELECT * FROM t WHERE id = 7 FOR UPDATE;` 7 不存在，锁住它可能落入的间隙 `(5,10)`。注意间隙锁之间**互不冲突**，两个事务可以同时持有同一个间隙锁，这是死锁的常见来源。

3. **规则三：非唯一索引等值 → 临键锁 + 间隙锁。** `SELECT * FROM t WHERE c = 10 FOR UPDATE;` 先按 idx_c 找到 c=10 的记录，加临键锁 `(5,10]`；因为 c 不唯一，还要继续向右扫描，直到第一个不满足 c=10 的值（c=15），对其加间隙锁 `(10,15)`。合起来是 `(5,15)`。同时要对聚簇索引上对应的主键行加记录锁（回表加锁）。

4. **规则四：非唯一索引等值未命中 → 间隙锁。** `SELECT * FROM t WHERE c = 12 FOR UPDATE;` 12 不存在，落在 `(10,15)` 间隙，只加间隙锁 `(10,15)`。

5. **规则五：范围查询 → 临键锁，扫到第一个不满足的为止。** `SELECT * FROM t WHERE id >= 10 AND id < 15 FOR UPDATE;` 主键范围扫描，锁 `(10,15)` 这个临键区间（左开右闭：包含 15 之前的间隙，不含 15 本身？实际是锁住 `[10,15)` 对应的临键，从 10 开始向右直到 15 前）。规范说法：锁住 `(5,10]` 之后到 `(10,15]` 之前，即区间 `[10,15)`，不含 15 之后的间隙。

6. **规则六：非唯一索引范围 → 多个临键锁。** `SELECT * FROM t WHERE c >= 10 AND c < 15 FOR UPDATE;` 沿 idx_c 扫描，锁 `(5,10]`、`(10,15]`，即 `(5,15]`。注意右端包含 15（因为临键锁右闭），这是很多人漏掉的一点。

**加锁规则速查表**：

| 查询条件 | 索引类型 | 是否命中 | 加锁结果 |
| --- | --- | --- | --- |
| `id = 10` | 主键（唯一） | 命中 | 记录锁 `[10,10]` |
| `id = 7` | 主键（唯一） | 未命中 | 间隙锁 `(5,10)` |
| `id >= 10 and id < 15` | 主键 | 范围 | 临键锁，区间约 `[10,15)` |
| `c = 10` | 普通索引 | 命中 | 临键锁 `(5,10]` + 间隙 `(10,15)` = `(5,15)` |
| `c = 12` | 普通索引 | 未命中 | 间隙锁 `(10,15)` |
| `c >= 10 and c < 15` | 普通索引 | 范围 | 临键锁 `(5,10]` + `(10,15]` = `(5,15]` |
| `d = 10` | 无索引 | — | 全表扫描，所有行加锁（等效锁表） |

7. **两个必须记住的边界。** 第一，**加锁加在索引上**，若 where 条件用的列没有索引，InnoDB 会扫描聚簇索引并对每一行加锁，效果等同锁表。第二，**RC 隔离级别下没有间隙锁**（外键与唯一键冲突检查除外），所以同样的 SQL 在 RC 下锁范围小得多，这也是 RC 死锁更少的原因。

8. **插入意向锁（Insert Intention Lock）。** 执行 insert 时，若目标间隙上已有间隙锁，insert 会生成插入意向锁并等待。插入意向锁是一种特殊的间隙锁，多个插入意向锁之间不冲突（不同位置的插入可以并发），但与间隙锁冲突。这就是"间隙锁导致 insert 被阻塞"的机制。

```sql
-- 复现间隙锁阻塞 insert
-- 会话 A
BEGIN;
SELECT * FROM t WHERE id = 7 FOR UPDATE;      -- 持有间隙锁 (5,10)
-- 会话 B
INSERT INTO t VALUES (8, 8, 8);                -- 阻塞，等待插入意向锁
-- 会话 A 提交后 B 才继续
```

**面试追问**：
- 追问：为什么唯一索引等值命中可以退化为记录锁？→ 答题要点：唯一性保证不会有第二行同值，无需防插入，锁住记录本身即可。
- 追问：两个事务都对同一间隙加间隙锁会冲突吗？→ 答题要点：不冲突，间隙锁的作用是"阻止插入"，彼此不互斥，这是死锁的经典成因。
- 追问：`select ... for update` 没走索引会怎样？→ 答题要点：全表扫描逐行加锁，等效锁表，必须避免。
- 追问：怎么验证加了哪些锁？→ 答题要点：MySQL 8.0 查 `performance_schema.data_locks` 与 `data_lock_waits`；5.7 查 `information_schema.innodb_locks`。

### Q18. 死锁是怎么产生的？怎么排查和避免？（高级） {#q18}

> 前置：锁等待、等待图、`SHOW ENGINE INNODB STATUS`

**一句话结论**：死锁是多个事务以不同顺序持有并等待对方所需的锁，形成循环等待。InnoDB 有死锁检测（`innodb_deadlock_detect` 默认开启），发现后主动回滚代价较小的事务并报 `Deadlock found`。排查看 `SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK` 段，避免手段是固定加锁顺序、缩小事务、减少范围锁、必要时降级到 RC 或加业务重试。

**先把话说白**：死锁不是 bug，是并发系统的必然现象——只要允许多个事务同时持锁并等待，就可能画出环。数据库能做的是"尽快发现并打破环"，而不是"保证不发生"。所以工程上的目标不是消灭死锁，而是让死锁**少发生、快恢复、可观测**。

**底层原理**：

1. **四个必要条件。** 互斥、持有并等待、不可剥夺、循环等待。数据库层面只能打破"循环等待"（靠检测与回滚）和"持有并等待"（靠一次性加锁或缩小事务），前两个是锁机制本身的属性，无法消除。

2. **最常见的三种成因。** 一是**加锁顺序不一致**：事务 A 先锁 id=1 再锁 id=2，事务 B 反过来，必然成环。二是**间隙锁交叉**：两个事务各持有一个间隙锁，再各自插入对方间隙，插入意向锁互相等待。三是**唯一键冲突**：两个事务同时 insert 相同唯一键，其中一个持有 S 锁等待，另一个持有 X 锁等待，形成环。

3. **死锁检测的代价。** `innodb_deadlock_detect=ON` 时，每次加锁等待都要做环路检测，复杂度与事务数相关。高并发下这个检测本身会成为瓶颈，所以有些高并发场景会关闭检测、依赖 `innodb_lock_wait_timeout`（默认 50 秒）超时回滚——代价是响应时间从毫秒级变成秒级，必须配合上游重试。

4. **怎么看死锁日志。** `SHOW ENGINE INNODB STATUS` 输出中的 `LATEST DETECTED DEADLOCK` 段包含：两个事务的 ID、各自执行的最后一条 SQL、各自持有的锁与等待的锁、以及最终被回滚的事务。关键信息是 `HOLDS THE LOCK(S)` 与 `WAITING FOR THIS LOCK TO BE GRANTED`，把两者拼起来就能画出环。

5. **避免的四个层次。** SQL 层：确保 where 走索引，避免范围过大导致锁多行。事务层：缩小事务边界，把非数据库操作（RPC、发消息）移出事务。代码层：对多行更新按固定顺序（如按主键升序）加锁。架构层：热点行用队列串行化、或把扣减改成乐观锁/单行原子更新。

```sql
-- 排查：查看最近的死锁详情
SHOW ENGINE INNODB STATUS\G
-- 关注 LATEST DETECTED DEADLOCK 段

-- 8.0：实时查看锁与等待关系
SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;

-- 5.7：旧视图（8.0 已移除）
SELECT * FROM information_schema.innodb_locks;
SELECT * FROM information_schema.innodb_lock_waits;

-- 查看当前长事务（死锁的常见源头）
SELECT trx_id, trx_state, trx_started, trx_mysql_thread_id, trx_query
FROM information_schema.innodb_trx
ORDER BY trx_started;
```

死锁日志的关键片段形如：

```text
LATEST DETECTED DEADLOCK
------------------------
*** (1) TRANSACTION:
TRANSACTION 1234, ACTIVE 3 sec starting index read
UPDATE account SET balance = balance - 10 WHERE id = 2
*** (1) HOLDS THE LOCK(S):
RECORD LOCKS ... index PRIMARY of table `db`.`account` trx id 1234 lock_mode X
*** (1) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS ... lock_mode X locks rec but not gap waiting
*** (2) TRANSACTION:
TRANSACTION 1235, ACTIVE 2 sec starting index read
UPDATE account SET balance = balance - 10 WHERE id = 1
*** WE ROLL BACK TRANSACTION (1)
```

读法：事务 1 已持有 id=2 的锁、等 id=1；事务 2 反过来。两条 SQL 的 id 顺序相反，就是典型的"加锁顺序不一致"。

**易混对比**：

| 手段 | 作用点 | 代价 | 适用场景 |
| --- | --- | --- | --- |
| 固定加锁顺序 | 打破循环等待 | 需业务配合 | 批量更新、转账 |
| 缩小事务 | 减少持有时间 | 需拆分业务逻辑 | 所有场景 |
| 走索引避免范围锁 | 减少锁行数 | 需索引设计 | 条件更新 |
| 降级 RC | 消除间隙锁 | 失去 RR 快照一致性 | 高并发写入 |
| 关闭死锁检测 | 省 CPU | 退化为 50 秒超时 | 极高并发且能重试 |
| 乐观锁 / 单行原子更新 | 减少锁竞争 | 需处理失败重试 | 库存扣减、计数 |

**面试追问**：
- 追问：死锁后事务会自动重试吗？→ 答题要点：不会，InnoDB 只回滚并抛错，重试必须业务层做，且要限制重试次数。
- 追问：`innodb_lock_wait_timeout` 与死锁检测的关系？→ 答题要点：前者是超时兜底，后者是主动检测；关掉检测后只能靠超时。
- 追问：为什么间隙锁特别容易死锁？→ 答题要点：间隙锁之间不互斥，两个事务可同时持有同一间隙，再各自插入对方间隙就成环。
- 追问：怎么在生产上快速定位死锁？→ 答题要点：开 `innodb_print_all_deadlocks` 把死锁写进错误日志，配合监控告警，不要等出事再去 show status。

### Q19. EXPLAIN 的每个字段怎么看？（中级） {#q19}

> 前置：执行计划、type、key、rows

**一句话结论**：`type` 反映访问方式（性能从好到差：`system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL`），`key` 是实际使用的索引（为 NULL 说明没走索引），`rows` 是估算扫描行数，`filtered` 是过滤后剩余百分比，`Extra` 里 `Using index` 表示覆盖索引、`Using index condition` 表示索引下推、`Using filesort` 表示额外排序、`Using temporary` 表示用了临时表。

**先把话说白**：EXPLAIN 不是"看有没有走索引"这么简单，它回答的是"优化器打算怎么执行"。三个字段最关键：走什么方式（type）、扫多少行（rows）、有没有额外动作（Extra）。看到 `ALL` 加 `Using filesort` 加几十万 rows，基本可以断定这条 SQL 要改。

**底层原理**：

1. **`id` 与执行顺序。** id 越大越先执行；id 相同则从上到下执行。子查询可能生成独立的 id，`UNION` 会产生 `id=NULL` 的临时表行。

2. **`select_type`。** `SIMPLE`（无子查询无 union）、`PRIMARY`（最外层）、`SUBQUERY`（select 列表或 where 中的子查询）、`DERIVED`（from 中的子查询，会物化成临时表）、`UNION`、`UNION RESULT`。`DERIVED` 值得注意：派生表在 5.7 会被物化且无法下推谓词，8.0 引入了 derived condition pushdown 有所改善。

3. **`type` 的等级。** 从好到差：
   - `system`：表只有一行，特殊情况。
   - `const`：主键或唯一索引等值命中，最多一行，优化阶段就能确定。
   - `eq_ref`：join 时被驱动表用主键/唯一索引等值匹配，每行驱动数据对应一行。
   - `ref`：普通索引等值匹配，可能多行。
   - `range`：索引范围扫描（`>`、`<`、`between`、`in`、`like 'x%'`）。
   - `index`：全索引扫描，比 `ALL` 好一点（索引小），但仍扫全量。
   - `ALL`：全表扫描。
   还有 `index_merge`、`ref_or_null`、`fulltext` 等，出现频率低。

4. **`key_len`。** 表示实际使用的索引字节数，可用来判断联合索引用到了几列。规则：`int` 为 4 字节（可空则 +1）、`bigint` 为 8 字节、`datetime` 为 5 字节、`varchar(n)` 为 `3n`（utf8mb4 下是 `4n`）再加 2 字节长度前缀（可空再加 1）。这是判断"联合索引只用了一半"的实用技巧。

5. **`rows` 与 `filtered`。** `rows` 是估算的扫描行数，`filtered` 是条件过滤后剩余的百分比，两者相乘约等于最终参与 join 的行数。`filtered` 在 5.7 之前恒为 100%，5.7 起才有实际估算值，回答时点明版本差异会加分。

6. **`Extra` 的六种常见值。**
   - `Using index`：覆盖索引，不回表，最优。
   - `Using index condition`：索引下推（5.6+），在索引上先过滤。
   - `Using where`：server 层还要再过滤，说明有条件下推不到索引。
   - `Using filesort`：需要额外排序，不一定是磁盘排序，内存里也可能叫这个名字。
   - `Using temporary`：用了临时表，常见于 `group by`、`distinct`、`union`。
   - `Using join buffer (Block Nested Loop)` / `(hash join)`：被驱动表无索引，用了 join buffer 或哈希连接。

```sql
EXPLAIN SELECT o.id, o.amount
FROM orders o
JOIN users u ON o.user_id = u.id
WHERE o.status = 1 AND o.create_time > '2026-01-01'
ORDER BY o.create_time DESC
LIMIT 20\G

-- 典型输出解读：
-- type=ref（走 idx_status_time 的等值前缀）
-- key=idx_status_time
-- rows=1200（估算扫 1200 行）
-- filtered=33.33（过滤后约 400 行）
-- Extra=Using index condition; Using where
--   → 索引下推生效，但 create_time 排序可能与 where 冲突
```

**易混对比**：

| Extra 值 | 含义 | 严重程度 | 优化方向 |
| --- | --- | --- | --- |
| `Using index` | 覆盖索引，无回表 | 优 | 无需优化 |
| `Using index condition` | 索引下推过滤 | 良 | 可接受 |
| `Using where` | server 层再过滤 | 中 | 考虑把条件下推到索引 |
| `Using filesort` | 额外排序 | 差 | 让索引顺序匹配 order by |
| `Using temporary` | 临时表 | 差 | 改写 group by 或用覆盖索引 |
| `Using join buffer` | 被驱动表无索引 | 差 | 给 join 列建索引 |

**面试追问**：
- 追问：`type=index` 和 `ALL` 哪个快？→ 答题要点：通常 `index` 略快，因为只扫索引页（更小），但本质都是全量扫描。
- 追问：`rows` 很小但查询仍慢，可能是什么原因？→ 答题要点：回表随机 IO 多、锁等待、或 `filtered` 很低导致实际处理行数远超 rows。
- 追问：怎么判断联合索引用到了第几列？→ 答题要点：看 `key_len`，按各列字节数累加推算。
- 追问：EXPLAIN 会真正执行 SQL 吗？→ 答题要点：不会，只输出计划；8.0.18 的 `EXPLAIN ANALYZE` 会真实执行并给出实际耗时。

### Q20. 一条慢 SQL 怎么定位和优化？深分页怎么处理？（中级） {#q20}

> 前置：索引、深分页、覆盖索引

**一句话结论**：定位流程是"慢查询日志找出 Top SQL → `pt-query-digest` 聚合 → `EXPLAIN` 看执行计划 → 针对性优化（加索引、改写 SQL、减少回表、拆分）"。深分页的三种解法：延迟关联（先用覆盖索引取主键再回表）、游标分页（记录上一页最后一个 id，用 `where id > ?`）、以及业务上限制最大页数或改用搜索引擎。

**先把话说白**：`limit 1000000, 20` 慢，不是因为只返回 20 行，而是因为要先**读出并丢弃前 100 万行**。就像你要一本书的第 500 页，前面 499 页可以不看，但数据库的翻页方式是"一页一页数过去"。解决办法只有两个：要么别数（游标），要么数得快（覆盖索引 + 延迟关联）。

**底层原理**：

1. **慢查询日志。** `slow_query_log=ON`、`long_query_time`（默认 10 秒，生产建议 0.5~1 秒）、`log_queries_not_using_indexes`（记录未走索引的 SQL，谨慎开启否则日志爆炸）。日志里包含执行时间、扫描行数、返回行数、锁等待时间，判断"慢在扫描还是慢在锁"看这几个数就够。

2. **聚合分析。** `pt-query-digest` 按 SQL 指纹（把常量替换为 `?`）聚合，输出总耗时占比、调用次数、平均耗时、扫描行数。优先优化"总耗时占比高"的，而不是"单次最慢"的——一条每分钟跑一次、耗时 3 秒的 SQL，比一条每天跑一次、耗时 30 秒的 SQL 更值得优化。

3. **深分页为什么慢。** `limit M, N` 的语义是"扫描前 M+N 行，丢弃前 M 行，返回后 N 行"。若走二级索引，还要对前 M 行逐行回表（虽然最终丢弃），代价是 M 次随机 IO。所以偏移量越大越慢，且是线性增长。

4. **方案一：延迟关联。** 先用覆盖索引在二级索引上翻页拿到主键（不回表，快），再用主键 join 回原表取整行。适用"必须支持跳页"的场景。

5. **方案二：游标分页。** 记录上一页最后一条的 id，下一页用 `where id > last_id order by id limit N`。走索引范围扫描，代价与页码无关。缺点是不能跳页，只能"下一页"，适合信息流类场景（这也是所有 App 下拉加载的做法）。

6. **方案三：业务限制。** 限制最大可翻页数（如只允许看前 100 页）、或超过阈值时引导用户用更精确的筛选条件。很多搜索引擎的"结果最多显示 100 页"就是这个思路——不是技术做不到，是成本不划算。

```sql
-- 慢 SQL：偏移 100 万，走 idx_create_time 后逐行回表
SELECT * FROM orders ORDER BY create_time DESC LIMIT 1000000, 20;

-- 方案一：延迟关联（先覆盖索引取主键，再回表）
SELECT o.* FROM orders o
JOIN (
  SELECT id FROM orders ORDER BY create_time DESC LIMIT 1000000, 20
) t ON o.id = t.id;

-- 方案二：游标分页（推荐，代价与页码无关）
SELECT * FROM orders
WHERE create_time < '上一页最后一条的 create_time'
ORDER BY create_time DESC LIMIT 20;

-- 若排序键不唯一，用 (create_time, id) 做联合游标，避免漏数据
SELECT * FROM orders
WHERE (create_time, id) < ('2026-01-01 10:00:00', 10086)
ORDER BY create_time DESC, id DESC LIMIT 20;
```

**易混对比**：

| 方案 | 是否支持跳页 | 代价随页码增长 | 额外要求 | 适用场景 |
| --- | --- | --- | --- | --- |
| 原始 `limit M,N` | 支持 | 线性增长 | 无 | 小数据量 |
| 延迟关联 | 支持 | 缓慢增长（仅索引扫描） | 排序列有索引 | 后台管理列表 |
| 游标分页 | 不支持 | 基本不变 | 排序列唯一或可组合 | App 信息流、导出 |
| 搜索引擎（ES） | 支持 | 受 `max_result_window` 限制 | 数据同步 | 复杂检索、深度翻页 |

**面试追问**：
- 追问：延迟关联为什么能快？→ 答题要点：子查询走覆盖索引不回表，扫描的是小得多的索引页；只有最终 20 行才回表。
- 追问：游标分页用 `create_time` 会有什么问题？→ 答题要点：时间重复时可能漏数据或重复，需加上唯一列（如 id）组成联合游标。
- 追问：`order by` 的列没索引，还能优化吗？→ 答题要点：只能减小结果集（先过滤再排序）或增加索引，`filesort` 无法靠参数消除。
- 追问：慢查询日志本身有性能开销吗？→ 答题要点：有，写文件与格式化有成本；`long_query_time` 设得过小会导致日志量过大，需配合采样。

### Q21. `count(*)`、`count(1)`、`count(字段)` 有什么区别？（中级） {#q21}

> 前置：聚集索引、二级索引、优化

**一句话结论**：`count(*)` 与 `count(1)` 语义等价，统计行数，InnoDB 会选**最小的二级索引**来扫描以减少 IO；`count(字段)` 统计该列非 NULL 的行数，需要逐行判断值是否为 NULL，因此不能使用"选最小索引"的优化，通常更慢；`count(distinct 字段)` 还要额外去重。三者都不存在"`count(1)` 比 `count(*)` 快"的说法。

**先把话说白**：`count(*)` 里的 `*` 不是"所有列"，SQL 标准里它就是"统计行数"的意思，优化器不会真去读每一列。而 `count(字段)` 带了一个额外语义："这个字段是 NULL 的行不算"。既然要判断 NULL，就必须把这一列读出来，优化空间自然就小了。

**底层原理**：

1. **语义差异。** `count(*)` 和 `count(1)` 统计所有行；`count(col)` 统计 `col is not null` 的行；`count(distinct col)` 统计 `col` 的非重复非空值个数。所以三者结果在列有 NULL 时会不同，这是语义差异不是性能差异。

2. **InnoDB 为什么不能像 MyISAM 那样 O(1)。** MyISAM 在表元数据里存了行数，不带 where 的 `count(*)` 直接返回。InnoDB 因为 MVCC，不同事务看到的行数可能不同（各自 ReadView 不同），无法维护一个全局准确计数，只能实时统计。这是"事务能力换来的代价"。

3. **InnoDB 的优化：选最小索引。** 既然必须扫，就选最小的那棵树扫。二级索引叶子只存"索引列 + 主键"，比聚簇索引（整行）小得多，同样的数据量页数更少，扫起来更快。所以 `count(*)` 会优先选最短的二级索引；如果表只有聚簇索引，才扫聚簇索引。这也是"为什么有人建议建一个窄索引来加速 count"的原因。

4. **`count(1)` 与 `count(*)` 完全等价。** MySQL 优化器会把 `count(1)` 改写成 `count(*)`，执行计划一致，性能一致。网上"`count(1)` 比 `count(*)` 快"的说法在 MySQL 上不成立（在部分其他数据库上可能有差异）。

5. **`count(col)` 更慢的原因。** 必须读出 `col` 的值判断是否为 NULL，若 `col` 不在任何索引中，还要回表；且无法使用"最小索引"优化（因为要读的列可能不在那个索引里）。所以 `count(某业务字段)` 在大表上通常明显慢于 `count(*)`。

6. **大表计数的工程方案。** 精确计数代价高，通常改为"近似值 + 增量维护"：用 Redis 计数器（写入时 `incr`）、单独维护计数表（同事务更新）、或直接展示"约 xx 条"。若必须精确且高频，应把计数从主表剥离。

**易混对比**：

| 写法 | 统计语义 | 是否判 NULL | 能否用最小索引优化 | 相对性能 |
| --- | --- | --- | --- | --- |
| `count(*)` | 所有行 | 否 | 能 | 最快 |
| `count(1)` | 所有行 | 否 | 能 | 与 `count(*)` 相同 |
| `count(col)` | `col` 非 NULL 的行 | 是 | 通常不能 | 较慢 |
| `count(distinct col)` | 非重复非 NULL 值 | 是 | 不能 | 最慢 |
| `count(1)` 带 where | 满足条件的行 | 否 | 视条件而定 | 取决于索引 |

**面试追问**：
- 追问：为什么 InnoDB 不缓存一个行数？→ 答题要点：MVCC 下不同事务看到不同行数，缓存无法对所有人正确。可参考 `information_schema.tables.table_rows` 的估算值。
- 追问：`count(*)` 会扫全表吗？→ 答题要点：会扫一棵完整的索引树，但通常是最小的二级索引，不是聚簇索引。
- 追问：加一个 `where` 后 `count(*)` 怎么选索引？→ 答题要点：优先选能用于 where 过滤的索引，其次在可用索引中选最短的。
- 追问：`information_schema.tables.table_rows` 准确吗？→ 答题要点：不准确，是采样估算值，误差可能很大，只能用于粗略判断。

### Q22. JOIN 有哪几种执行算法？驱动表怎么选？（高级） {#q22}

> 前置：Nested Loop、Hash Join、驱动表

**一句话结论**：MySQL 有三种 join 算法：嵌套循环连接（NLJ，被驱动表有索引时用，走索引查找）、块嵌套循环（BNL，被驱动表无索引时用 join buffer 批量匹配）、哈希连接（Hash Join，8.0.18 引入，等值连接且无索引时替代 BNL）。驱动表选择原则是"小表驱动大表"，即结果集小的表做驱动表，减少被驱动表的查找次数。

**先把话说白**：join 的本质是"拿一张表的每一行，去另一张表里找匹配"。如果另一张表有索引，每次查找很快，那就老老实实一行一行找（NLJ）；如果没有索引，每次都要全表扫，那就把驱动表的一批行先装进内存，再扫一遍被驱动表（BNL）；如果连"一批批比对"都嫌慢，那就给两边都建哈希表，一次扫完（Hash Join）。

**底层原理**：

1. **NLJ 与 Index NLJ。** 两层循环：外层取驱动表一行，内层用该行的 join 列去被驱动表的索引上查找。若被驱动表 join 列有索引，内层是索引查找，复杂度约 `驱动行数 × log(被驱动行数)`，非常高效。注意 `join_buffer_size` 在这里用于"被驱动表无索引"的场景，有索引时不生效。

2. **Simple NLJ（无索引的朴素嵌套）。** 被驱动表无索引且 join buffer 不够用时，退化为"对驱动表每一行都全表扫描被驱动表"，复杂度是笛卡尔积级别，必须避免。

3. **BNL（Block Nested-Loop）。** 把驱动表的一批行装入 `join_buffer_size`（默认 256KB）的 join buffer，然后**全表扫描一次**被驱动表，把 buffer 中的行与被驱动表的每一行逐一比对。相比 Simple NLJ，把"驱动表行数 × 全表扫描"降为"驱动表行数 / buffer 容量 × 全表扫描"。Extra 显示 `Using join buffer (Block Nested Loop)`。

4. **Hash Join。** MySQL 8.0.18 引入，8.0.20 起在无索引等值连接时默认替代 BNL。做法是对较小的表（构建表）在内存中建哈希表，再扫描另一张表（探测表）逐行探测。复杂度接近 O(M+N)，远优于 BNL。限制：只支持等值连接（`=`），非等值（`>`、`<`）仍用 BNL；内存不足时会落盘分批。Extra 显示 `Using join buffer (hash join)`。

5. **驱动表怎么选。** 原则是"结果集小的做驱动表"。因为驱动表的每一行都要触发一次对被驱动表的查找，驱动表越小，查找次数越少。但"小"指的是**经过 where 过滤后的结果集大小**，不是表的总行数。优化器通过 `rows × filtered` 估算，估算不准时会选错，可用 `STRAIGHT_JOIN` 强制顺序。

6. **join 的其它注意事项。** 一是 join 列的类型与字符集必须一致，否则索引失效（Q8 第 8 条）；二是 `left join` 的驱动表固定为左表，不能随意调换，`where` 中对右表的过滤条件若写在 where 里会把外连接退化为内连接（要写在 on 里）；三是 join 表数量不宜超过 3 张，超过后优化器的搜索空间爆炸，容易选出坏计划。

**易混对比**：

| 算法 | 触发条件 | 复杂度 | 内存依赖 | 版本 |
| --- | --- | --- | --- | --- |
| Index NLJ | 被驱动表 join 列有索引 | 驱动行数 × 索引查找 | 低 | 全版本 |
| Simple NLJ | 无索引且 join buffer 不足 | 驱动行数 × 被驱动行数 | 低 | 全版本 |
| BNL | 无索引，join buffer 够用 | 驱动行数 / buffer × 被驱动行数 | `join_buffer_size` | 5.6+ |
| Hash Join | 等值连接且无可用索引 | 约 O(M+N) | `join_buffer_size` | 8.0.18+ |

**面试追问**：
- 追问：为什么 Hash Join 只支持等值？→ 答题要点：哈希函数只能判断"相等"，无法表达区间关系，范围连接仍需排序或嵌套。
- 追问：`left join` 能把小表放左边吗？→ 答题要点：不能随意换，左连接语义要求左表全部保留，换表会改语义；需要换就用 `right join` 或改写。
- 追问：join 太多表会怎样？→ 答题要点：优化器搜索空间随表数阶乘增长，可能超时退化为贪心选择，计划质量下降。
- 追问：`join_buffer_size` 调大有用吗？→ 答题要点：对 BNL 有用（减少扫描次数），对 Hash Join 有用（减少落盘），但它是每连接分配的，调大会撑爆内存。

### Q23. 大事务有什么危害？怎么拆分？（中级） {#q23}

> 前置：undo、锁持有、主从延迟

**一句话结论**：大事务的危害有五条：长时间持有锁导致锁等待与死锁概率上升、undo log 无法回收导致 undo 表空间膨胀、redo 与 binlog 一次性写入过大导致提交抖动、主从延迟（从库要回放同样长的事务）、以及回滚成本极高。拆分方式是分批提交，每批控制在几百到几千行，并保证批间可重入。

**先把话说白**：事务的代价不是"操作了多少数据"，而是"锁持有了多久"。一个事务跑 30 秒，它锁住的那些行就 30 秒不能被别人碰；而如果中途失败，前面所有操作都要撤销，撤销本身也要 30 秒。所以大事务的问题在时间维度上被放大。

**底层原理**：

1. **锁持有时间长。** 事务内所有锁要到 commit 才释放。大事务意味着行锁、间隙锁的持有时间成倍延长，其他事务排队，`innodb_lock_wait_timeout` 超时率上升，死锁概率也随之上升。

2. **undo 膨胀。** undo 记录要保留到事务结束（供回滚），且 MVCC 还需要它们。长事务让 purge 线程无法清理更早的 undo，undo 表空间持续增长，极端情况会撑满磁盘。同时版本链变长，快照读要遍历更多版本，读性能下降。

3. **提交抖动。** 事务结束时一次性 fsync redo 与 binlog，写入量越大，fsync 越久，表现为周期性卡顿。binlog 在 `ROW` 格式下，一条 update 影响 100 万行就写 100 万条记录。

4. **主从延迟。** 从库的 SQL 线程（或 worker）要回放同样大的事务，回放期间该事务在从库上是一个原子单位，其他事务可能被阻塞，表现为从库延迟陡增。这是"主库一个大事务把从库打挂"的机制。

5. **回滚成本。** 回滚是反向执行 undo，耗时可能比正向执行更长（因为要随机读 undo 并写回数据页）。所以"跑了一半失败"往往是最坏情况。

6. **怎么拆。** 按主键范围分批（`where id between ? and ?`）、按时间分批、每批 `limit 500~2000` 行并提交，循环推进。要求：批间可重入（失败后能从断点继续）、业务上允许中间态（或用一个状态字段标记进度）、并且要有总量上限防止死循环。

```java
// 分批更新，每批 1000 行，避免大事务
long lastId = 0;
while (true) {
    List<Long> ids = jdbcTemplate.queryForList(
        "SELECT id FROM orders WHERE id > ? AND status = 0 ORDER BY id LIMIT 1000",
        Long.class, lastId);
    if (ids.isEmpty()) break;

    // 每批一个独立事务
    transactionTemplate.executeWithoutResult(status ->
        jdbcTemplate.update(
            "UPDATE orders SET status = 1 WHERE id IN (" +
            ids.stream().map(String::valueOf).collect(Collectors.joining(",")) + ")"));
    lastId = ids.get(ids.size() - 1);
}
```

**面试追问**：
- 追问：分批后如何保证整体一致性？→ 答题要点：通常靠"最终一致 + 补偿"，或用状态字段做断点续跑；跨批强一致需要分布式事务，成本高。
- 追问：怎么发现线上有大事务？→ 答题要点：查 `information_schema.innodb_trx` 按 `trx_started` 排序，或监控 `trx_rows_modified`。
- 追问：`delete` 大表数据怎么避免大事务？→ 答题要点：分批 `delete ... limit N`，且注意删除会产生大量 undo 与 binlog，需控制节奏。
- 追问：DDL 算大事务吗？→ 答题要点：DDL 是隐式提交，不占事务，但长 DDL 会持有 MDL 锁阻塞后续所有请求，危害类似。

### Q24. 什么时候需要分库分表？分片键怎么选？（高级） {#q24}

> 前置：分片键、路由、扩容

**一句话结论**：单表数据量导致索引层数增加、单库写入或连接数达到瓶颈、单机磁盘容量不足时，才考虑分库分表。分垂直（按业务拆库、按列拆表）与水平（按行拆分）两种；分片键要选**高基数、分布均匀、且能覆盖主流查询**的字段（通常是 user_id 或 tenant_id），否则会退化成广播查询。

**先把话说白**：分库分表是"最后手段"，因为它把简单问题（一个库）换成一堆复杂问题（跨库查询、分布式事务、扩容、运维）。经验上单表 2000 万行不是硬门槛——只要索引合理、热数据能进 Buffer Pool，几千万行照样跑得动。真正的信号是"优化到极限仍然撑不住"。

**底层原理**：

1. **该不该分的判断。** 三个信号：单表数据量导致 B+ 树从 3 层涨到 4 层以上（意味着每次查询多一次 IO）；单库写入 QPS 或连接数打满，加从库也救不了写；单机磁盘容量或备份恢复时间不可接受。若只是读压力大，优先加从库 + 缓存，不需要分片。

2. **垂直拆分。** 垂直分库：按业务域拆成订单库、用户库、商品库，降低单库压力、隔离故障。垂直分表：把大字段（`text`、`blob`）或低频列拆到扩展表，让主表行更小、每页能放更多行，提升 Buffer Pool 效率。这一层几乎无副作用，应优先做。

3. **水平拆分。** 按行拆分到多个库/表，规则有 hash（`user_id % N`）、range（按时间或 ID 区间）、以及一致性哈希。hash 分布均匀但扩容需迁移；range 扩容方便但可能热点（新数据都落在最后一个分片）。

4. **分片键的选择标准。** 三条：高基数（避免数据倾斜）、分布均匀（避免热点）、**能覆盖主流查询**（避免跨分片）。订单表用 `user_id` 分片，则"查我的订单"能定位到单分片，但"按订单号查"就需要额外维护"订单号 → user_id"的映射表，或让订单号本身编码 user_id（基因法）。选错分片键的代价是"每次查询都要广播到所有分片再聚合"，比不分片还慢。

5. **跨库 join 的四种解法。** 字段冗余（把常用字段冗余到主表，避免 join）、广播表（小表在每个分片存一份全量）、内存拼装（分别查再在应用层 join）、以及异构索引表（用 ES 承担复杂查询）。原则是"能冗余就不 join，能单分片就不跨分片"。

6. **分布式事务。** 跨分片写入需要分布式事务，常见方案：2PC/XA（强一致但性能差、协调者单点）、TCC（业务侵入大、需处理幂等与悬挂）、本地消息表 / 事务消息（最终一致，最常用）、Seata AT 模式（自动生成反向 SQL，介于两者之间）。多数互联网业务选最终一致。

7. **扩容的双写迁移。** 新老库同时写（双写）、用影身读（读老库同时比对写新库）、灰度切读、最后停双写。关键是**迁移期间的数据校验**与**可回滚**，不能一次性切。

**易混对比**：

| 维度 | 垂直拆分 | 水平拆分 |
| --- | --- | --- |
| 拆分依据 | 业务域 / 列 | 行（按分片键） |
| 解决的问题 | 单库压力、表太宽 | 单表数据量、单库写入瓶颈 |
| 复杂度 | 低，几乎无跨库问题 | 高，跨库 join、事务、扩容 |
| 扩容难度 | 低（加库即可） | 高（需数据迁移） |
| 典型工具 | 无（应用层拆） | ShardingSphere、MyCat、Vitess |
| 推荐顺序 | 先做 | 后做 |

**面试追问**：
- 追问：为什么说 2000 万行不是硬门槛？→ 答题要点：取决于行大小与访问模式，窄表能存更多；关键指标是索引层数与缓存命中率。
- 追问：`user_id % 1024` 分片，扩容到 2048 怎么办？→ 答题要点：取模基数变化会导致全量迁移，应使用成倍扩容 + 双写迁移，或改用一致性哈希/范围分片。
- 追问：分片后怎么做分页？→ 答题要点：各分片取前 N 条再归并排序，深分页代价极高，通常限制或改用搜索引擎。
- 追问：分片后自增主键怎么办？→ 答题要点：用 Snowflake、号段模式（Leaf/Redis）或按分片设置不同起始值与步长。

### Q25. 主从复制的原理是什么？主从延迟怎么解决？（高级） {#q25}

> 前置：binlog、relay log、延迟

**一句话结论**：主库把变更写入 binlog，从库的 IO 线程拉取 binlog 写入本地 relay log，SQL 线程（或并行 worker）回放 relay log 应用到从库数据。主从延迟的根因是"从库回放速度跟不上主库写入速度"，常见于大事务、大表 DDL、从库压力大、单线程回放；解决手段有并行复制、半同步复制、强制走主库、以及业务层容忍。

**先把话说白**：复制就是"主库记流水账，从库照着账本重做一遍"。异步复制下，主库记完账就返回成功，不等从库做完，所以从库天然落后一点。落后得少没关系，落后得多就是延迟。而延迟的可怕之处在于：用户刚下单（写主库），立刻查订单（读从库），查不到——这是"读写分离"最典型的坑。

**底层原理**：

1. **三个线程。** 主库的 dump 线程：读取 binlog 并发送给从库。从库的 IO 线程：接收 binlog 写入 relay log（中继日志）。从库的 SQL 线程：读 relay log 并执行。三个线程各司其职，任一环节慢都会造成延迟。

2. **位点与 GTID。** 传统复制靠 `binlog file + position` 记录进度，主库切换时需要人工找位点，容易出错。GTID（Global Transaction Identifier）给每个事务一个全局唯一编号，从库只需知道"已执行到哪个 GTID 集合"，主从切换可自动定位，是现代部署的默认选择。

3. **复制格式。** `STATEMENT` 记 SQL 原文，日志小但某些函数（`now()`、`uuid()`、`limit` 不带 `order by`）会导致主从不一致；`ROW` 记行变更前后镜像，日志大但绝对安全；`MIXED` 自动选择。生产上必须用 `ROW`。

4. **异步 / 半同步 / 全同步。** 异步：主库提交即返回，不等待从库，性能最好但可能丢数据。半同步：主库等待至少一个从库**收到并写入 relay log** 后才返回（`AFTER_SYNC` 模式，5.7 引入的无损半同步），保证不丢 binlog，但仍可能"从库收到但未回放"。全同步（组复制 MGR）：多数派确认后才提交，强一致但性能与运维成本高。

5. **延迟的五个来源。** 从库机器配置比主库差；从库承担大量读请求（读写分离后从库压力更大）；大事务回放期间无法并行；大表 DDL 在从库串行执行；网络带宽不足导致 binlog 传输慢。要区分是"IO 线程慢（网络/带宽）"还是"SQL 线程慢（回放）"，看 `SHOW SLAVE STATUS` 里 `Slave_IO_Running` 与 `Seconds_Behind_Master`，以及 `Relay_Log_Space` 的增长。

6. **并行复制的原理。** 5.6 基于 schema 并行（效果差，因为多数应用单库）；5.7 基于组提交（`slave_parallel_type=LOGICAL_CLOCK`），把同一组提交内的事务并行回放，因为组内事务在主库上本就没有锁冲突；8.0 基于 write set（`binlog_transaction_dependency_tracking=WRITESET`），能识别"修改的行集不重叠"的事务并并行，粒度更细。并行度由 `slave_parallel_workers` 控制。

**易混对比**：

| 复制模式 | 主库返回时机 | 数据安全性 | 性能 | 适用场景 |
| --- | --- | --- | --- | --- |
| 异步复制 | 提交即返回 | 主库宕机可能丢 | 最好 | 日志类、可容忍丢失 |
| 半同步（AFTER_SYNC） | 至少一个从库写入 relay log | 不丢 binlog | 较好 | 多数在线业务 |
| 半同步（AFTER_COMMIT） | 从库收到后主库才返回客户端 | 5.7 前模式，有幽灵事务风险 | 较差 | 已不推荐 |
| 组复制 MGR | 多数派认证通过 | 强一致 | 差 | 金融核心 |

**面试追问**：
- 追问：半同步能保证读到最新数据吗？→ 答题要点：不能，只保证 binlog 已传到从库，回放可能还没完成，读仍可能读到旧值。
- 追问：`Seconds_Behind_Master` 为 0 就说明没延迟吗？→ 答题要点：不一定，它基于时间戳估算，网络中断或 SQL 线程卡住时可能显示 0 或 NULL。
- 追问：为什么大事务会放大延迟？→ 答题要点：事务在从库是原子回放单位，无法拆给多个 worker 并行，且执行期间可能阻塞其他事务。
- 追问：读写分离后如何保证"写完立刻能读到"？→ 答题要点：关键路径强制走主库、或写后短时间内粘住主库（会话粘滞）、或用半同步 + GTID 等待。

### Q26. 读写分离后怎么保证一致性？缓存双删为什么有效？（中级） {#q26}

> 前置：主从延迟、双删、缓存

**一句话结论**：读写分离的一致性问题是"复制窗口"——写主库成功后，从库可能还没回放，此时读从库会读到旧值。解决思路是分级：强一致场景强制走主库；弱一致场景接受延迟并用"写后粘主库"收敛；缓存层用"先删缓存、再更新库、延迟再删一次"（缓存双删）缩小不一致窗口，并用过期时间兜底。

**先把话说白**：读写分离把"写"和"读"分到两台机器上，中间隔着一段复制时间，这段窗口里数据是不一致的。缓存又在这之上加了一层，窗口变得更复杂。工程上没办法完全消除窗口，只能把它压到业务可接受的范围——所以关键是"哪些读必须强一致"，而不是"如何让所有读都强一致"。

**底层原理**：

1. **不一致的三种来源。** 主从复制延迟（写主读从）、缓存与数据库不同步（更新库成功但删缓存失败）、并发读写交叉（读请求把旧值回填缓存，覆盖了刚删的key）。

2. **强制走主库。** 对一致性敏感的读（下单后查订单、支付后查状态）用注解或路由强制路由到主库。代价是主库压力上升，所以只对关键路径用，不能全站开启。

3. **写后粘主库。** 记录该会话最近一次写入的时间，在接下来 N 秒（略大于最大复制延迟）内的读都走主库，之后恢复正常路由。这是"用时间换一致性"的折中，N 的取值需要根据实际延迟分布定。

4. **缓存双删的时序。** 第一步：更新前先删缓存（避免更新期间读到旧缓存）；第二步：更新数据库；第三步：延迟几百毫秒再删一次缓存（清除这期间被旧值回填的缓存）。第二次删除是关键——因为"读请求在删缓存之后、更新库之前把旧值写回缓存"这种情况一定存在，只删一次挡不住。

5. **为什么用"删"而不是"更新"缓存。** 更新缓存在并发下会产生乱序（两个更新线程写缓存顺序可能与写库顺序相反），导致缓存长期脏数据；删除则是幂等的，最坏情况是缓存未命中回源，代价可控。这是 Cache-Aside 模式的标准做法。

6. **兜底：过期时间。** 无论双删做得多好，都必须给缓存设 TTL。它是最后一道防线：所有一致性方案都可能在极端情况下失败（进程崩溃、网络分区），TTL 保证"最终一定会好"。

```java
public void updateProduct(Product p) {
    String key = "product:" + p.getId();
    redis.delete(key);                       // 1. 先删缓存
    productMapper.updateById(p);             // 2. 更新数据库
    executor.schedule(() -> {                // 3. 延迟再删一次
        redis.delete(key);
    }, 500, TimeUnit.MILLISECONDS);
}
```

**易混对比**：

| 方案 | 一致性强度 | 主库压力 | 实现成本 | 适用场景 |
| --- | --- | --- | --- | --- |
| 全部读主库 | 强 | 极高 | 低 | 极小流量、强一致 |
| 关键路径走主库 | 关键路径强 | 中 | 低 | 订单、支付 |
| 写后粘主库 N 秒 | 近似强（窗口内） | 中 | 中 | 用户自己数据的读 |
| 半同步 + 等待 GTID | 强 | 中 | 高 | 金融级 |
| 缓存双删 + TTL | 最终一致 | 低 | 中 | 商品、配置类读多写少 |

**面试追问**：
- 追问：双删的第二次延迟怎么定？→ 答题要点：略大于"一次读请求的回源耗时 + 主从延迟"，通常几百毫秒，且必须配 TTL 兜底。
- 追问：为什么不先用"更新缓存"？→ 答题要点：并发更新会导致缓存与库的顺序错乱，删除是幂等的，更安全。
- 追问：缓存和数据库能做强一致吗？→ 答题要点：很难，除非用分布式事务或把缓存当唯一数据源，通常选择最终一致。
- 追问：主从延迟突然变大，业务怎么降级？→ 答题要点：读请求切主库、关闭非核心读、限流，并告警到 DBA 排查大事务。

### Q27. Online DDL 有哪几种方式？会不会锁表？（高级） {#q27}

> 前置：表锁、copy、inplace

**一句话结论**：MySQL 的 DDL 有三种算法：`COPY`（创建新表、逐行拷贝、全程锁写，最慢）、`INPLACE`（在原表上重建或就地修改，允许并发 DML，但需要 brief 的元数据锁）、`INSTANT`（8.0.12 起支持部分操作如加列，只改数据字典，秒级完成）。是否锁表取决于算法与 `LOCK` 子句，可用 `ALGORITHM` 与 `LOCK` 显式约束，不满足时直接报错而不是悄悄降级。

**先把话说白**：给千万级大表加一个字段，如果按"建新表 + 拷数据 + 改名"的老办法，要拷几个小时，期间写入全阻塞——这就是典型的"发版把数据库搞挂"。Online DDL 的目标是"改表结构的同时，业务还能读写"。

**底层原理**：

1. **COPY 算法。** 建一张结构相同的新表，逐行把数据拷过去（同时转换格式），拷完加锁 rename。全程不允许并发写，最慢。5.6 之前几乎所有 DDL 都走这条。

2. **INPLACE 算法。** 不创建新表副本（或只在内部重建），在原有表空间上完成。执行期间允许并发 DML，靠 **online log**（一块内存区域）记录 DDL 期间的增量变更，DDL 完成后把增量应用到新结构上。关键点：DDL 开始与结束各需要一次**元数据锁（MDL）**，写锁只在极短时间内持有，但如果之前有长事务持有 MDL 读锁，DDL 会等待，进而阻塞后续所有请求——这就是"加个字段导致全站雪崩"的真实机制。

3. **INSTANT 算法。** 8.0.12 起支持 `ADD COLUMN`（只能加在最后一列）为 INSTANT，8.0.29 起支持任意位置加列与删列。只修改数据字典中的列定义，不触碰数据行，秒级完成。查询时对"老行"用默认值补齐（记录在数据字典里），所以**加列必须允许为 NULL 或有默认值**。

4. **`ALGORITHM` 与 `LOCK` 子句。** `ALGORITHM=INPLACE` 表示"必须用 INPLACE，否则报错"，`ALGORITHM=INSTANT` 同理；`LOCK=NONE` 表示"不允许阻塞任何读写"，`LOCK=SHARED` 允许读不允许写。显式指定是生产规范：宁可报错让你改方案，也不要悄悄降级成锁表几小时。

5. **哪些操作支持 INSTANT / INPLACE。** 加列、删列（8.0.29+）、加索引（INPLACE）、改索引名、设置/删除默认值（INSTANT）、改字段类型（多数需 INPLACE 重建，且可能丢精度）、加外键（INPLACE 但需 `foreign_key_checks=0`）。改主键、改字符集通常必须重建表。

6. **gh-ost 与 pt-osc。** 原生 Online DDL 仍受 MDL 与主从延迟困扰（大表 INPLACE 会在主库产生大量 binlog，从库单线程回放跟不上）。第三方工具的思路是"影子表 + 增量同步 + 切换"：`pt-osc` 用触发器捕获增量，`gh-ost` 用伪装成从库读取 binlog（无触发器，对主库压力更小，可限流、可暂停）。代价是需要在应用低峰执行，且切换瞬间有短暂不可写。

**易混对比**：

| 算法 | 是否重建表 | 并发 DML | 耗时 | 典型操作 | 版本 |
| --- | --- | --- | --- | --- | --- |
| COPY | 是（新表） | 不允许 | 与数据量线性 | 改字符集、改主键 | 全版本 |
| INPLACE | 可能重建（rebuild） | 允许 | 与数据量线性但更快 | 加索引、改字段类型 | 5.6+ |
| INSTANT | 否 | 允许 | 秒级 | 加列、改默认值 | 8.0.12+ |
| gh-ost | 影子表 | 允许（切换瞬间除外） | 可控、可限流 | 任意变更 | 工具 |

**面试追问**：
- 追问：加索引会不会锁表？→ 答题要点：INPLACE 下允许并发 DML，但开始与结束需要 brief MDL；若有长事务占着 MDL，会排队并阻塞后续请求。
- 追问：为什么"加字段把数据库搞挂了"？→ 答题要点：DDL 等 MDL 写锁，排在其后的所有查询也等 MDL，形成雪崩；根因是长事务，不是 DDL 本身。
- 追问：INSTANT 加列后，老数据怎么读到新列的值？→ 答题要点：数据字典记录默认值，读取时对老行动态补齐，不物理回填。
- 追问：gh-ost 比 pt-osc 好在哪？→ 答题要点：不用触发器（避免额外写入开销与锁），可读 binlog 限流、可暂停，对主库影响更小。

### Q28. 建表时字段类型和约束该怎么选？（初级） {#q28}

> 前置：存储、字符集、约束

**一句话结论**：字段类型遵循"够用就好"——整数用最小合适类型、金额用 `decimal` 不用 `float`、变长字符串用 `varchar` 并给合理长度、时间用 `datetime` 或 `timestamp` 按需选择；约束上尽量 `NOT NULL` 加默认值（NULL 会让索引统计与比较逻辑变复杂）、统一 `utf8mb4` 字符集、控制索引数量在 5 个以内。

**先把话说白**：表设计是"一次决定、长期偿还"的事。字段类型选大了，每行多几个字节，一亿行就是几百 MB，Buffer Pool 少缓存几万个页；允许 NULL，索引统计、`count`、`!=` 查询都会多出边界情况。这些代价单看很小，乘以数据量就很可观。

**底层原理**：

1. **整数类型。** `tinyint`(1 字节)、`smallint`(2)、`mediumint`(3)、`int`(4)、`bigint`(8)。够用就好，但主键建议直接用 `bigint unsigned`，避免几年后改类型（大表 DDL 代价极高）。`int unsigned` 上限约 42 亿，看似够用，但业务增长常超预期。

2. **金额绝对不能用 `float` / `double`。** 浮点数二进制无法精确表示十进制小数，累加会产生误差（`0.1 + 0.2 != 0.3`）。用 `decimal(m, d)`（精确十进制）或把金额存为整数分（`bigint`），后者运算更快、无精度问题，是互联网公司的常见做法。

3. **字符串类型。** `char(n)` 定长，适合长度固定的（如身份证、MD5）；`varchar(n)` 变长，适合长度差异大的。`varchar` 的长度要按业务上限给，不要一律 `varchar(255)`——虽然存储按实际长度，但排序、临时表、`max_sort_length` 会按声明长度分配内存，且索引前缀长度受限制。大文本用 `text` 并拆到扩展表。

4. **时间类型。** `datetime` 存字面值，范围 1000~9999 年，不受时区影响，占 5 字节（5.6.4 起支持小数秒）；`timestamp` 存 UTC 时间戳，占 4 字节，范围到 2038 年，受 `time_zone` 影响。跨时区业务用 `timestamp`，需要超过 2038 年或存历史日期用 `datetime`。`int` 存时间戳也是一种选择（省空间、时区由应用处理），但可读性差。

5. **NULL 的代价。** 一是索引统计：NULL 值参与 `cardinality` 计算但比较逻辑特殊，`count(col)` 会跳过 NULL；二是查询：`col != 1` 不会返回 NULL 行（三值逻辑），容易写出"漏数据"的 bug；三是存储：可空列需要额外的 NULL 标志位，且可空列不能让索引完全覆盖（`key_len` 多 1 字节）；四是唯一索引：多个 NULL 在唯一索引中不冲突，与业务预期常不一致。所以规范上要求 `NOT NULL DEFAULT`。

6. **字符集统一 `utf8mb4`。** MySQL 的 `utf8` 实际是 `utf8mb3`，最多 3 字节，存不了 emoji 与部分生僻字（4 字节）。8.0 起默认字符集已改为 `utf8mb4`，5.7 默认是 `latin1`。更要紧的是**同一张表关联的列字符集必须一致**，否则 join 时发生隐式转换、索引失效（Q8 第 8 条）。

7. **为什么不建太多索引。** 见 Q11。补充一条实践：单表索引控制在 5 个以内，联合索引列数不超过 5 列，且必须定期用 `sys.schema_unused_indexes` 清理无用索引。

**易混对比**：

| 场景 | 推荐类型 | 不推荐 | 原因 |
| --- | --- | --- | --- |
| 金额 | `decimal(18,2)` 或 `bigint` 存分 | `float` / `double` | 浮点精度丢失 |
| 主键 | `bigint unsigned` 自增 | `int` / `char(36)` | 容量与顺序插入 |
| 状态 | `tinyint` | `varchar(10)` | 空间与比较效率 |
| 时间 | `datetime`（跨 2038 用） | `timestamp`（有 2038 限制） | 范围与时区语义 |
| 布尔 | `tinyint(1)` + `NOT NULL DEFAULT 0` | 允许 NULL | 三值逻辑易出错 |
| 字符串 | `varchar(实际上限)` | 一律 `varchar(255)` | 内存分配与索引长度 |
| 字符集 | `utf8mb4` | `utf8`（即 utf8mb3） | 不支持 emoji 与 4 字节字符 |

**面试追问**：
- 追问：`utf8` 和 `utf8mb4` 有什么区别？→ 答题要点：`utf8` 是 `utf8mb3`，最多 3 字节；`utf8mb4` 支持 4 字节，能存 emoji。
- 追问：为什么唯一索引里可以有多个 NULL？→ 答题要点：SQL 标准规定 NULL 不等于任何值（包括 NULL），所以不违反唯一约束；业务上要靠 `NOT NULL` 规避。
- 追问：`varchar(255)` 和 `varchar(20)` 存储上有区别吗？→ 答题要点：存储按实际长度，但内存分配、临时表、索引前缀限制按声明长度考虑。
- 追问：大字段为什么要拆表？→ 答题要点：行溢出会让页内行数骤减，Buffer Pool 效率下降，且 `select *` 会拖慢一切查询。

## 五、本章速记卡 {#s5}

- SQL 执行链：连接器 → 解析器 → 优化器 → 执行器 → 引擎；**server 层不存数据**，8.0 已移除查询缓存。
- 优化器统计信息是**采样**的（默认 20 个页），这是"选错索引"的根因；先 `optimizer_trace` 定位，再 `analyze`，最后才 `force index`。
- Buffer Pool 三链表：free、flush（按 LSN 排序）、LRU（young 63% / old 37%，midpoint 插入 + 1 秒时间窗抗扫描）；change buffer 只服务**非唯一二级索引**。
- redo 保持久（前滚）、undo 保回滚与 MVCC（后滚）、binlog 保复制（server 层，追加写）。
- 2PC：redo prepare → binlog → redo commit；崩溃恢复**以 binlog 是否完整为准**。双 1 = `innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`。
- 三层 B+ 树约存 2000 万行（1170 × 1170 × 16）；优势是**扇出大、树矮、叶子链表**，不是"单点查询更快"。
- 聚簇索引叶子存整行，二级索引叶子存主键；主键越长，**所有**二级索引越大。
- 最左前缀的本质是字典序，跳过左列则后续列全局无序；隐式转换看方向：`varchar` 列传数字**失效**，`int` 列传字符串**不失效**。
- ReadView 四字段：`m_ids`、`min_trx_id`、`max_trx_id`（是"下一个"ID）、`creator_trx_id`；RC 每次建、RR 首次建（不是 `begin` 时），`快照读 + update` 仍可幻读。
- 加锁三问：走哪个索引 → 扫描区间 → 唯一索引等值命中否。命中退化记录锁，非唯一与范围加临键锁，RC 无间隙锁，间隙锁之间**不互斥**。
- 死锁排查看 `LATEST DETECTED DEADLOCK` 的 `HOLDS` 与 `WAITING FOR`，8.0 用 `performance_schema.data_locks`；避免靠固定加锁顺序。
- `type` 优先级 `const` > `eq_ref` > `ref` > `range` > `index` > `ALL`；`Using index` 是覆盖、`Using index condition` 是 ICP。深分页用延迟关联或游标。
- `count(*)` = `count(1)` 走最小二级索引，`count(字段)` 要判 NULL 无法优化；join 小表驱动大表，8.0.18+ 无索引等值连接走 Hash Join。
- 大事务五宗罪：长持锁、undo 膨胀、提交抖动、主从延迟、回滚极慢；按主键分批提交，批间可重入。
- 主从三线程 dump → IO（写 relay log）→ SQL（回放），半同步 `AFTER_SYNC` 才不丢 binlog；Online DDL 的 COPY 锁写、INPLACE 有两次 brief MDL、INSTANT（8.0.12+）只改字典。

## 七、动手实验与失败现象 {#s7}

### 实验：一条 SQL 在有无索引时的执行计划

先造一张一万行的表（MySQL 8.0.33 实测）：

```sql
SET SESSION cte_max_recursion_depth = 20000;

CREATE TABLE t_user (
  id INT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(32),
  age INT
) ENGINE=InnoDB;

INSERT INTO t_user (name, age)
WITH RECURSIVE seq(n) AS (
  SELECT 1 UNION ALL SELECT n + 1 FROM seq WHERE n < 10000
)
SELECT CONCAT('user', n), n % 100 FROM seq;
```

`age` 取值是 `n % 100`，所以每个年龄恰好 100 行。先看没有索引时：

```sql
EXPLAIN FORMAT=TREE SELECT * FROM t_user WHERE age = 30;
```

```text
-> Filter: (t_user.age = 30)  (cost=1024 rows=1017)
    -> Table scan on t_user  (cost=1024 rows=10173)
```

加上索引再看：

```sql
CREATE INDEX idx_age ON t_user (age);
ANALYZE TABLE t_user;
EXPLAIN FORMAT=TREE SELECT * FROM t_user WHERE age = 30;
```

```text
-> Index lookup on t_user using idx_age (age=30)  (cost=29.5 rows=100)
```

从"扫 10173 行"变成"定位 100 行"，代价估算从 1024 降到 29.5。注意 `rows=100` 是估算值，不是精确值；优化器靠采样统计信息得出，所以统计信息过期时它也会选错。

**改一个地方看看**：把条件改成 `age > 98`，执行计划变成 `type=range`、`rows=100`、`Extra=Using index condition`；改成 `age > 30` 反而退回全表扫描 `type=ALL`——因为这时要回表取 68% 的行，优化器判断"走索引再回表"比"直接顺序扫"更贵。**有索引不等于一定走索引**，这是 Q11 那道题最容易被忽略的一半。

### 失败现象：索引在，但一行也用不上

```sql
EXPLAIN SELECT * FROM t_user WHERE age + 1 = 31;
EXPLAIN SELECT * FROM t_user WHERE name = 123;
```

两条语句的关键列（其余列省略）：

| 查询条件 | type | possible_keys | key | rows |
| --- | --- | --- | --- | --- |
| `age + 1 = 31` | ALL | NULL | NULL | 9868 |
| `name = 123` | ALL | idx_name | NULL | 10173 |

**症状**：`idx_age` 明明存在，`possible_keys` 却是 NULL；`idx_name` 更迷惑——优化器"考虑过"它，最终 `key` 仍是 NULL，实际走全表扫描。

**原因**：索引里存的是**列的原值**的有序结构。`age + 1 = 31` 要先对每一行算一遍 `age + 1`，索引的有序性用不上，只能逐行过滤；`name = 123` 是隐式类型转换，MySQL 把 `name` 转成数字再比，等价于对列做了函数运算，同样用不上索引（回指 Q8）。

排查口诀：**索引列上不要做运算、不要套函数、不要让类型不一致**。三件事只要发生一件，索引就退化成摆设。
