# 第 2 章 集合框架：从底层结构到并发容器

> 一句话定位：集合是唯一一个"每一轮面试都会问、而且越问越深"的模块——从 ArrayList 的扩容倍率，能一直问到 ConcurrentHashMap 的多线程协助扩容。

## 一、本章考察重点概览 {#s1}

集合框架在面试中的定位，是检验你**是否真正读过 JDK 源码**。这一章有个很明显的分层：初级只会说"ArrayList 查询快、LinkedList 增删快"，中级能讲清扩容与树化，高级能说清 2 的幂、高低位拆分、CounterCell 分段计数。面试官通过这一章判断三件事：

1. **你是背结论还是理解机制。** "ArrayList 扩容 1.5 倍"是结论，"为什么是 1.5 而不是 2、扩容时 `Arrays.copyOf` 到底复制了什么"才是机制。后者答得出来，说明你读过 `grow()`。
2. **你对数字是否敏感。** 树化阈值 8、退化阈值 6、最小树化容量 64、默认容量 16、负载因子 0.75、并发度 16，这些数字背后都有理由。能说出理由的人和背下数字的人，追问两句就分开了。
3. **你有没有并发意识。** HashMap 线程不安全是常识，但"具体怎么坏"分三种：JDK 7 成环、JDK 8 覆盖、任何版本 size 都不准。能分开讲，才说明你真在高并发环境里踩过或分析过。

## 四、题目详解 {#s4}

### Q1. ArrayList 的底层结构与扩容机制是怎样的？（初级） {#q1}

> 前置：数组、扩容拷贝、均摊复杂度

**一句话结论**：ArrayList 用 `Object[] elementData` 连续存储元素，无参构造在 JDK 8 中延迟到首次 `add` 才分配容量 10，满了以后扩为原来的 1.5 倍（`oldCap + (oldCap >> 1)`），并通过 `Arrays.copyOf` 整数组复制迁移。

**先把话说白**：ArrayList 就是一个会自动变长的数组。数组的好处是按下标访问是一次地址计算，坏处是长度固定。ArrayList 的做法是：平时装在一个数组里，装不下了就换一个更大的数组，把旧的搬过去。所以"扩容"的本质不是数组变长，而是换数组。

**底层原理**：

1. **存储结构。** 只有一个核心字段 `transient Object[] elementData`，加一个 `int size` 记录实际元素个数。`elementData.length` 是容量，`size` 是元素数，两者不是一回事——这也是 `new ArrayList<>(100)` 之后 `size()` 仍是 0 的原因。数组声明为 `transient` 是因为序列化时只写出 size 个有效元素，不把整个容量写出去，`writeObject` 里做了定制。

2. **三个构造器的差异。** 无参构造在 JDK 8 中赋的是共享的空数组 `DEFAULTCAPACITY_EMPTY_ELEMENTDATA`，第一次 `add` 时才通过 `ensureCapacityInternal` 扩到 10；`new ArrayList<>(n)` 直接分配 `new Object[n]`；`new ArrayList<>(collection)` 用 `collection.toArray()` 再判断是否多留一格。JDK 6 及以前无参构造会立刻 `new Object[10]`，所以"ArrayList 默认容量 10"这句话在 JDK 8 里严格说是"首次扩容后的容量"。

3. **扩容的完整链路。** `add` 先 `ensureCapacityInternal(size + 1)`，计算最小需要容量，若超过当前数组长度就进 `grow(minCapacity)`：`newCapacity = oldCapacity + (oldCapacity >> 1)`，也就是 1.5 倍；若仍不够就用 `minCapacity`；若超过 `MAX_ARRAY_SIZE`（`Integer.MAX_VALUE - 8`）则走 `hugeCapacity` 判断是否直接抛 `OutOfMemoryError`。最后 `Arrays.copyOf` 复制。

4. **为什么是 1.5 倍而不是 2 倍。** 这是空间与时间的折中。2 倍增长会导致内存占用翻倍式上涨，容易在扩容瞬间触发一次大对象分配失败；1.5 倍在长期增长下总复制次数只比 2 倍多常数级，但峰值内存更平滑。另一个实际原因是 1.5 倍可以通过 `oldCap + (oldCap >> 1)` 用移位加加法实现，且多次扩容后的容量序列（10、15、22、33……）不会像 2 倍那样迅速逼近上限。

5. **代价与边界。** `Arrays.copyOf` 底层是 `System.arraycopy`，是 native 的内存块拷贝，单位是引用（4 或 8 字节），所以复制本身不涉及对象深拷贝——新旧数组共享同一批元素对象。真正的成本是：一次 O(n) 的拷贝 + 一次新数组分配 + 旧数组变成垃圾。所以能预估大小时一定要用 `new ArrayList<>(expectedSize)`，避免反复扩容。

```java
// 预估容量，避免 10→15→22 的反复拷贝
List<Order> list = new ArrayList<>(orders.size());
for (Order o : orders) {
    list.add(o);          // 不再触发扩容
}
```

**易混对比**：

| 维度 | 容量 capacity | 元素数 size |
| --- | --- | --- |
| 含义 | `elementData.length`，能装多少 | 实际存了几个 |
| 获取方式 | 无公开 API，只能反射或 `ensureCapacity` 间接控制 | `size()` |
| 何时变化 | 扩容时按 1.5 倍变 | 每次 add/remove 变 |
| 常见误解 | `new ArrayList<>(100)` 后 size 是 100 | 实际是 0 |

**面试追问**：
- 追问：`new ArrayList<>(100)` 会立刻分配数组吗？→ 答题要点：会，指定初始容量时直接 `new Object[100]`，只有无参构造才延迟分配。
- 追问：扩容时元素对象会被复制一份吗？→ 答题要点：不会，数组里存的是引用，`System.arraycopy` 复制的是引用值，对象本身还在堆上原位。
- 追问：`ArrayList` 删除元素为什么也慢？→ 答题要点：`remove(index)` 要用 `System.arraycopy` 把后面的元素整体左移，复杂度 O(n)，且 `size` 位置要置 null 帮助 GC。

### Q2. ArrayList 与 LinkedList 到底该选谁？（中级） {#q2}

> 前置：数组与链表、缓存局部性

**一句话结论**：除了"在头部或迭代器当前位置频繁插入删除"这一种场景，几乎所有情况都该选 ArrayList；两者的真实差距不在时间复杂度表，而在内存布局带来的 CPU 缓存命中率。

**先把话说白**：很多人背的是"ArrayList 查快改慢，LinkedList 查慢改快"。这句话只对了一半。LinkedList 的"改快"有个前提：你已经拿着那个节点的引用。如果只给一个下标，LinkedList 得先从头（或从尾）走一遍，定位本身就是 O(n)，定位完之后插入的 O(1) 已经没有意义了。

**底层原理**：

1. **结构差异。** ArrayList 是一块连续的引用数组；LinkedList 是 `Node<E>` 双向链表，每个节点含 `prev`、`item`、`next` 三个引用。在开启压缩指针（`-XX:+UseCompressedOops`，堆小于 32G 时默认开启）的情况下，对象头 12 字节加三个 4 字节引用再加对齐，一个 Node 大约占 24 字节，而 ArrayList 里一个元素只占 4 字节。存一百万个 Integer 引用，链表要多花约 20MB 在节点开销上。

2. **随机访问的真实成本。** ArrayList 的 `get(i)` 是一次 `elementData[i]`，即基址加偏移，通常 1~2 个时钟周期；LinkedList 的 `get(i)` 会先比较 `i < size/2` 决定从头还是从尾走，平均走 n/4 步，每步都要解引用 `next` 并判断是否为空。

3. **缓存局部性才是决定因素。** CPU 从内存取数据是按缓存行（Cache Line，通常 64 字节）整块加载的。ArrayList 的数组是连续的，一行能装下 16 个引用（压缩指针下），遍历时一次加载能命中后续十几次访问，硬件预取器还能识别顺序访问模式提前加载。LinkedList 的节点是 `new` 出来的，散落在堆的各处，每跳一个节点大概率是一次缓存未命中（Cache Miss），要等上百个周期。所以同样是"遍历一百万个元素"，ArrayList 常常快数倍，这不是常数因子的问题，是数量级的内存延迟差异。

4. **头插的真相。** `LinkedList.addFirst` 确实是 O(1)，`ArrayList.add(0, e)` 要整体右移 O(n)。但只有当你**持续在头部插入大量元素**时，这个差距才有意义。而即便在这种场景，`ArrayDeque` 通常是更好的选择——它用环形数组实现双端队列，头尾操作都是 O(1)，且没有链表节点的内存开销和缓存问题。LinkedList 唯一难以替代的场景是：用 `ListIterator` 在遍历过程中频繁插入删除当前元素，因为迭代器持有节点引用，此时才是真正的 O(1)。

5. **结论性的选择建议。** 绝大多数业务代码用 ArrayList；需要队列/栈用 ArrayDeque；需要按 key 快速查找用 HashMap；只有在明确测量出链表优势（比如实现 LRU 的双向链表、频繁在迭代位置增删）时才用 LinkedList。JDK 官方文档里 ArrayList 的注释也直接写了"LinkedList 在列表头部频繁插入时更快，但整体上 ArrayList 更常用"。

**易混对比**：

| 维度 | ArrayList | LinkedList |
| --- | --- | --- |
| 底层结构 | 连续 `Object[]` | 双向链表 Node |
| 随机访问 `get(i)` | O(1)，一次地址计算 | O(n)，需遍历定位 |
| 尾部追加 | 均摊 O(1)，偶尔扩容 O(n) | O(1)，但要 new 节点 |
| 头部插入 | O(n)，整体右移 | O(1) |
| 中间插入 | O(n) 移动 + O(1) 赋值 | O(n) 定位 + O(1) 链接 |
| 单元素内存开销 | 4 字节（压缩指针） | 约 24 字节 |
| 缓存友好度 | 高，顺序访问可预取 | 低，随机跳转易未命中 |
| 典型适用 | 列表、批量遍历、按索引读 | 迭代器位置频繁增删、双向链表结构 |

**面试追问**：
- 追问：LinkedList 的 `add(index, e)` 是 O(1) 吗？→ 答题要点：不是，定位是 O(n)，只有 `addFirst`/`addLast` 和迭代器内部的插入才是 O(1)。
- 追问：为什么说 ArrayDeque 比 LinkedList 更适合做队列？→ 答题要点：环形数组无节点分配、无 GC 压力、缓存友好，头尾操作都是 O(1)。
- 追问：ArrayList 线程安全吗？怎么变成线程安全？→ 答题要点：不安全，可用 `Collections.synchronizedList`（迭代仍需手动同步）或 `CopyOnWriteArrayList`（读多写极少）。

### Q3. HashMap 在 JDK 7 与 JDK 8 中的结构差异？（中级） {#q3}

> 前置：哈希表、链表、红黑树

**一句话结论**：JDK 7 是"数组 + 链表"且用头插法，JDK 8 变成"数组 + 链表 + 红黑树"并改用尾插法，同时把 hash 扰动从四次移位简化成一次，扩容从重新计算下标改成高低位拆分。

**先把话说白**：HashMap 本质是一个桶数组，key 的 hash 决定进哪个桶，多个 key 落到同一个桶就叫哈希冲突，冲突的 key 在桶里排成链表。JDK 7 的问题是链表太长时查询退化成 O(n)，而且头插法在并发扩容时会形成环。JDK 8 针对这两点分别改了：链表过长转红黑树，插入改成尾插。

**底层原理**：

1. **JDK 7 的结构。** `Entry<K,V>[] table`，每个 Entry 有 `hash`、`key`、`value`、`next` 四个字段。插入时若桶为空则直接放，否则遍历链表，用 `hash` 相等且 `equals` 相等判断是否覆盖，没找到就**头插**到链表最前面。头插的动机是"刚插入的元素更可能被再次访问"，同时省去遍历到尾部的时间，但它导致了扩容时的链表反转。

2. **JDK 8 的结构。** `Node<K,V>[] table`，Node 同样是四字段链表节点，另有 `TreeNode` 继承 `LinkedHashMap.Entry` 再继承 `Node`，额外维护 `parent`、`left`、`right`、`prev`、`red` 五个字段。当某个桶的链表长度达到 8 且数组长度达到 64 时，`treeifyBin` 会把链表转成红黑树，查询从 O(n) 降到 O(log n)。插入改为**尾插**，遍历到链表末尾再挂上。

3. **put 的完整流程（JDK 8）。** 先判断 table 是否为空，空则 `resize()` 初始化；计算 `(n-1) & hash` 得到桶下标；桶为空则 CAS 或直接放新节点；桶头 `hash` 相同且 `key` 相等则覆盖；若是 `TreeNode` 走红黑树插入；否则遍历链表，到尾就尾插，插入后判断是否达到树化阈值；最后 `++size`，超过 `threshold` 就 `resize()`。

4. **为什么 JDK 8 要引入红黑树。** 链表查询是 O(n)，在 hash 被人为构造（如恶意请求参数）或分布极差时，桶会退化成一条长链，查询从 O(1) 变成 O(n)，这既是性能问题也是安全隐患（哈希碰撞拒绝服务攻击）。红黑树保证 O(log n)，且插入删除的旋转次数是常数级，比 AVL 树更适合写多的场景。

5. **改动的代价。** TreeNode 的内存占用约为普通 Node 的两倍（多了五个字段），所以树化必须"很少发生"才划算，这也是阈值定在 8 的原因之一。另外树化与退化都有成本，代码复杂度显著上升，`putTreeVal`、`split`、`untreeify` 这些方法在 JDK 7 里根本不存在。

**易混对比**：

| 维度 | JDK 7 | JDK 8 |
| --- | --- | --- |
| 数据结构 | 数组 + 链表 | 数组 + 链表 + 红黑树 |
| 节点类型 | `Entry` | `Node` / `TreeNode` |
| 插入方式 | 头插 | 尾插 |
| hash 扰动 | 四次移位异或 | 一次 `h ^ (h >>> 16)` |
| 下标计算 | `indexFor(h, length)` 即 `h & (length-1)` | 同为 `(n-1) & hash` |
| 扩容迁移 | 重新计算每个节点下标，链表会反转 | 按 `hash & oldCap` 拆 lo/hi 两条链 |
| 并发后果 | 可能形成环形链表，get 死循环 | 不会成环，但会覆盖丢数据 |

**面试追问**：
- 追问：JDK 8 为什么把 head 插改成尾插？→ 答题要点：头插在并发扩容时会让链表反转，两个线程互相引用形成环；尾插保持顺序，避免成环（但不解决线程安全）。
- 追问：红黑树节点什么时候退化回链表？→ 答题要点：扩容拆分后树节点数小于等于 6 时 `untreeify`，删除时也按 6 判断。
- 追问：为什么 TreeNode 还要保留 `next` 指针？→ 答题要点：树化后仍保留链表结构，便于遍历和退化，`prev` 则用于删除时快速找前驱。

### Q4. hash 扰动函数为什么右移 16 位异或？（中级） {#q4}

> 前置：哈希码、位运算、桶下标

**一句话结论**：`(h = key.hashCode()) ^ (h >>> 16)` 的作用是把 32 位 hash 的高 16 位折到低 16 位，让高位也参与桶下标计算；因为容量通常远小于 2^16，下标只由低位决定，不扰动就会浪费 hash 的高半区信息。

**先把话说白**：算桶下标用的是 `(n-1) & hash`，`n-1` 是形如 `0000...1111` 的掩码。容量 16 时掩码只有低 4 位，也就是说一个 32 位的 hash 只有最后 4 位有用，高 28 位全被丢掉。如果两个 key 的 hashCode 只有高 16 位不同、低 16 位相同，它们必然进同一个桶。扰动的目的就是让被丢掉的高位信息"折叠"到低位里去。

**底层原理**：

1. **掩码决定了有效位数。** 容量为 n 时，`n-1` 的二进制是 log2(n) 个 1。n=16 时只有 4 位有效，n=1024 时 10 位。所以无论 hashCode 分布得多好，只要低位相同就必然冲突。而 `Object.hashCode()` 的默认实现（HotSpot 中基于对象地址或线程本地随机数生成）并不能保证低位均匀。

2. **右移 16 位的选择依据。** int 是 32 位，右移 16 位正好把高半区移到低半区，与原值异或后，结果的低 16 位同时包含原高位与原低位的混合信息。选 16 而不是 8 或 24，是因为容量在现实中绝大多数情况不超过 2^16 = 65536（即 6 万多个桶，对应约 5 万元素、负载因子 0.75），此时下标最多用到低 16 位，右移 16 位刚好覆盖"会被用到的那部分"与"完全被丢弃的那部分"的边界。

3. **为什么用异或而不是与、或。** 与运算会让结果偏向 0（大量位被清零），或运算会让结果偏向 1，两者都会破坏均匀性。异或的可逆性最好：每一位有 50% 概率翻转，输入变化时输出变化最分散，是混合（mixing）操作里代价最低、效果最稳的选择。

4. **与 JDK 7 的对比。** JDK 7 的 `hash()` 做了四次移位异或：`h ^= (h>>>20) ^ (h>>>12); return h ^ (h>>>7) ^ (h>>>4);`，把高低位混合得更彻底，但代价是四次移位加四次异或。JDK 8 认为在红黑树兜底的前提下，一次扰动已经够用，于是简化成一次，把省下的指令留给更热的路径。这是一次典型的"用兜底机制换常规路径性能"的取舍。

5. **边界：扰动不能解决所有问题。** 如果用户自己重写了 `hashCode()` 返回常量（比如所有对象都返回 1），扰动再狠也没用，全部落在一个桶，此时只能靠红黑树把 O(n) 降到 O(log n)。另外 `String.hashCode()` 是确定性的（`s[0]*31^(n-1) + ...`），攻击者可以刻意构造碰撞串，这也是 JDK 8 引入红黑树的现实动机之一。

```java
static final int hash(Object key) {
    int h;
    // 高 16 位与低 16 位异或，让高位参与后续的 (n-1) & hash
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
// 容量 16 时下标只取低 4 位，不扰动则高 28 位完全无效
int index = (16 - 1) & hash(key);
```

**易混对比**：

| 方案 | 指令数 | 混合效果 | 采用版本 |
| --- | --- | --- | --- |
| 不扰动，直接用 hashCode | 0 | 高位全丢 | 无 |
| 一次 `h ^ (h>>>16)` | 2 | 高低 16 位混合 | JDK 8 |
| 四次移位异或 | 8 | 混合更彻底 | JDK 7 |
| 取模 `hash % n` | 1 次除法 | 依赖全部位，但慢 | 非 2 的幂时 |

**面试追问**：
- 追问：为什么不用 `hash % n` 代替位运算？→ 答题要点：除法指令约 20 个周期，位与只要 1 个；只有在 n 不是 2 的幂时才必须取模（如 `HashTable` 用素数容量）。
- 追问：`key == null` 为什么返回 0？→ 答题要点：null 的 hash 定为 0，落在 0 号桶，避免 NPE，同时让 HashMap 支持 null key。
- 追问：扰动函数能保证不冲突吗？→ 答题要点：不能，只能降低冲突概率；冲突最终由链表和红黑树处理。

### Q5. 为什么 HashMap 容量必须是 2 的幂？（中级） {#q5}

> 前置：位运算、取模、索引计算

**一句话结论**：容量为 2 的幂时，`(n-1) & hash` 与 `hash % n` 结果完全等价，但位运算快一个数量级；同时 `n-1` 是全 1 掩码，能让 hash 的每一位都参与下标，扩容时也只需判断 `hash & oldCap` 一位就能确定新位置。

**先把话说白**：HashMap 要把 hash 映射到 0 到 n-1 的桶下标。取模是最直观的做法，但除法在 CPU 上很慢。当 n 是 2 的幂时，`n-1` 的二进制全是 1，此时"与"运算的结果恰好等于取模的结果——这是二进制的一个恒等式，不是近似。

**底层原理**：

1. **等价性的数学证明。** 设 n = 2^k，则 n-1 的低 k 位全是 1、其余位全是 0。`hash & (n-1)` 保留了 hash 的低 k 位，丢弃高位，结果必然落在 `[0, 2^k - 1]`。而 `hash % 2^k` 在二进制下的含义正是"取低 k 位"，两者完全一致。注意这个等价性只对 2 的幂成立：n=15 时 `n-1=1110`，最低位恒为 0，所有奇数 hash 永远进不了 1 号桶，一半的桶被浪费。

2. **性能差异。** `idiv`/`irem` 指令在现代 x86 上约 20~40 个周期，`and` 只要 1 个周期。HashMap 的 get/put 是最高频的操作，这个差距会被放大到整个应用的吞吐上。这是"用容量约束换运算速度"的典型设计。

3. **扩容的额外红利。** 因为容量翻倍后 n-1 只是多了一个 1 位，元素的新下标只有两种可能：原位置 j，或 j + oldCap。判断依据只有一位：`(e.hash & oldCap) == 0` 则留在原位，否则移到高位。这让 JDK 8 的扩容不需要重新计算 hash、不需要重新取模，只要把一条链拆成两条。如果容量是素数（如 Hashtable 的 11），扩容后必须对每个节点重新 `% newCap`，成本高得多。

4. **容量是怎么保证的。** `tableSizeFor(int cap)` 用五次无符号右移加或运算，把传入值"向上取整"到最近的 2 的幂：`n |= n>>>1; n |= n>>>2; ... n |= n>>>16;`，本质是把最高位的 1 向右"抹平"，最后加 1。所以 `new HashMap<>(17)` 的实际容量是 32。`putAll` 时还会用 `(int)((float)size/0.75f + 1.0f)` 预估，避免多次扩容。

5. **代价与边界。** 2 的幂意味着容量只能是 16、32、64……不能让容量贴合素数以获得更好的散列性质，所以必须靠扰动函数弥补低位信息的不足。这是在"运算速度"和"分布均匀"之间做的交换：用一次廉价的异或，换掉昂贵的取模和素数容量管理。

```java
// JDK 8 源码：把 cap 向上取整到 2 的幂
static final int tableSizeFor(int cap) {
    int n = cap - 1;          // 减 1 防止 cap 本身已是 2 的幂时翻倍
    n |= n >>> 1;  n |= n >>> 2;
    n |= n >>> 4;  n |= n >>> 8;  n |= n >>> 16;
    return (n < 0) ? 1 : (n >= MAXIMUM_CAPACITY) ? MAXIMUM_CAPACITY : n + 1;
}
// tableSizeFor(17) == 32，tableSizeFor(16) == 16
```

**易混对比**：

| 维度 | 容量为 2 的幂（HashMap） | 容量为素数（Hashtable） |
| --- | --- | --- |
| 下标计算 | `hash & (n-1)`，1 个周期 | `(hash & 0x7FFFFFFF) % n`，除法 |
| 分布均匀性 | 依赖扰动函数弥补 | 素数天然减少规律性冲突 |
| 扩容成本 | 拆 lo/hi 两条链，O(1) 判断 | 每个节点重新取模 |
| 容量取值 | 16、32、64…… | 11、23、47…… |

**面试追问**：
- 追问：如果容量不是 2 的幂会怎样？→ 答题要点：`n-1` 不再是全 1 掩码，部分桶永远为空，且 `&` 不再等价于取模，结果错误。
- 追问：负载因子为什么是 0.75？→ 答题要点：空间与冲突概率的折中，0.75 时泊松分布下链表长度期望较低；调高省空间但冲突多，调低查询快但浪费内存。
- 追问：`new HashMap<>(1000)` 的真实容量是多少？→ 答题要点：1024，`tableSizeFor` 向上取整到 2 的幂，阈值同时被设为 1024。

### Q6. JDK 8 扩容时的高低位拆分是怎么做的？（高级） {#q6}

> 前置：扩容、哈希高位、链表拆分

**一句话结论**：扩容时把旧桶的链表按 `(e.hash & oldCap) == 0` 拆成 lo 和 hi 两条链，lo 链留在原下标 j，hi 链移到 `j + oldCap`，全程不重新计算 hash，也不改变节点相对顺序。

**先把话说白**：容量翻倍后，掩码从 k 个 1 变成 k+1 个 1，多出来的那位恰好是 `oldCap` 对应的那一位。所以一个元素的新下标只取决于 hash 在 oldCap 这一位上是 0 还是 1：0 就原地不动，1 就往后挪一个 oldCap。这就像把一排人按"新加的那个条件"分成两队，而不是所有人重新排队。

**底层原理**：

1. **掩码视角。** 旧容量 16，掩码 `1111`，下标 = hash 的低 4 位。新容量 32，掩码 `11111`，下标 = 低 5 位。两者只差最高那一位（值为 16 的那位）。所以新下标 = 旧下标 + (该位为 1 ? 16 : 0)。而"该位是否为 1"正好可以用 `hash & oldCap` 判断，因为 oldCap 的二进制就是那一个 1。

2. **lo/hi 两条链的构建。** 遍历旧桶的链表，用四个引用 `loHead/loTail`、`hiHead/hiTail`。每个节点判断 `(e.hash & oldCap) == 0`，为 0 挂到 lo 链尾，否则挂到 hi 链尾。遍历结束后，lo 链放到 `newTab[j]`，hi 链放到 `newTab[j + oldCap]`。整个过程只遍历一次，每个节点做一次与运算和两次指针赋值。

3. **为什么用尾插而不是头插。** 尾插保持节点在链表中的相对顺序。JDK 7 的 `transfer` 用头插，扩容后链表整体反转；在并发场景下，两个线程同时 transfer 可能让 A 指向 B、B 又指向 A，形成环，后续 `get` 落到这个桶就会无限循环，CPU 打满。JDK 8 改成尾插后，这个特定的死循环问题消失了。

4. **树节点的拆分。** 如果旧桶是 `TreeNode`，走 `split` 方法：先按同样规则把树节点分成 lo/hi 两组并统计数量，若某组数量小于等于 `UNTREEIFY_THRESHOLD`（6）就 `untreeify` 退化成链表，否则若另一组不为空就重新 `treeify`。这里体现了"扩容后冲突可能自然缓解"的思路：原本挤在一个桶里的元素被分到两个桶，树可能就不需要了。

5. **并发下的边界。** JDK 8 的 resize 依然不是线程安全的。多个线程同时扩容可能操作同一个 `newTab`，互相覆盖；`size` 的自增也不是原子的。ConcurrentHashMap 才通过 `ForwardingNode` 和 `sizeCtl` 把扩容变成可协作的任务，这一点在 Q11 展开。

```java
// JDK 8 resize 中拆分单个桶的核心逻辑（简化）
Node<K,V> loHead = null, loTail = null, hiHead = null, hiTail = null;
for (Node<K,V> e = oldTab[j]; e != null; e = e.next) {
    Node<K,V> next = e.next;
    if ((e.hash & oldCap) == 0) {          // 该位为 0，留在原位
        if (loTail == null) loHead = e; else loTail.next = e;
        loTail = e;
    } else {                                // 该位为 1，移到 j + oldCap
        if (hiTail == null) hiHead = e; else hiTail.next = e;
        hiTail = e;
    }
}
if (loTail != null) { loTail.next = null; newTab[j] = loHead; }
if (hiTail != null) { hiTail.next = null; newTab[j + oldCap] = hiHead; }
```

**易混对比**：

| 维度 | JDK 7 的 transfer | JDK 8 的 resize |
| --- | --- | --- |
| 下标计算 | 对每个节点重新 `indexFor(hash, newCap)` | 只判断 `hash & oldCap` 一位 |
| 插入方式 | 头插，链表反转 | 尾插，顺序不变 |
| 遍历次数 | 每个桶遍历一次 | 每个桶遍历一次 |
| 并发后果 | 可能成环，get 死循环 | 不成环，但可能丢节点 |
| 树处理 | 无 | `split` 拆分并可能退化 |

**面试追问**：
- 追问：为什么 `hash & oldCap` 能判断新下标？→ 答题要点：新掩码比旧掩码多一位，该位权重正好是 oldCap，为 1 则新下标多 oldCap。
- 追问：扩容后链表顺序会变吗？→ 答题要点：JDK 8 不变，lo 链和 hi 链都保持原相对顺序；JDK 7 因为头插会反转。
- 追问：JDK 8 扩容就不会死循环了吗？→ 答题要点：不会成环，但并发下仍可能读到中间态、丢数据、size 不准，依然不能用。

### Q7. 树化阈值为什么是 8、退化是 6、最小树化容量 64？（高级） {#q7}

> 前置：红黑树、链表退化、泊松分布

**一句话结论**：8 是在理想 hash 分布下链表长度达到该值的概率极低（源码注释给出的量级是千万分之一以下），树化只作为极端情况的兜底；退化用 6 而不是 7 是为了留出缓冲带防止频繁抖动；64 是因为数组太小时冲突的根因是容量不足，应先扩容而不是树化。

**先把话说白**：这三个数字不是拍脑袋定的，它们分别回答三个问题：什么时候值得付出红黑树的内存和旋转成本（8）、什么时候可以安全地退回去（6）、以及冲突到底是"hash 不好"还是"桶太少"（64）。

**底层原理**：

1. **8 的来源是概率。** HashMap 源码的注释里写明了：在理想的随机 hash 下，桶内节点数服从泊松分布（Poisson Distribution），参数约为 0.5，长度达到 8 的概率约为 0.00000006。也就是说，正常情况下几乎永远不会树化。反过来说，如果真的树化了，说明 hash 分布出现了严重问题（恶意构造或 `hashCode` 实现糟糕），此时必须有一个 O(log n) 的兜底。所以树化阈值不是为了"优化常规性能"，而是为了"防住异常情况"。

2. **为什么不设成更小，比如 4 或 6。** 树节点（TreeNode）比链表节点多五个引用字段，内存约为两倍；插入时要维护红黑树性质，可能触发旋转和重新着色；遍历时树的常数因子也比链表大。如果阈值太小，正常业务里会频繁树化又退化，白白付出内存和 CPU。设成 8，意味着"宁可让极端情况慢一点，也不让常规情况变重"。

3. **退化阈值 6 的缓冲作用。** 如果树化是 8、退化也是 8，那么当桶内节点数在 8 附近反复增减时，就会在"树化—退化—树化"之间抖动，每次都要重建结构，代价很大。取 6 留出两个节点的缓冲带，让状态变化有迟滞（hysteresis），这是控制系统里的常见手法。删除节点时如果发现树太小，也会用 6 判断是否 `untreeify`。

4. **最小树化容量 64 的含义。** `treeifyBin` 里先判断 `tab.length < MIN_TREEIFY_CAPACITY`，如果是，就不树化而是直接 `resize()`。原因是：数组只有 16 或 32 时，一个桶里挤了 8 个元素，更可能的原因是桶太少（负载因子已经超过 0.75 却还没扩容），而不是 hash 分布差。扩容后元素被拆到新桶，冲突自然缓解，比维护一棵树更划算。只有容量达到 64 以后仍然冲突，才认为是真正的 hash 问题。

5. **三者的协同。** put 时链表长度到 8 → 检查容量是否到 64 → 不到就扩容，到了就树化；删除或扩容拆分后节点数降到 6 → 退化回链表。这套规则保证了：容量不足优先扩容，容量足够才用树，且树与链表之间不会来回抖。

**易混对比**：

| 常量 | 值 | 作用 | 设定依据 |
| --- | --- | --- | --- |
| `TREEIFY_THRESHOLD` | 8 | 链表转树的节点数 | 泊松分布下概率极低，仅作兜底 |
| `UNTREEIFY_THRESHOLD` | 6 | 树退化回链表的节点数 | 留缓冲带，防树化/退化抖动 |
| `MIN_TREEIFY_CAPACITY` | 64 | 允许树化的最小数组长度 | 容量小时冲突源于桶少，应先扩容 |
| `DEFAULT_INITIAL_CAPACITY` | 16 | 默认桶数组长度 | 与 0.75 负载因子配合，阈值为 12 |
| `LOAD_FACTOR` | 0.75 | 触发扩容的元素占比 | 空间与冲突概率的折中 |

**面试追问**：
- 追问：为什么树化阈值和退化阈值不一样？→ 答题要点：留迟滞区间，避免节点数在阈值附近波动时反复转换结构。
- 追问：桶里只有 7 个元素但数组长度 16，会树化吗？→ 答题要点：不会，先判断 `MIN_TREEIFY_CAPACITY`，容量不足时选择扩容。
- 追问：为什么说红黑树而不是 AVL 树？→ 答题要点：红黑树插入删除的旋转次数更少（最多 3 次旋转），写多场景更稳，查询 O(log n) 与 AVL 同阶。

### Q8. HashMap 线程不安全具体表现在哪？（中级） {#q8}

> 前置：竞态条件、扩容、JDK 7 死循环

**一句话结论**：JDK 7 在并发扩容时头插会形成环形链表，导致 `get` 死循环打满 CPU；JDK 8 改成尾插后不再成环，但并发 put 仍会互相覆盖丢数据，且 `++size` 非原子导致 size 长期不准，扩容期间还可能读到 null。

**先把话说白**："HashMap 线程不安全"这句话本身没有信息量。面试官想听的是：不安全会以什么形式暴露？是报错、是丢数据、还是卡死？不同版本答案还不一样。能把三种故障模式分开讲，才算真理解。

**底层原理**：

1. **JDK 7 的成环机制。** `transfer()` 里用头插把旧链表的节点搬到新桶：`e.next = newTable[i]; newTable[i] = e;`。假设线程 A 和 B 同时对同一个桶做 transfer，A 读到 `e = a`、`next = b` 后被挂起；B 完成整个迁移，链表变成 `b -> a`；A 恢复后继续按自己手里的 `next` 指针操作，把 a 又插到 b 前面，最终可能形成 `a -> b -> a` 的环。之后任何落到这个桶的 `get` 都会在 `for (Entry e = table[i]; e != null; e = e.next)` 里无限循环，表现为 CPU 100%、线程栈停在 `HashMap.getEntry`。

2. **JDK 8 的覆盖丢数据。** `putVal` 里判断桶为空时直接 `tab[i] = newNode(...)`，这个"判断 + 赋值"不是原子的。两个线程同时判断桶为空，都创建节点，后写的覆盖先写的，前一个元素凭空消失。类似地，两个线程同时对同一个桶做尾插，可能其中一个节点的 `next` 赋值丢失。这类问题的特点是**不报错、不异常，只是数据变少**，比死循环更难排查。

3. **size 永远不准。** `++size` 是"读—加—写"三步，不是原子操作。多线程并发 put 时，两个线程可能读到同一个旧值，各自加一后写回，最终 size 比实际元素数小。而 `size` 又参与扩容判断（`++size > threshold`），size 偏小会导致扩容滞后，进一步加剧冲突。

4. **扩容期间的可见性问题。** `table` 字段不是 `volatile`，`resize()` 把 `newTab` 赋值给 `table` 的瞬间，其他线程可能看到旧数组、新数组，或看到数组引用已更新但元素还没搬完的中间状态，读到 null。`Node.next` 也不是 `volatile`，链表节点的挂载对其他线程不保证立即可见。

5. **正确的替代方案。** 单线程或确定无共享用 HashMap；读多写少且能接受弱一致用 `Collections.synchronizedMap`（全表锁，迭代需手动同步）；高并发用 `ConcurrentHashMap`（桶级锁 + CAS）；需要有序且并发用 `ConcurrentSkipListMap`。注意 `Hashtable` 虽然线程安全但是全表锁且不允许 null，早已不推荐。

**易混对比**：

| 版本 / 容器 | 并发下的具体故障 | 是否抛异常 | 典型现象 |
| --- | --- | --- | --- |
| JDK 7 HashMap | 头插成环 | 否 | get 死循环，CPU 100% |
| JDK 8 HashMap | 桶赋值覆盖、尾插丢节点 | 否 | 元素莫名减少，size 偏小 |
| 任意版本 HashMap | `++size` 非原子 | 否 | size 与实际不符，扩容滞后 |
| Hashtable | 无（全表 synchronized） | 否 | 性能差，串行化 |
| ConcurrentHashMap | 弱一致，size 是估算值 | 否 | `size()` 可能不含并发写入 |

**面试追问**：
- 追问：JDK 8 的 HashMap 还会死循环吗？→ 答题要点：单次 put 不会成环，但如果在并发扩容期间持续写入，仍可能出现结构异常；"不死循环"不等于"线程安全"。
- 追问：为什么 `Collections.synchronizedMap` 迭代还要手动加锁？→ 答题要点：它只给单个方法加锁，复合操作（遍历）需要自己 `synchronized(map)` 包住。
- 追问：`ConcurrentHashMap` 能完全替代 HashMap 吗？→ 答题要点：不能，它不允许 null key/value，单线程下还有额外开销，无共享时没必要用。

### Q9. ConcurrentHashMap 7 与 8 的实现差异？（高级） {#q9}

> 前置：分段锁、CAS、`synchronized`

**一句话结论**：JDK 7 用 Segment 数组做分段锁，锁粒度是一个 Segment（默认 16 段，并发度固定）；JDK 8 取消 Segment，直接用 Node 数组，桶为空时 CAS 插入、桶非空时 synchronized 锁住桶头节点，锁粒度细化到单个桶，并引入红黑树与多线程协助扩容。

**先把话说白**：分段锁的思路是"把一张大表切成 16 张小表，每张小表一把锁"，不同小表可以同时写。问题是并发度在初始化时就固定了，而且一张表里的热点 key 仍然会锁住整个段。JDK 8 改成"每个桶一把锁"：只有落到同一个桶的写入才互斥，粒度细了一个数量级，且并发度随容量增长。

**底层原理**：

1. **JDK 7 的 Segment 结构。** `ConcurrentHashMap` 内部是一个 `Segment<K,V>[] segments`，每个 Segment 继承 `ReentrantLock`，内部又是一个 `HashEntry[]` 数组。定位需要两次 hash：先 `hash >>> segmentShift & segmentMask` 找到段，再用 `hash & (table.length-1)` 找到段内桶。写操作 `lock()` 住整个 Segment，读操作不加锁（HashEntry 的 `value` 和 `next` 是 `volatile`）。并发度等于 Segment 数量，构造时指定，默认 16，之后不能改。

2. **JDK 8 的锁策略。** 结构退化成和 HashMap 类似的 `Node[] table`，但节点加了 `volatile`。put 时的分支是：桶为空 → `casTabAt` 用 CAS 放入新节点，失败则自旋重试；桶头 hash 为 `MOVED`（-1）→ 说明正在扩容，当前线程去 `helpTransfer`；否则 `synchronized (f)` 锁住桶头节点，在锁内做链表遍历或红黑树插入。锁的对象是桶的第一个节点，不同桶完全并行。

3. **为什么从 ReentrantLock 换成 synchronized。** JDK 6 之后 `synchronized` 做了大量优化（偏向锁、轻量级锁、锁消除、自适应自旋），在"锁持有时间极短、竞争不激烈"的场景下性能已不输 `ReentrantLock`，而且不需要在对象头之外额外分配 AQS 结构，内存更省。ConcurrentHashMap 的临界区只有"遍历一个桶并插入"这几步，正好符合这个特征。

4. **红黑树的引入。** 和 HashMap 一样，当桶内节点数达到 8 且容量达到 64 时树化，用 `TreeBin` 包装红黑树（`TreeBin` 本身作为桶头，持有 root 和读写锁状态）。`TreeBin` 内部还有一个简单的读写锁机制，让读操作在树旋转期间也能安全进行，这是它比 HashMap 的 TreeNode 更复杂的地方。

5. **弱一致性。** `get` 不加锁，依赖 `volatile` 读，所以可能读到正在插入的中间状态；`size()` 返回的是估算值，并发写入时不一定精确；迭代器是弱一致的，遍历过程中能看到部分新数据，但不会抛 `ConcurrentModificationException`。这些不是缺陷，而是为吞吐做的取舍——要强一致就得全局加锁。

**易混对比**：

| 维度 | JDK 7 ConcurrentHashMap | JDK 8 ConcurrentHashMap |
| --- | --- | --- |
| 结构 | Segment 数组 + HashEntry 数组 | Node 数组 + 链表 / 红黑树 |
| 锁粒度 | 单个 Segment | 单个桶（桶头节点） |
| 锁实现 | `ReentrantLock` | CAS + `synchronized` |
| 并发度 | 固定为 Segment 数（默认 16） | 随 table 长度增长 |
| 空桶插入 | 段内加锁 | CAS 无锁 |
| 扩容 | 段内独立扩容，单线程 | 多线程协助 `helpTransfer` |
| size 统计 | 两次无锁尝试 + 加锁兜底 | `baseCount` + `CounterCell` |
| 复杂度 | 较低 | 高（引入 ForwardingNode、TreeBin） |

**面试追问**：
- 追问：JDK 8 的锁会不会退化？→ 答题要点：同桶高并发时 `synchronized` 会膨胀为重量级锁，但粒度是单桶，影响面远小于 Segment。
- 追问：为什么 key 和 value 都不允许 null？→ 答题要点：并发下 `get` 返回 null 无法区分"不存在"和"值为 null"，无法用 `containsKey` 二次确认（中间可能被改），索性禁止。
- 追问：`ConcurrentHashMap` 的 `get` 为什么不需要加锁？→ 答题要点：`Node.val` 与 `Node.next` 是 `volatile`，读线程能看到已发布的节点；链表挂载是先改 next 再发布，不会读到半个节点。

### Q10. ConcurrentHashMap 的 size 怎么统计？（高级） {#q10}

> 前置：分片计数、弱一致性、`LongAdder`

**一句话结论**：JDK 8 用 `baseCount` 加一个 `CounterCell[]` 数组做分段计数：先 CAS 更新 `baseCount`，失败则按线程探针哈希随机选一个 `CounterCell` 累加，`size()` 时把 `baseCount` 与所有非空 cell 求和，本质是 `LongAdder` 的思想。

**先把话说白**：如果所有线程都去 CAS 同一个 `size` 变量，高并发下会疯狂失败重试，这个变量就成了新的热点。解决办法是"分散写、汇总读"：每个线程挑一个自己的小格子加一，读的时候把所有格子加起来。写散了，读贵一点，但读远少于写。

**底层原理**：

1. **为什么不能简单加锁。** 加一把全局锁统计 size，会让所有 put/remove 串行化，直接抹掉分段锁带来的并发收益。用 `AtomicLong` 做 CAS 自增，在几十个线程同时写时失败率极高，CAS 自旋会烧 CPU。

2. **`addCount` 的两条路径。** put/remove 完成后调用 `addCount(1L, binCount)`：先尝试 `CAS(baseCount, b, b+x)`，成功就结束；失败说明有竞争，进入 `fullAddCount`，用线程的 `ThreadLocalRandom.getProbe()` 作为哈希，定位到 `CounterCell` 数组的某个槽，对该槽做 CAS 累加；槽为空就新建 cell 并用 CAS 放进数组；数组不够大（发生多次冲突）就扩容 `CounterCell[]`。

3. **`CounterCell` 的缓存行填充。** `CounterCell` 内部只有一个 `volatile long value`，但它继承自一个空实现的类，配合 `@sun.misc.Contended` 注解（JDK 8 内部使用）做缓存行填充，避免两个 cell 落在同一条 64 字节缓存行上互相"伪共享"（False Sharing）。伪共享会让 CAS 在缓存一致性协议下反复失效，是分段计数能不能生效的关键细节。

4. **`sumCount` 的读逻辑。** 遍历 `counterCells` 求和，加上 `baseCount`。这个过程中可能有线程正在写，所以结果是一个**近似值**。`size()` 的注释明确写了返回的是估算值（an estimate），并发场景下不应依赖它做精确判断，需要精确计数应该用 `mappingCount()` 或外部计数器。

5. **与扩容的耦合。** `addCount` 还负责检查是否需要扩容：当 `sumCount() >= sizeCtl`（阈值）时，CAS 把 `sizeCtl` 改成一个负的扩容戳，进入 `transfer`。`sizeCtl` 在 JDK 8 里身兼三职：负数表示正在扩容（高 16 位是扩容戳，低 16 位是参与线程数减一）、-1 表示正在初始化、正数表示下次扩容的阈值。

```java
// 简化的计数模型，与 LongAdder 同构
long sum = baseCount;                       // 基础计数，低竞争时都走这里
CounterCell[] cs = counterCells;
if (cs != null) {
    for (CounterCell c : cs) {
        if (c != null) sum += c.value;      // 分散的增量，读时汇总
    }
}
```

**易混对比**：

| 方案 | 写竞争 | 读成本 | 精确性 |
| --- | --- | --- | --- |
| `AtomicLong` 全局 CAS | 高，热点集中 | 低 | 精确 |
| 全局锁 | 极高，串行化 | 低 | 精确 |
| `baseCount` + `CounterCell` | 低，分散到多槽 | 需遍历求和 | 近似 |
| JDK 7 Segment 累加 | 中，按段加锁 | 需锁所有段 | 相对精确 |

**面试追问**：
- 追问：`size()` 和 `mappingCount()` 有什么区别？→ 答题要点：`size()` 返回 int，超过 `Integer.MAX_VALUE` 会截断；`mappingCount()` 返回 long，是大容量场景的正确选择。
- 追问：为什么需要缓存行填充？→ 答题要点：多个 cell 在同一缓存行时，一个核的写会让其他核的副本失效，CAS 反复失败，填充后各自独占一行。
- 追问：`sizeCtl` 一个字段怎么表达这么多状态？→ 答题要点：用符号区分——负数表示扩容/初始化，正数表示阈值；负数的低 16 位再编码参与线程数。

### Q11. ConcurrentHashMap 扩容时多线程如何协助？（高级） {#q11}

> 前置：扩容戳、节点迁移、`ForwardingNode`

**一句话结论**：扩容时先把 `sizeCtl` 置为负的扩容戳，迁移完的桶放一个 `ForwardingNode`（hash 为 -1）标记；其他线程 put 时遇到 `ForwardingNode` 就调用 `helpTransfer` 领取一段桶区间一起迁移，迁完后最后一个线程做收尾并把 `table` 指向新数组。

**先把话说白**：单线程扩容要搬完整张表，元素多的时候停顿明显。既然多核都在，那就把桶切成若干段，谁有空谁领一段搬——这就是"协助扩容"。`ForwardingNode` 相当于在搬空的桶上贴了张条子："此处已搬走，请去新表找，顺便帮我也搬几段。"

**底层原理**：

1. **扩容的启动。** `addCount` 发现总量超过阈值，用 CAS 把 `sizeCtl` 改成一个负数。这个负数的低 16 位记录参与线程数减一，高位是扩容戳（`resizeStamp`，与容量相关），用来区分"同一轮扩容"，防止过期线程重复参与。

2. **任务切分。** `transfer` 里维护一个 `transferIndex` 游标，从旧数组末尾往前分配区间。每个线程用 CAS 把 `transferIndex` 减 `stride`（步长，至少 16），领到 `[transferIndex, transferIndex+stride)` 这一段桶，逐个迁移。这种"倒序领取 + CAS 扣减"的设计让多个线程天然不重叠，且不需要额外的任务队列。

3. **`ForwardingNode` 的作用。** 每个桶迁移完成后，在旧表的该位置放一个 `ForwardingNode`，它持有 `nextTable` 引用，且 `hash` 固定为 `MOVED`（-1）。三处会用到它：
   - put 遇到它 → 说明正在扩容，调用 `helpTransfer` 参与；
   - get 遇到它 → 直接去 `nextTable` 里查，保证扩容期间读操作可用；
   - 其他线程的 transfer 遇到它 → 跳过，说明这段已经被别人迁完。

4. **`helpTransfer` 的准入判断。** 线程不是无条件帮忙：先检查 `sizeCtl` 的高位扩容戳是否与当前 `table` 匹配，低 16 位记录的线程数是否还没到上限（`MAX_RESIZERS`），`transferIndex` 是否还有剩余区间。都满足才 CAS 把线程数加一并加入迁移；否则直接返回，避免无意义的空转。

5. **收尾。** 每个线程迁完自己那段后，把 `sizeCtl` 的计数减一；最后一个退出的线程（计数归零）负责把 `table` 指向 `nextTable`，把 `nextTable` 置空，并重算新的阈值。这一步必须是单线程完成，否则会出现多个线程同时替换 `table` 的问题。

**易混对比**：

| 机制 | 作用 | 关键字段 |
| --- | --- | --- |
| `ForwardingNode` | 标记已迁移的桶，转发读写 | `hash = MOVED(-1)`，持有 `nextTable` |
| `helpTransfer` | 让写线程加入迁移 | 校验扩容戳、线程数、`transferIndex` |
| `transferIndex` | 任务游标，CAS 扣减领区间 | 从高位向低位分配 |
| `stride` | 单次领取的桶数 | 至少 16，避免粒度太细 |
| `sizeCtl` | 扩容状态与参与线程数 | 负数的低 16 位存线程数 |

**面试追问**：
- 追问：扩容期间 get 会不会读到旧数据？→ 答题要点：不会读到错位数据，遇到 `ForwardingNode` 会转发到新表；但整体是弱一致，可能读不到刚写入的值。
- 追问：为什么 `ForwardingNode` 的 hash 要用 -1？→ 答题要点：正常节点的 hash 是非负的，用负数做哨兵可以在不额外判断类型的情况下快速分流。
- 追问：所有线程都在 put 时谁来收尾？→ 答题要点：最后一个完成迁移的线程，通过 `sizeCtl` 计数归零判定，由它替换 `table` 并重算阈值。

### Q12. fail-fast 与 fail-safe 的区别？（初级） {#q12}

> 前置：迭代器、`modCount`、并发修改

**一句话结论**：fail-fast 在迭代时比较 `modCount` 与 `expectedModCount`，不一致立刻抛 `ConcurrentModificationException`；fail-safe 在迭代时操作一份快照或副本，遍历期间不抛异常，但可能看不到最新修改。

**先把话说白**：fail-fast 是"发现有人在我遍历时动了集合，我立刻报警"；fail-safe 是"你改你的，我在我开始遍历时拍的那张快照上走"。前者安全但脆弱，后者不报错但可能读到旧数据。

**底层原理**：

1. **`modCount` 的维护。** `AbstractList` 有一个 `transient int modCount`，记录结构性修改（增、删、清空、`trimToSize`）的次数。注意它**不是** `volatile`，所以并发下的可见性没有保证——这意味着 fail-fast 是"尽力而为"的检测，不能作为并发正确性的依赖。

2. **迭代器的检查点。** `ArrayList.Itr` 在构造时把 `modCount` 存进 `expectedModCount`，每次 `next()` 先调 `checkForComodification()`：若 `modCount != expectedModCount` 就抛 CME。所以异常抛在 `next()` 里，而不是在 `list.remove()` 那一行——这也是很多人看堆栈时困惑的地方。

3. **为什么 for-each 里 remove 会炸。** for-each 是 `Iterator` 的语法糖，`list.remove(o)` 会 `modCount++`，但迭代器手里的 `expectedModCount` 没变，下一次 `next()` 就抛。唯一的例外是删除倒数第二个元素时，`hasNext()` 恰好返回 false、循环结束，没机会检查——这个"偶然不报错"是最坑的地方，容易让人误以为写法没问题。

4. **fail-safe 的实现。** `CopyOnWriteArrayList` 的写操作在 `ReentrantLock` 保护下复制整个数组，替换 `array` 引用；迭代器持有构造时的那个数组快照，遍历的是旧数组，所以完全不受并发修改影响。`ConcurrentHashMap` 的迭代器是弱一致的：不复制，但不抛 CME，遍历时能看到部分新数据。

5. **代价。** `CopyOnWriteArrayList` 每次写都要复制整个数组，写多时性能灾难，且内存瞬时翻倍；只适合读极多、写极少且元素数量不大的场景（监听器列表、白名单、路由表）。`ConcurrentHashMap` 的弱一致迭代器不保证看到全部最新数据，需要强一致就得自己加同步。

**易混对比**：

| 维度 | fail-fast | fail-safe |
| --- | --- | --- |
| 代表 | `ArrayList`、`HashMap`、`HashSet` | `CopyOnWriteArrayList`、`ConcurrentHashMap` |
| 检测机制 | `modCount` 与 `expectedModCount` 比对 | 快照 / 弱一致遍历 |
| 并发修改时 | 抛 `ConcurrentModificationException` | 不抛异常 |
| 数据一致性 | 不保证，直接失败 | 弱一致，可能读旧值 |
| 额外开销 | 无 | 写时复制或额外的 volatile 读 |

**面试追问**：
- 追问：`modCount` 为什么不是 `volatile`？→ 答题要点：fail-fast 只是错误检测，不是并发保障；加 volatile 会拖慢所有集合操作，收益不匹配。
- 追问：遍历中怎么安全删除？→ 答题要点：`Iterator.remove()`（会同步 `expectedModCount`）、`removeIf`、或倒序下标删除。
- 追问：`ConcurrentHashMap` 的迭代器为什么不抛 CME？→ 答题要点：它基于数组的当前状态遍历，不维护 `modCount`，属于弱一致迭代器。

### Q13. LinkedHashMap 如何实现 LRU？（中级） {#q13}

> 前置：双向链表、访问顺序、`removeEldestEntry`

**一句话结论**：`LinkedHashMap` 继承 `HashMap`，在节点上加了 `before/after` 双向链表指针；构造时传 `accessOrder=true`，每次 `get` 或覆盖 `put` 都会通过 `afterNodeAccess` 把节点移到链表尾部，重写 `removeEldestEntry` 返回 true 即可在插入后自动淘汰链表头（最久未使用）。

**先把话说白**：HashMap 只管"放哪儿"，不管"顺序"。LinkedHashMap 额外用一根双向链表把所有节点串起来，插入顺序或访问顺序都能维护。既然最久没用的会被挤到链表头，那就在插入新元素后把头部删掉——这就是 LRU（Least Recently Used，最近最少使用）。

**底层原理**：

1. **链表是怎么挂上去的。** `LinkedHashMap.Entry` 继承 `HashMap.Node`，多了 `before`、`after` 两个指针；此外 `LinkedHashMap` 自己维护 `head`、`tail` 两个引用。节点在 `newNode` 时同时挂进哈希桶和双向链表，所以迭代顺序由链表决定，而不是桶顺序。

2. **`accessOrder` 决定顺序语义。** 默认 `false`，链表按插入顺序排列，重复 put 不改变位置。设为 `true` 后，`afterNodeAccess(e)` 会把被访问的节点从当前位置摘下、接到 `tail` 后面。注意这个方法在 `get`、`getOrDefault`、`put` 命中已有 key 时都会调用——所以**读操作会修改结构**，这一点在多线程下很危险。

3. **`afterNodeInsertion` 与淘汰。** 插入新节点后回调 `afterNodeInsertion(evict)`，它调用 `removeEldestEntry(first)`，默认返回 `false` 表示不淘汰。重写它，判断 `size() > capacity` 就返回 true，父类便会 `removeNode` 掉 `head` 指向的节点，也就是最久未使用的那一个。

4. **为什么 `accessOrder=true` 时不是线程安全的。** `get` 会改 `before/after` 指针，并发读会破坏链表结构，甚至形成环。需要并发 LRU 时不能直接用，得加锁或用 `ConcurrentHashMap` + 独立链表（如 Caffeine 的分段设计）。

5. **手写 LRU 的两种做法。** 一是上面这种"继承 LinkedHashMap + 重写 `removeEldestEntry`"，十行代码，适合面试快速作答；二是"HashMap + 自维护双向链表"，`get` 时把节点移到头部，`put` 超容量时删尾部，需要自己处理头尾哨兵、节点摘除与插入的指针顺序，约 40 行，能体现你确实理解链表操作。后者的优势是可以精细控制并发与过期策略。

```java
// 做法一：继承 LinkedHashMap，10 行实现 LRU
class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    LRUCache(int capacity) {
        // accessOrder = true：按访问顺序排序，get 会把节点移到队尾
        super(capacity, 0.75f, true);
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;   // 超出容量就淘汰链表头（最久未使用）
    }
}
```

```java
// 做法二：HashMap + 双向链表（带哨兵头尾，省去边界判断）
class LRU<K, V> {
    private static class Node<K, V> {
        K k; V v; Node<K, V> prev, next;
        Node(K k, V v) { this.k = k; this.v = v; }
    }
    private final Map<K, Node<K, V>> map = new HashMap<>();
    private final Node<K, V> head = new Node<>(null, null);  // 哨兵，head.next 是最新
    private final Node<K, V> tail = new Node<>(null, null);  // 哨兵，tail.prev 是最旧
    private final int cap;

    LRU(int cap) {
        this.cap = cap;
        head.next = tail; tail.prev = head;
    }
    private void unlink(Node<K, V> n) {           // 从链表摘除
        n.prev.next = n.next; n.next.prev = n.prev;
    }
    private void addFirst(Node<K, V> n) {         // 插到头部表示最近使用
        n.next = head.next; n.prev = head;
        head.next.prev = n; head.next = n;
    }
    public V get(K k) {
        Node<K, V> n = map.get(k);
        if (n == null) return null;
        unlink(n); addFirst(n);                   // 访问即提升优先级
        return n.v;
    }
    public void put(K k, V v) {
        Node<K, V> n = map.get(k);
        if (n != null) { n.v = v; unlink(n); addFirst(n); return; }
        if (map.size() == cap) {                  // 淘汰尾部最旧节点
            Node<K, V> old = tail.prev;
            unlink(old); map.remove(old.k);
        }
        n = new Node<>(k, v);
        map.put(k, n); addFirst(n);
    }
}
```

**易混对比**：

| 维度 | LinkedHashMap 方案 | HashMap + 双向链表方案 |
| --- | --- | --- |
| 代码量 | 约 10 行 | 约 40 行 |
| 淘汰触发点 | `removeEldestEntry` 返回 true | put 时手动判断并删尾 |
| 顺序维护 | JDK 通过 `afterNodeAccess` 完成 | 自己写 `unlink` 与 `addFirst` |
| 可控性 | 低，只能改淘汰条件 | 高，可加过期、并发、统计 |
| 线程安全 | 不安全（`get` 会改结构） | 取决于自己加的锁 |

**面试追问**：
- 追问：`accessOrder=true` 时为什么 `get` 也算结构性修改？→ 答题要点：会把节点移到链表尾，改变 `before/after` 指针，所以并发读不安全。
- 追问：`removeEldestEntry` 什么时候被调用？→ 答题要点：`afterNodeInsertion` 中，只在插入新节点后调用，覆盖已有 key 不触发。
- 追问：生产环境为什么不用它做缓存？→ 答题要点：没有过期时间、没有并发保护、没有统计与预热，通常用 Caffeine 或 Redis。

### Q14. TreeMap 与 HashMap 怎么选？（初级） {#q14}

> 前置：红黑树、`Comparator`、有序性

**一句话结论**：需要按 key 有序、范围查询（`subMap`、`headMap`、`tailMap`）或找邻近值（`floorKey`、`ceilingKey`）时用 TreeMap，它的操作是 O(log n)；只需要按 key 快速存取时用 HashMap，O(1)。

**先把话说白**：HashMap 是"按门牌号找人"，TreeMap 是"按姓氏笔画排好队找人"。前者找得快，但你说不出"排在张三后面的第一个人是谁"；后者能回答这类问题，代价是每次操作都要维持红黑树的平衡。

**底层原理**：

1. **红黑树的基本性质。** 每个节点非红即黑；根节点为黑；叶子（NIL）为黑；红节点的子节点必为黑；从任一节点到其所有叶子的路径上黑节点数相同。这五条性质保证最长路径不超过最短路径的两倍，树高被限制在 2log(n+1) 以内，所以查询、插入、删除都是 O(log n)。

2. **比较器与排序。** TreeMap 用 `Comparator` 或 key 的 `Comparable` 决定顺序。**关键坑**：TreeMap 判断两个 key 是否相等用的是 `compareTo() == 0`，不是 `equals()`。如果 `compareTo` 只比较了部分字段（比如只比 id 不比版本），两个业务上不同的对象会被当成同一个 key 覆盖掉。这是与 HashMap 最本质的语义差异。

3. **范围查询的能力。** `subMap(from, to)`、`headMap(to)`、`tailMap(from)` 返回的是**视图**（View），不是拷贝，对视图的修改会反映到原 map。`floorKey(k)` 返回小于等于 k 的最大 key，`ceilingKey(k)` 返回大于等于 k 的最小 key，这两个在"找最近的时间片""找匹配的区间"这类需求里非常有用。

4. **性能对比。** HashMap 的 put/get 平均 O(1)，最坏 O(log n)（JDK 8 树化后）；TreeMap 恒定 O(log n)。数据量小时两者差别不明显，百万级时 HashMap 明显更快。TreeMap 的节点还有 `left/right/parent/color` 四个额外字段，内存也更高。

5. **并发替代。** 需要有序且并发用 `ConcurrentSkipListMap`（跳表，O(log n)，无锁读），而不是 `Collections.synchronizedSortedMap`（全表锁）。Redis 的 ZSet 底层也是跳表，思路一致：用概率平衡替代严格平衡，换来实现简单和更好的并发性。

**易混对比**：

| 维度 | HashMap | TreeMap |
| --- | --- | --- |
| 底层结构 | 数组 + 链表 + 红黑树 | 红黑树 |
| 顺序 | 无序（按 hash 分布） | 按 key 排序 |
| 时间复杂度 | 平均 O(1) | O(log n) |
| key 相等判定 | `hash` 相等且 `equals` 为 true | `compareTo` 返回 0 |
| 范围查询 | 不支持 | `subMap` / `floorKey` 等 |
| null key | 允许一个 | 不允许（无法比较） |
| 并发替代 | `ConcurrentHashMap` | `ConcurrentSkipListMap` |

**面试追问**：
- 追问：TreeMap 的 key 可以为 null 吗？→ 答题要点：不能，第一次 put null 就会 NPE，因为要调用 `compareTo` 比较。
- 追问：`subMap` 返回的是拷贝吗？→ 答题要点：是视图，修改会写回原 map，且原 map 结构变化后视图可能抛 CME。
- 追问：为什么 ConcurrentSkipListMap 用跳表而不是红黑树？→ 答题要点：跳表的插入删除只影响局部指针，容易做无锁；红黑树的旋转会影响大片结构，难以无锁化。

### Q15. HashSet 如何复用 HashMap？为什么去重必须先 hashCode？（初级） {#q15}

> 前置：哈希表、`equals` 与 `hashCode` 契约

**一句话结论**：HashSet 内部就是一个 `HashMap<E, Object>`，add 的元素作为 key，value 统一放一个静态常量 `PRESENT`；去重时先用 `hashCode` 定位桶，再用 `equals` 在桶内比较，hash 不同就进不了同一个桶，所以只重写 `equals` 不重写 `hashCode` 会导致去重失效。

**先把话说白**：HashSet 没有自己的数据结构，它是把 HashMap 的 value 位置浪费掉，只借用 key 的唯一性。就像用储物柜的编号去重：编号是 hash 算出来的，撞到同一个柜子才需要比对里面是不是同一件东西。

**底层原理**：

1. **复用的具体写法。** `private transient HashMap<E, Object> map;` 加 `private static final Object PRESENT = new Object();`。`add(e)` 就是 `map.put(e, PRESENT) == null`，返回 true 表示原来没有；`remove(e)` 是 `map.remove(e) == PRESENT`；`contains(e)` 是 `map.containsKey(e)`；`size()` 直接委托。所以 HashSet 的内存开销和 HashMap 一致，每个元素都要一个 Node。

2. **去重的两步判定。** put 时先算 `hash(key)`，再 `(n-1) & hash` 定位桶；桶为空直接放入；桶非空则遍历，先比 `hash` 是否相等（快速失败），再比 `(k == key || key.equals(k))`。两步都满足才认为是同一个 key，执行覆盖。

3. **只重写 equals 会怎样。** 两个对象 equals 相等但 hashCode 不同（因为用的是 `Object` 的默认 hash，基于地址），会被分到不同的桶，遍历时根本碰不到对方，于是两个都插入成功。`HashSet` 里出现"重复"元素，`contains` 也返回 false。反过来只重写 hashCode 不重写 equals，桶对了但桶内比较走 `==`，同样去重失败。

4. **为什么先比 hash 再比 equals。** 这是性能优化。`equals` 可能很重（比较多个字段、甚至查库），而 int 比较是一条指令。先比 hash 能把绝大多数不同元素挡掉，只有 hash 相同的才需要真正比较。这也是为什么"hashCode 分布均匀"能提升性能——冲突少了，equals 调用次数就少。

5. **LinkedHashSet 与 TreeSet。** `LinkedHashSet` 继承 HashSet，但内部用的是 `LinkedHashMap`，所以能保持插入顺序；`TreeSet` 内部是 `TreeMap`，元素必须可比较，去重依据是 `compareTo() == 0` 而不是 equals。这三个类的行为差异，本质上就是它们背后 Map 的差异。

**易混对比**：

| 集合 | 底层 Map | 顺序 | 去重依据 | 复杂度 |
| --- | --- | --- | --- | --- |
| `HashSet` | `HashMap` | 无序 | hash + equals | 平均 O(1) |
| `LinkedHashSet` | `LinkedHashMap` | 插入顺序 | hash + equals | 平均 O(1) |
| `TreeSet` | `TreeMap` | 排序 | `compareTo == 0` | O(log n) |
| `CopyOnWriteArraySet` | `CopyOnWriteArrayList` | 插入顺序 | equals（线性扫描） | 读 O(n) |

**面试追问**：
- 追问：HashSet 的 value 为什么用同一个 `PRESENT` 对象？→ 答题要点：节省内存，所有 key 共享一个 value，不需要为每个元素创建新对象。
- 追问：`new HashSet<>(1000)` 的初始容量是多少？→ 答题要点：内部会 `tableSizeFor(1000/0.75+1)`，约 2048，避免扩容。
- 追问：自定义对象做 HashSet 元素，字段修改后会怎样？→ 答题要点：hash 变了，桶位置找不到，`contains` 返回 false，等于"丢失"，所以不要让参与 hash 的字段可变。

### Q16. 遍历集合时删除元素的正确姿势？（初级） {#q16}

> 前置：迭代器、fail-fast、`removeIf`

**一句话结论**：用 `Iterator.remove()` 或 JDK 8 的 `Collection.removeIf()`；不要在 for-each 里直接调用集合的 `remove`，它会让 `modCount` 与 `expectedModCount` 不一致，下一次 `next()` 抛 `ConcurrentModificationException`。

**先把话说白**：迭代器就像一个"读指针"，它记着自己出发时集合被改过几次。你绕过它直接改集合，它下次往前读的时候发现"哎，次数对不上"，就报警了。正确做法是通过迭代器自己删，它会顺便把自己的计数也更新掉。

**底层原理**：

1. **for-each 的真实形态。** `for (String s : list)` 编译后是 `for (Iterator<String> it = list.iterator(); it.hasNext(); )`。循环体里调用 `list.remove(s)` 改的是集合的 `modCount`，迭代器的 `expectedModCount` 还是旧值。

2. **异常的抛出点。** `ArrayList.Itr.next()` 第一行就是 `checkForComodification()`，比较 `modCount != expectedModCount` 就 `throw new ConcurrentModificationException()`。所以堆栈指向 `next()`，而不是你写 `remove` 的那一行。`forEach` 与 `removeIf` 走的是另一套逻辑，`removeIf` 内部用 `BitSet` 标记再批量删除，不会触发 CME。

3. **`Iterator.remove()` 为什么安全。** 它删完后执行 `expectedModCount = modCount`，把两边的计数重新对齐。约束是必须先 `next()` 再 `remove()`，且不能连续两次 `remove()`（`lastRet` 会被置 -1）。对 `ArrayList` 而言，每次 `remove` 还要移动数组，整体复杂度 O(n²)，数据量大时应该用 `removeIf`。

4. **倒序遍历的特例。** 对 `ArrayList` 用普通 for 倒序删除是安全的：`for (int i = size-1; i >= 0; i--) if (cond) list.remove(i);`。因为删除只会影响后面的元素下标，倒着走不会被跳过。但对 `LinkedList` 而言，`get(i)` 是 O(n)，倒序删除会退化成 O(n²)，不推荐。

5. **并发容器的差异。** `CopyOnWriteArrayList` 的迭代器基于快照，`remove()` 直接抛 `UnsupportedOperationException`；`ConcurrentHashMap` 的迭代器弱一致，遍历中删除不会抛异常，但可能看不到删除结果。所以"正确姿势"取决于容器类型，不能一套写法通吃。

```java
// 错误：for-each 中直接 remove，下一次 next() 抛 CME
for (String s : list) {
    if (s.isEmpty()) list.remove(s);
}

// 正确一：Iterator.remove，会同步 expectedModCount
Iterator<String> it = list.iterator();
while (it.hasNext()) {
    if (it.next().isEmpty()) it.remove();
}

// 正确二：removeIf（JDK 8），批量标记后统一删除，效率更高
list.removeIf(String::isEmpty);
```

**易混对比**：

| 写法 | 是否安全 | 适用容器 | 复杂度 |
| --- | --- | --- | --- |
| for-each + `list.remove` | 否，抛 CME | 无 | — |
| `Iterator.remove()` | 是 | 所有支持 remove 的集合 | ArrayList 下 O(n²) |
| `removeIf` | 是 | JDK 8+ 的 Collection | 通常 O(n) |
| 倒序 for + `remove(i)` | 是 | ArrayList 等随机访问列表 | O(n²) |
| `CopyOnWriteArrayList` 迭代器 remove | 否，抛不支持异常 | 无 | — |

**面试追问**：
- 追问：为什么有时候 for-each 里 remove 不报错？→ 答题要点：删的是倒数第二个元素时，`hasNext()` 已为 false，循环结束没机会检查，属于巧合。
- 追问：`modCount` 为什么设计成非 volatile？→ 答题要点：它只用于单线程的错误检测，加 volatile 会拖慢所有集合写操作。
- 追问：多线程遍历时怎么保证安全？→ 答题要点：用并发容器，或对集合加锁并复制一份再遍历。

### Q17. Arrays.asList、List.of、双括号初始化有哪些坑？（中级） {#q17}

> 前置：固定长度视图、不可变集合、匿名内部类

**一句话结论**：`Arrays.asList` 返回的是固定长度的数组视图，不能 `add`/`remove` 但可以 `set`，且会与原数组互相影响；`List.of`（JDK 9）是真正不可变，任何修改都抛异常且不接受 null；双括号初始化会创建匿名内部类并隐式持有外部类引用，容易造成内存泄漏。

**先把话说白**：这三种写法看起来都是"快速造一个 List"，但它们的身份完全不同：一个是"套在数组外面的壳"，一个是"焊死的只读列表"，一个是"偷偷生成了一个子类"。用错地方就是线上事故。

**底层原理**：

1. **`Arrays.asList` 的本质。** 它返回 `java.util.Arrays.ArrayList`（一个私有静态内部类），内部直接持有传入的数组 `a`，`size()` 返回 `a.length`。因为它没有实现 `add`/`remove`，父类 `AbstractList` 的默认实现抛 `UnsupportedOperationException`；但 `set` 是实现了的，会直接改原数组。所以 `list.set(0, x)` 之后，原数组也变了——这是"视图"而非"拷贝"。

2. **基本类型数组的陷阱。** `Arrays.asList(new int[]{1,2,3})` 得到的是 `List<int[]>`，size 为 1，唯一元素是那个数组。因为泛型不支持基本类型，`asList(T... a)` 的 `T` 被推断为 `int[]`，整个数组成了**一个**可变参数。必须用 `Integer[]` 或 `Arrays.stream(ints).boxed().collect(...)`。

3. **`List.of` 的不可变性。** JDK 9 引入，返回的是 `ImmutableCollections.ListN` 等实现，所有修改方法直接抛 `UnsupportedOperationException`，包括 `set`。同时**不接受 null**，`List.of("a", null)` 直接 NPE。它是值语义的不可变集合，适合做常量、做方法返回值、做防御性拷贝（`List.copyOf`）。

4. **双括号初始化的代价。** <code v-pre>new HashMap<>() {{ put("a", 1); }}</code> 实际创建了一个匿名子类，外层括号是 `new`，内层括号是实例初始化块。三个问题：一是匿名内部类隐式持有外部类实例的引用，如果这个 map 被长期持有（比如放进静态字段或缓存），外部类对象就无法回收，典型的内存泄漏；二是每次都会生成一个 `Outer$1.class`，增大 jar 体积、影响类加载；三是序列化时外部类不可序列化就会失败。正确做法是用 `Map.of`（JDK 9，最多 10 个键值对）或 Guava 的 `ImmutableMap.builder()`。

5. **怎么选。** 只是临时包装一个已有数组并且需要回写 → `Arrays.asList`；要一个不可变常量集合 → `List.of` / `Map.of` / `Set.of`；需要可变且要初始化 → `new ArrayList<>(List.of(...))`。另外 `Collections.unmodifiableList` 也是视图，原集合变了它也跟着变，与 `List.of` 的"真不可变"不同。

**易混对比**：

| 方式 | 能否 add/remove | 能否 set | 是否允许 null | 与原数组关系 |
| --- | --- | --- | --- | --- |
| `Arrays.asList(arr)` | 否 | 是 | 是 | 视图，互相影响 |
| `List.of(...)` | 否 | 否 | 否 | 拷贝，无关联 |
| `Collections.unmodifiableList(l)` | 否 | 否 | 取决于原集合 | 视图，原集合变它也变 |
| `new ArrayList<>(Arrays.asList(arr))` | 是 | 是 | 是 | 独立拷贝 |
| 双括号初始化 | 是 | 是 | 是 | 独立，但持有外部类引用 |

**面试追问**：
- 追问：`Arrays.asList` 为什么不能 add？→ 答题要点：返回的是 `Arrays` 的内部类，底层是定长数组，没有实现扩容逻辑，父类默认实现抛异常。
- 追问：`List.of` 和 `Collections.unmodifiableList` 有什么区别？→ 答题要点：前者是独立不可变副本，后者是只读视图，原集合修改仍会反映。
- 追问：双括号初始化除了内存泄漏还有什么问题？→ 答题要点：生成额外 class 文件、序列化失败、调试时类名怪异、IDE 告警。

### Q18. PriorityQueue 的底层结构与 topK 怎么用？（中级） {#q18}

> 前置：二叉堆、上浮与下沉、TopK

**一句话结论**：PriorityQueue 用数组存储的二叉小顶堆实现，`add` 通过上浮（siftUp）、`poll` 通过下沉（siftDown）维护堆序，两者都是 O(log n)，`peek` 是 O(1)；求"最大的 K 个"要维护一个容量为 K 的**小顶堆**，堆顶是这 K 个里最小的，新元素比堆顶大才替换。

**先把话说白**：堆不是排序数组，它只保证"父节点不大于子节点"，所以堆顶永远是最小值，但整体遍历出来是乱序的。求 topK 时用小顶堆是个反直觉但很实用的技巧：用一个只能装 K 个的筛子，筛子的门槛是当前 K 个里最小的那个，比门槛大的才配进来。

**底层原理**：

1. **数组表示的完全二叉树。** `queue[i]` 的左子节点是 `queue[2i+1]`，右子是 `queue[2i+2]`，父节点是 `queue[(i-1)/2]`。用数组而不是链式结构，是因为完全二叉树没有空洞，数组能紧凑存储且缓存友好。默认初始容量 11，扩容时小于 64 翻倍，否则增长 50%。

2. **上浮与下沉。** `offer` 把新元素放到数组末尾，然后不断与父节点比较，比父节点小就交换，直到满足堆序，这是 `siftUp`。`poll` 取出 `queue[0]`，把末尾元素放到堆顶，然后与较小的子节点比较并下移，这是 `siftDown`。两者都只走一条从根到叶的路径，所以是 O(log n)。

3. **为什么遍历不保证有序。** 堆只维护父子偏序，兄弟之间、跨层之间没有约束。要对 PriorityQueue 排序必须反复 `poll`，得到的是 O(n log n) 的堆排序。这一点常被误解为"PriorityQueue 是有序队列"，它不是。

4. **topK 的正确姿势。** 求"最大的 K 个"用小顶堆：堆里始终保持 K 个候选，堆顶是当前候选中最小的。新元素若大于堆顶，就 `poll` 掉堆顶再 `offer` 新元素；否则直接丢弃。遍历完一遍，堆里就是最大的 K 个。时间复杂度 O(n log k)，空间 O(k)。求"最小的 K 个"则反过来用大顶堆（`Comparator.reverseOrder()`）。如果 K 接近 n，直接全排序更快；K 很小时堆的优势明显。

5. **边界。** PriorityQueue 非线程安全，并发用 `PriorityBlockingQueue`（无界，`take` 会阻塞）；不接受 null（无法比较）；元素要么实现 `Comparable`，要么构造时传 `Comparator`；迭代器不保证顺序，也不支持并发修改。

```java
// 求数组中最大的 K 个元素：容量为 K 的小顶堆
static List<Integer> topK(int[] nums, int k) {
    PriorityQueue<Integer> heap = new PriorityQueue<>(k);   // 默认小顶堆
    for (int n : nums) {
        if (heap.size() < k) {
            heap.offer(n);
        } else if (n > heap.peek()) {   // 比当前门槛大才替换
            heap.poll();                // 弹出当前 K 个里最小的
            heap.offer(n);
        }
    }
    return new ArrayList<>(heap);       // 注意：顺序不保证
}
```

**易混对比**：

| 场景 | 堆类型 | 堆顶含义 | 比较方向 |
| --- | --- | --- | --- |
| 求最大 K 个 | 小顶堆 | K 个候选里最小的 | 新元素 > 堆顶则替换 |
| 求最小 K 个 | 大顶堆 | K 个候选里最大的 | 新元素 < 堆顶则替换 |
| 优先任务调度 | 小顶堆（按优先级） | 优先级最高的任务 | 自定义 `Comparator` |
| 合并 K 个有序链表 | 小顶堆 | 当前最小头节点 | 按节点值比较 |

**面试追问**：
- 追问：topK 为什么不用大顶堆？→ 答题要点：大顶堆堆顶是最大值，无法快速判断新元素是否该进入候选集，也无法快速淘汰。
- 追问：`PriorityQueue` 的 `iterator()` 有序吗？→ 答题要点：无序，只保证堆序；要按序输出必须反复 `poll`。
- 追问：海量数据求 topK 怎么处理？→ 答题要点：分治，先按 hash 或范围切分到多台机器各自求 topK，再对小规模的 K×机器数 结果做一次归并。

## 五、本章速记卡 {#s5}

- ArrayList 是 `Object[]`，无参构造首次 add 才扩到 10，之后按 1.5 倍（`old + (old>>1)`）扩，`Arrays.copyOf` 只复制引用。
- ArrayList vs LinkedList 的真实差距是缓存局部性，不是 O(1)/O(n)；队列场景优先 `ArrayDeque`。
- HashMap 默认容量 16、负载因子 0.75、阈值 12；容量永远是 2 的幂，由 `tableSizeFor` 向上取整。
- JDK 7：数组 + 链表 + 头插 + 四次扰动；JDK 8：加红黑树、改尾插、扰动简化为 `h ^ (h>>>16)`。
- 扰动把高 16 位折到低 16 位，因为 `(n-1) & hash` 只用到低位；该式等价于 `hash % n` 的前提是 n 为 2 的幂。
- 扩容拆分看 `hash & oldCap`：0 留原位 j，1 移到 j + oldCap，全程不重算 hash。
- 树化 8、退化 6、最小树化容量 64；8 来自泊松分布（概率约 6e-8），6 是防抖缓冲，64 是"先扩容再树化"。
- JDK 7 并发扩容头插成环 → get 死循环；JDK 8 不成环但会覆盖丢数据；`++size` 任何版本都不准。
- ConcurrentHashMap 7 = Segment（ReentrantLock）分段锁；8 = CAS + 桶头 synchronized + 红黑树。
- JDK 8 计数 = `baseCount` + `CounterCell[]`（带缓存行填充），思想同 LongAdder，`size()` 是估算值。
- 扩容协助靠 `ForwardingNode`（hash = -1）+ `transferIndex` 领任务 + `sizeCtl` 记录线程数。
- fail-fast 靠 `modCount`（非 volatile），异常抛在 `next()`；正确删除用 `Iterator.remove` 或 `removeIf`。
- LinkedHashMap 的 LRU = `accessOrder=true` + `afterNodeAccess` 移尾 + 重写 `removeEldestEntry`。
- `Arrays.asList` 是定长视图（可 set 不可 add），`List.of` 是真不可变（不可 set、不许 null），双括号会泄漏外部类引用。
- PriorityQueue 是二叉小顶堆，求最大 K 个用小顶堆，复杂度 O(n log k)。

## 七、动手实验与失败现象 {#s7}

### 实验：为什么容量必须是 2 的幂

```java
public class IndexLab {
    public static void main(String[] args) {
        int h = "hello".hashCode();
        int spread = h ^ (h >>> 16);
        for (int cap : new int[]{15, 16, 17, 32}) {
            System.out.printf("cap=%-3d %%cap=%-3d (cap-1)&hash=%-3d 相等=%b%n",
                    cap, spread % cap, (cap - 1) & spread,
                    (spread % cap) == ((cap - 1) & spread));
        }
    }
}
```

运行结果（JDK 21.0.9）：

```text
cap=15  %cap=11  (cap-1)&hash=10  相等=false
cap=16  %cap=11  (cap-1)&hash=11  相等=true
cap=17  %cap=3   (cap-1)&hash=16  相等=false
cap=32  %cap=27  (cap-1)&hash=27  相等=true
```

位与比取模快得多，但 `(cap-1) & hash` 只有在 cap 是 2 的幂时才等价于 `hash % cap`——因为此时 `cap-1` 的二进制全是低位 1，位与恰好截出低 n 位，与取模同义。容量是 15、17 这类数时两者结果不同，桶下标就错了。

**改一个地方看看**：把 `cap` 改成 64，仍然相等；改成 24（3 的倍数但不是 2 的幂），立刻不等。这也解释了 `HashMap` 的 `tableSizeFor` 为什么要把传入容量向上取到最近的 2 的幂，以及扩容为什么每次翻倍而不是加固定值。

### 失败现象：for-each 里删除元素

```java
import java.util.ArrayList;
import java.util.Arrays;
import java.util.List;

public class RemoveLab {
    public static void main(String[] args) {
        List<String> list = new ArrayList<String>(Arrays.asList("a", "b", "c"));
        for (String s : list) {
            if ("a".equals(s)) list.remove(s);
        }
    }
}
```

**症状**：`java.util.ConcurrentModificationException`，堆栈指向 `ArrayList$Itr.next`，而不是 `remove` 那一行——异常在下一次迭代时才抛，所以看起来"删成功了，下一轮才炸"。

更麻烦的是它**不总是抛异常**。把条件换成删除 `"b"`（倒数第二个元素），程序会正常结束、不报任何错：遍历只到 `a` 和 `b`，`c` 从头到尾没被处理，集合最后是 `[a, c]`。线上这类问题不会报错，只会表现为"偶尔漏处理一条"，比抛异常难查得多。

**原因**：for-each 编译后是迭代器遍历。`ArrayList.remove` 会改 `modCount`，迭代器的 `expectedModCount` 没跟着变，`next()` 一进方法就检查两者是否相等，不等即抛。之所以删 `"b"` 不抛，是因为删完后 `size` 正好等于 `cursor`，`hasNext()` 判定"没有下一个"直接结束循环，根本没走到 `next()` 的检查。单线程也会触发，和并发无关，`modCount` 只是"结构性修改计数器"（回指 Q12、Q16）。

正确写法是 `Iterator.remove()` 或 `list.removeIf(...)`，前者会同步更新 `expectedModCount`。
