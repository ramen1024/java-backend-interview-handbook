# 《Java 后端面试系统化复习》写作规范（所有章节必须严格遵守）

## 0. 读者与目标
- 读者：1~5 年经验的 Java 后端工程师，正在准备跳槽面试；也包含校招同学。
- 目标：读一章能"讲得出来"，而不是"看过"。每道题的答案都应当能直接作为面试口头回答的骨架。
- 判断标准：如果一段话只是把八股结论重复一遍，没有解释"为什么这么设计 / 不这样会怎样 / 真实场景里怎么用"，就视为不合格。

## 1. 语言与语气
- 简体中文，技术名词首次出现时给出英文（如 垃圾回收（GC, Garbage Collection））。
- 平实、克制、有判断。不用"宝子们""干货满满""一文带你彻底搞懂"这类营销词，不用 emoji。
- 允许用第二人称"你"和比喻，但比喻之后必须回到真实机制，不能只停在比喻。
- 不要写"面试官想听到的是……"这样的揣测句，直接讲技术本身；追问方向统一放在每题末尾的固定小节。

## 2. 每章固定结构（顺序不可变）

```
# 第 N 章 章节名

> 一句话定位：本章在面试中的位置。

## 一、本章考察重点概览
- 3~5 条要点，说明面试官真正在筛什么能力。
- 一个表格：| 考点 | 出现频率 | 难度 | 说明 |（频率用 高/中/低，难度用 初级/中级/高级）

## 二、复习优先级
表格：| 优先级 | 题目编号 | 理由 |，P0 必须背到能画图，P1 要能说清主线，P2 有余力再看。
并给一句"时间分配建议"（例如：本章建议 2 天，P0 占 70% 时间）。

## 三、高频面试题清单
表格：| 编号 | 题目 | 面试难度 | 阅读门槛 | 优先级 | 一句话答案 |
编号 Q1..Qn 连续，一句话答案控制在 40 字内。
面试难度用 初级/中级/高级，阅读门槛用 低/中/高，两者不可混为一谈（定义见第 3 节末）。

## 四、题目详解
### Q1. 题目（难度）
（按第 3 节模板展开，逐题）

## 五、本章速记卡
- 8~15 条要点，每条一行，用于考前 10 分钟扫读。
- 可以包含一个 ASCII/Mermaid 流程图或一张对比表。

## 六、本章自测清单
- 5~8 个"能否不看文档讲出来"的自问句。

## 七、动手实验与失败现象
### 实验：<一句话说明验证什么>
- 一个完整可运行的 Java 程序（含 main，10~35 行，JDK 8 可编译）。
- 给出真实运行输出（代码块标 text），不得编造。
- "改一个地方看看"：说明改动哪个值 / 哪一行，输出会怎么变，为什么。

### 失败现象：<一句话说明坏在哪>
- 一段能编译但行为错误的代码，或一个错误配置。
- 症状：可观察到的现象（输出、异常、卡住、数据不对）。
- 原因：一句话点破机制，并回指本章某道题。
```

## 3. 每道题详解的固定模板

```
### Q1. 题目（中级）

> 前置：`概念 A`、`概念 B`（2~3 个，只列名字不解释；读者据此判断该不该读这题）

**一句话结论**：1~2 句，能被直接背下来，包含最关键的两个关键词。

**先把话说白**：2~5 句，用场景或类比建立直觉。禁止只写类比不落地。

**底层原理**：分 3~6 个层次递进展开，每层一个小标题或加粗引导词。
- 层次顺序建议：是什么 → 怎么做的 → 为什么这样做 → 边界与代价。
- 涉及版本差异必须标注，如"JDK 8 用 数组+链表+红黑树；JDK 8 之后……"。
- 涉及流程必须能看出"输入 → 中间状态 → 输出"。

**代码 / 图示**（按需）：Java 代码控制在 10~30 行，带关键注释；流程用 Mermaid 或编号步骤描述。

**易混对比**（按需）：Markdown 表格，2~4 列，至少 3 行。表头写清对比维度，不要写"区别1/区别2"。

**面试追问**：3~4 条，格式 `- 追问：xxx → 答题要点：xxx`。

**加分点 / 易错点**（按需）：1~3 条，写"大多数人会答错的地方"或"能体现深度的一句"。
```

## 3.1 面试难度与阅读门槛（两个维度，不可合并）

| 维度 | 取值 | 含义 | 回答的问题 |
| --- | --- | --- | --- |
| 面试难度 | 初级 / 中级 / 高级 | 这道题通常出现在什么级别的面试里 | 值不值得投入时间 |
| 阅读门槛 | 低 / 中 / 高 | 读懂这道题需要多少前置知识 | 现在能不能读 |

- 门槛 低：会写 Java、用过该技术即可读，不依赖其他章节。
- 门槛 中：需要知道基础概念（如堆与栈、锁、索引、分区），但不必深入。
- 门槛 高：需要先读本书其他章节，或有对应生产经验；直接读会"认识每个字但接不上"。
- 门槛高的题必须在详情页给出可回退的前置章节或第 0 章术语条目。

## 4. 深度与准确性要求
- 不能只有结论。每个结论后面至少跟一句机制解释。
- 数字要保守：不要编造 benchmark（如"QPS 十万"）。涉及默认值时标注来源范围，如"JDK 8 默认 Parallel 收集器，堆小于 2G 且 CPU 少时"。
- 区分"规范"与"实现"：如 JMM 是规范，HotSpot 是实现；SQL 标准与 InnoDB 行为不同要说明。
- 版本相关要写清：JDK 8 / JDK 11 / JDK 17 / JDK 21；MySQL 5.7 / 8.0；Spring Boot 2.x / 3.x；Redis 6 / 7。
- 禁止写成"万能答案"。同一个问题如果有主流方案 A 和少数方案 B，要说明取舍。
- 涉及"为什么不用另一种方案"时，给出 2~3 条具体代价，而不是"性能更好"。

## 5. 篇幅与密度
- 每章 8000~13000 字（中文字符），题目数量 12~18 道（按各章 brief 要求）。
- 单题 400~900 字；P0 核心题可到 1200 字。
- 不要为了凑字数写废话。宁短勿水，但 P0 题必须讲透。
- 代码块、表格不算水分，鼓励用表格承载对比信息。

## 6. Markdown 约定
- 章内标题只用 `##`（一级小节）、`###`（题目）、`####`（题目内部小标题，尽量少用）。
- 表格必须有表头分隔行；代码块必须标语言（java / sql / bash / text / mermaid）。
- 术语一致性：统一用"线程池""阻塞队列""回表""聚簇索引""间隙锁（Gap Lock）"等标准译名，首次出现给英文。
- 不要在文档中写"本文""笔者""如上所述"这类冗余连接词。
- 章末不要写"总结：本章我们学习了……"这种空转段落，速记卡已经承担该功能。

## 7. 禁止项
- 禁止 emoji、禁止 HTML 标签（Mermaid 除外）。
- 禁止把同一段内容在"概览"和"详解"里原样重复。
- 禁止出现"由于篇幅原因不再赘述"。
- 禁止不确定却写得斩钉截铁；不确定时用"多数实现""通常""在 HotSpot 中"限定。
